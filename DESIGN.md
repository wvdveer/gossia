# Cliotree Design

A spreadsheet-like desktop application (Rust + egui, later wasm) in which each sheet is a **tree defined by a schema** (JSON Schema or XSD) rather than a 2D grid. Cells at any node can hold a **Python expression** whose result must match the node's schema type.

**Scope.** Version 1 is the desktop application. **Reports** and the **web (wasm) port** are deliberately deferred to a later version; their designs are kept in this document for planning and are marked as such (see Later versions).

**Status.** The design for v1 is complete. Every question raised during design review has been decided, and the decisions are in the sections below. What remains is implementation, in the order given under Build order, plus the risks listed at the end that can only be settled by building and measuring.

## Core model

**Workbook**: named Sheets (tabs), a trust flag, and embedded Python modules. Tabs come in two kinds:
- **Data Tabs** (including schema tabs): hold a data tree bound to a schema, as described below. A Data Tab can be shown in several **views**: the Data tree and its forms (see Forms).
- **Report Tabs** *(later version)*: read-only visual presentations of data from other tabs (see Reports).

Forms are views of a Data Tab, not tabs.

Rules for tabs:
- Tab names must be valid Python identifiers, must not be reserved words, and must be unique ignoring case (enforced on create and rename; see Names and reserved words).
- Each Data Tab has a schema reference, a data tree, and formula overlays.

**Data tree**: one format-neutral `Value` enum serves JSON and XML:
`Null | Bool | Int(i64) | Float(f64) | Str | Date | DateTime | Array(Vec<Node>) | Object(IndexMap<String, Node>) | Error(ErrorValue)`.
`Error` exists only in memory: it is how a failed formula's node is represented, and it is never written into a data file (see Stored values).
- Each node has a stable `NodeId`.
- XML maps onto the same model: attributes become fields prefixed `@`, text becomes `#text`, repeated elements become arrays. A format adapter handles the round trip; the evaluator never sees XML or JSON.
- Data format follows the schema language: JSON Schema gives JSON data, XSD gives XML data. The two meta-schemas (JSON Schema, XSD) are built in, so schema sheets get ordinary tree editing and validation (see Schema binding).

**Comments and structure fidelity.** Round-tripping is lossy only for incidental formatting. What the user wrote deliberately is preserved.
- **Field order.** Object fields keep the order of the schema's declared properties (JSON) or sequence (XML), and array items keep their order. Export and save write them in that order. A schema's declared order is itself user-authored and preserved.
- **Comments (XML tabs only).** A node on an **XML** tab can carry a **comment**: free text, like an Excel cell comment. **Comments are not available on JSON tabs**, because JSON has no comments. The comment commands do not appear on a JSON tab at all.
  - **In the document.** Comments are stored as real **XML comments** in `data.xml`, so they travel with the file and are visible to any other XML tool. A comment immediately before an element or attribute is that node's comment; if several comments precede one node, they are joined with line breaks and written back as a single comment. Comments elsewhere (before the root, after the root, at the end of an element) belong to the root or to the enclosing element, tagged with their position, and are written back in the same place.
  - **In memory** a comment is part of its node, so it moves with the node when items are inserted, deleted, or sorted (unlike formulas, which belong to a location).
  - **In the UI** comments look and work as they do in Excel (see Comments in the UI below).
  - **Not visible to Python.** Formulas cannot read or write comments; they are part of the document, not of the data.
  - **XML restrictions.** The text of an XML comment cannot contain `--` or end with `-`. The comment editor refuses such text with a message saying why. Comments imported from a file are always valid.
- **XML details preserved:** the XML declaration (version, encoding, standalone), namespace prefix and declarations, attribute order, element order.
- **Not preserved (accepted):** indentation and other insignificant whitespace (regenerated on write), CDATA sections (become ordinary text), entity and character-reference spelling, attribute quote style, empty-element syntax (`<a/>` vs `<a></a>`), processing instructions, and DOCTYPE declarations (dropped with a warning; DTD entities are never expanded and external entities are never fetched). Text content inside an element is preserved exactly, including its whitespace.
- **JSON details not preserved:** number spelling (`1e3` becomes `1000`, `1.0` stays a float), and indentation. Integers beyond the signed 64-bit range import as floating-point numbers, with a warning.

**Schema model**: JSON Schema and XSD are lowered once, at load, into a single internal `TypeSpec`:
- Kinds: `String | Integer | Number | Bool | Array(items, min/max) | Object(fields, required) | Map(value) | Enum`.
- `Map` is a string-keyed dictionary with a uniform value type. It comes only from JSON Schema (`additionalProperties` with a schema) and has no XSD counterpart.
- Named types may be referenced recursively (types are held by id, not inlined). Data is finite, so recursion terminates.
- Constraints: pattern, range, length.
- `OneOf` is reserved for a later version and is not produced in v1 (both subsets exclude unions).
- A source map points each `TypeSpec` back to its schema location for error messages.

**Schema binding**: every Data Tab declares its schema in exactly one of two ways:
- **Built-in meta-schema**: the sheet is itself a schema document. The application bundles a JSON Schema for JSON Schema and an XML Schema for XML Schema, each describing exactly the supported subset of its language (see below). Choosing one fixes the sheet's format (JSON or XML), and the sheet is edited, validated, and given formulas like any other tree.
- **Sheet reference**: the sheet names another workbook sheet that contains its schema. That sheet must itself be a schema sheet (bound to a built-in meta-schema). The referenced sheet's schema language determines the data format: JSON Schema gives JSON data, XSD gives XML data.

Rules:
- The built-ins are bundled in the binary, read-only, and are not workbook sheets. They are referenced by identifier (e.g. `builtin:jsonschema`, `builtin:xsd`), never by sheet name.
- A sheet reference must resolve to a schema sheet in the same workbook. A missing sheet, a non-schema sheet, or a cycle in the chain is a load-time error shown on the sheet.
- When a schema sheet is edited, every sheet bound to it is re-lowered to `TypeSpec` and revalidated, and dependent formula results are rechecked.
- **Auto-update.** A schema sheet has an **auto-update** checkbox, off by default, shown in a bar above its tree together with a line saying which tab uses it (for example *Used by: Orders*).
  - **When it is on, the tab that uses the schema can edit the schema** from its own tree grid or tabular view (see Editing the schema from a data tab). When it is off, those commands are unavailable, and the tab's own tooltip says which schema sheet to switch on.
  - **It can be switched on only while exactly one tab uses the schema.** With no users or with two or more it is disabled, and the tooltip says why. A single user means a schema edit can only ever change that one tab, so it can never silently change another.
  - **While it is on, no second tab may be bound to the schema sheet.** Creating, importing, or rebinding a tab to it is refused with a message that names the checkbox.
  - A file that breaks these rules (auto-update on with two users) still opens, as with other rule breaches: auto-update is treated as off and flagged until the user resolves it.
  - The setting is stored with the schema sheet in the manifest. Toggling it is an undoable edit and not executable content, so it does not affect trust.
- A schema sheet must be valid against its meta-schema, and also lowerable to `TypeSpec` (so it may use only the supported subset of its language).
- Neither bundled meta-schema is the official one (the W3C `XMLSchema.xsd` or the JSON Schema 2020-12 meta-schema). Each is our own schema that describes exactly the supported v1 subset, written using only that subset, and lowered through the normal path like any other schema. The two are kept parallel: the same concepts, the same restrictions, and the same exclusions. Widening a subset means updating its meta-schema in the same change.
- **Meta-schema** means a schema that describes schema documents, and only these two are meta-schemas. The application also bundles ordinary built-in schemas for its own design documents: `builtin:form` (form designs) and, in a later version, `builtin:report` (report designs). These describe designs, not schemas, are not meta-schemas, and are never the binding of a tab. They exist only to validate those documents, which are written in the same subset and lowered through the same path.
- Meta-schemas without unions can only approximate the language. Anything the structure can't express is caught by lowering, which reports precise errors (e.g. an `enum` with a bad value) and is the authoritative check.

### Schema subsets (v1)

Both languages are reduced to the same core: closed record types, arrays, and simple types with a few restrictions. The features line up as follows.

| Concept | JSON Schema (2020-12) | XSD |
|---|---|---|
| Record with ordered fields | `type: object` with `properties` (declared order kept) | `xs:complexType` with `xs:sequence` of `xs:element` |
| Optional / required field | name absent from / present in `required` | `minOccurs` 0 / 1 |
| Array | `type: array`, `items`, `minItems`, `maxItems` | `maxOccurs` > 1 (or `unbounded`) on an element |
| Attributes | not applicable | `xs:attribute`; text via `xs:simpleContent` |
| Reusable types, recursion | `$defs` plus local `$ref: "#/$defs/Name"` | named `xs:complexType` / `xs:simpleType`, `type=` references, `xs:element ref` |
| String / boolean | `string`, `boolean` | `string`, `boolean` |
| Numbers | `integer`, `number` | `integer`, `decimal`, `double` |
| Dates | `string` with `format: date` / `date-time` (a string constraint only; the node stays a string) | `date`, `dateTime` (typed nodes holding dates) |
| Enumeration | `enum` | `xs:enumeration` |
| Pattern | `pattern` | `xs:pattern` |
| Numeric range (inclusive) | `minimum`, `maximum` | `minInclusive`, `maxInclusive` |
| Length | `minLength`, `maxLength` | `minLength`, `maxLength` |
| Documentation | `title`, `description` (annotation only) | `xs:annotation` / `xs:documentation` (annotation only) |
| Map (dictionary) | `additionalProperties: <schema>`, instead of `properties` | none |

Objects are **closed**: no properties beyond those declared. The one deviation is `Map`, which allows any string key with one value type, and is the only way for an object to have undeclared keys. This is needed because the JSON Schema meta-schema itself contains such maps (`properties` and `$defs`). A schema object uses `properties` or a schema-valued `additionalProperties`, not both.

A schema document has one root: the top-level schema for JSON Schema, and the single global `xs:element` for XSD (other global declarations must be types).

Excluded from both, with the same intent: unions and alternatives (`oneOf` / `anyOf` / `allOf` / `not`, `xs:choice`, `union`), conditional schemas (`if` / `then` / `else`), nullable / `null` (`type` arrays, `nillable`), open content (`patternProperties`, `unevaluated*`, `xs:any`), type extension and derivation, remote or non-local references (`$ref` to a URL or `$anchor`, `xs:import` / `xs:include`), identity constraints (`uniqueItems`, `key` / `keyref`), exclusive ranges, `multipleOf`, `const`, tuple arrays (`prefixItems`), `contains`, `dependent*`, mixed content, multiple namespaces, `list`.

An unsupported construct or keyword fails at schema load with an error naming it and its location. Nothing is silently ignored. Unknown annotation keys are also an error, so typos aren't hidden.

Numeric enumerations are not in v1: `enum` is limited to string-typed nodes, because the meta-schemas have no way to say "any scalar" without a union. Both languages share this limit.

### Notes on the XSD side

- `maxOccurs="unbounded"` is a union in the official XSD, so the meta-schema types it as a string with a `pattern` of `[0-9]+|unbounded`.
- Other numeric and string built-in types (`int`, `long`, `float`, `token`, ...) alias to the listed ones.
- Type references resolve within one schema document and one target namespace.

### Likely first additions

Unions (`xs:choice`, `oneOf` / `anyOf`) are the most probable first widening. They lower to `OneOf`, which is why that kind is reserved, and nullable types and numeric enums come next. Each widens both languages together.

## Formulas

A formula is a Python expression string attached to a node **location** (its path), with a cached result. Formulas are stored beside the data (a parallel `formulas` map keyed by path), not inside it, so the data stays valid JSON / XML.

**Entering formulas.** Formulas are entered as in Excel.
- A **formula bar** sits above the tree grid. For the selected node it shows the node's path (for example `Orders.items[2].price`) and its content: the formula text if it has one, otherwise the literal value. Cells can also be edited in place (F2 or double-click), and the bar and the cell edit the same text.
- Text that **starts with `=`** is a formula, and what follows is a single Python expression: `=SUM(Orders.items.price)`. Anything else is a literal, parsed to the node's type.
- To enter a literal string that begins with `=`, start it with an apostrophe: `'=total` is stored as `=total`. A single leading apostrophe on entry is removed, so a literal that really starts with an apostrophe is typed with two. The apostrophe rule applies only to text-typed nodes.
- The expression is a Python *expression*, not statements. It may span lines (Shift+Enter in the bar) when the line breaks fall inside brackets, and may use lambdas and comprehensions. Surrounding whitespace is ignored.
- Enter commits and Esc cancels. A commit is one undoable entry. Replacing a formula with a literal removes the formula. Clearing the text removes both, leaving an absent optional node or an empty flagged required one.
- Committing queues a recalculation. The cell shows its last value (or empty) with the pending marker until the result arrives (see Evaluation and scheduling).
- Pasting a formula pastes its text verbatim, with no reference adjustment, as references are literal.
- On a node inside a computed subtree the bar is read-only and shows which formula and location computes it.
- Report expressions, form button conditions, and similar designer fields take a bare Python expression and do not use the `=` prefix.

**Syntax errors.** A formula whose text does not parse is **not rejected**. It is kept, and the node holds the error value `#SYNTAX!`, whose message gives Python's description and the line and column. The text stays in the overlay so the author can correct it. As for other errors, dependents see the error (see Error values), and the `ErrorValue`'s `.exception` is the `SyntaxError`.
- Parsing only reads the text and never runs it, so the syntax check also happens in an untrusted workbook.
- A formula rejected by the double-underscore attribute check (see Python engine) is reported the same way, as `#SYNTAX!` with a message saying that double-underscore access is not allowed.
- While the author types, the bar shows a non-blocking syntax hint. It never prevents committing.
- **Insert Function.** An *fx* button beside the formula bar opens a dialog, as in Excel, listing the functions a formula can call: the built-in functions (for example `SUM`, `IFERROR`), the public functions of the workbook's modules, and the allowed standard library modules. It groups them, has a search box, and shows each one's signature and a one-line description. For module functions the signature is read from the source and the description is the first line of the function's docstring. *Insert* writes the name with its brackets into the formula bar at the cursor.
- **Name completion.** While typing in the formula bar, a cell editor, or the code editor, a popup offers completions for the names a formula can use: tab names, module names and their functions, data source names, built-in functions, and the allowed Python builtins. After a tab name and a dot (`Orders.`) it offers the **fields of that node, taken from the schema**, and it keeps doing so through the path (`Orders.items[0].`). Tab or Enter accepts, and Esc dismisses. Completion for arbitrary Python objects is not attempted.

**Stored values.** A formula's result is written into the data tree at its node and saved with the sheet, so the data file is complete and valid JSON / XML on its own. Other tools can read it without running any Python. The formula text and its status live only in the overlay.
- On save, the tree holds the latest computed values and the overlay holds the formulas. Readers that ignore the overlay see plain data.
- On open, a **trusted** workbook is fully recalculated, so volatile functions (`NOW`, `RAND`) take fresh values. An **untrusted** workbook shows the stored values and runs nothing (see Trust model).
- Computed array and object results are materialised as ordinary children in the tree. They are marked computed by the formula at the subtree root, and the UI treats them as read-only. If a file is edited externally, the next recalculation overwrites computed values.
- **A failed formula puts an error value in the node.** If the formula raises, or returns something that doesn't match the node's schema type, the node's value becomes an error value (`#TYPE!`, `#DIV/0!`, ...), as in Excel. The previous value is discarded, so there is never a stale value to mislead. The error's kind, message, and traceback are kept in the overlay, and dependents see the error (see Error values).
- **Errors in saved files.** JSON and XML cannot hold error values, so the data file is written with an errored node **absent**, and the overlay records the error. On open of a trusted workbook the formula is recalculated anyway; on an untrusted one the overlay restores the error display without running anything. An errored required node therefore makes the plain data file schema-invalid, which is accepted, since the file is in an error state.
- **Absent nodes.** A formula may be attached to an optional node that is currently absent; a successful result creates the node. A result of `None` means "no value": the optional node is left absent, and for a required node it is a `#TYPE!` error. There is no null in v1 schemas.
- A formula can only be entered on a node the schema defines (see Cells exist only where the schema says), and not on a node whose ancestor already carries a formula.

**Cells exist only where the schema says.** A node can hold a value or a formula only if the schema defines it: a leaf, or an array or object node at any level. The schema, not the data, decides where cells are.
- Every schema-defined node has a cell, whether or not it currently has data. An absent optional node shows an empty cell that can be filled with a literal or a formula; array items and map entries get cells as they are added.
- Content in a loaded data file that the schema does not define (an unknown key, element, or attribute) gets **no cell**. It is preserved so the file round-trips, shown greyed and read-only in an "unrecognised" group on its parent, can be deleted, and is listed in the issues panel. It cannot carry a formula or be referenced by one.

**Invalid data.** The application never refuses or discards data because it doesn't validate.
- A literal in a schema-defined node that violates its type or constraints (from a loaded file, or because the schema was edited) is kept, drawn with a red outline, and listed in the issues panel. Reading it from a formula returns it as-is. The UI editors prevent entering such a literal in the first place.
- A missing required node shows as an empty flagged cell.
- A **formula** is stricter: its result must match the schema, or the node holds an error value instead (see Stored values). A formula never writes an invalid value.

**References are literal.** A path written in a formula means exactly that path, always. `Orders.items[2]` is the third item of `Orders.items` under any structural edit (insert, delete, sort); nothing rewrites formula text, and there is no Excel-style reference adjustment. Likewise a formula belongs to its location, not to the item currently there. Authors who want references that follow the data's structure compute them:
- by data, e.g. `Orders.items[Data.relevantOrder]`;
- by query, e.g. `JSONPATH("$.items[?(@.id == 7)]", Orders)` or `XMLPATH(...)`;
- by expression, e.g. a comprehension with a condition.

**Renames do not rewrite formulas.** The same principle applies to names. Renaming a tab or a schema field (or removing it) leaves every formula, form button, and report expression that mentions it untouched. Those expressions then fail at their next evaluation: a missing tab or module gives `#NAME!`, and a missing field gives `#REF!`. The error message names the missing identifier so the author can find and fix it. The application may offer a find-and-replace across formulas as a convenience, but never does so implicitly.

An index that falls outside the array after an edit yields `#REF!` like any other out-of-range access. `NodeId`s exist for UI identity (selection, expansion state, undo) and are not used by formulas.

**Name resolution**
- Each sheet name is injected as a global proxy object, e.g. `Orders.items[2].price`.
- Proxies resolve lazily via `__getattr__` / `__getitem__`; every access records a dependency edge, so no static parsing is needed.
- Relative addressing: `this`, `parent`, `root`.
- `JSONPATH("$.items[*].price", sheet)` and `XMLPATH(...)` cover queries that don't fit member syntax. They return live proxies or lists of them; each match is a dependency.

**Dependency graph and recalculation**
- Edges run `formula node -> nodes read`. Reading an array or object depends on its structure and children.
- An edit marks dependents dirty; they are topologically sorted and evaluated.
- Cycles produce `#CIRCULAR!` on every node in the cycle.
- Dynamic dependencies (`JSONPATH` results, computed indices) are re-captured on every evaluation.

**Result checking**
1. The Python result converts to `Value`: `list` -> array, `dict` -> object, `int` / `float` / `str` / `bool` / `None` map directly; proxies are unwrapped.
2. The `Value` is validated against the node's `TypeSpec`: kind, required fields, exact field names, constraints.
3. Success: cached and displayed. Failure: the node shows an error value.

**Scalar types.** Conversion is strict: a result must already be the right kind, and nothing is coerced. If the author wants a different kind, they convert explicitly (`round`, `int`, `str`, `.isoformat()`, ...).

| Node type | Accepts | Rejects (`#TYPE!`) |
|---|---|---|
| `integer` | `int` | `float` (even `3.0`), `bool`, `str` |
| `number` / `decimal` / `double` | `int`, `float` | `bool`, `str` |
| `boolean` | `bool` | `int`, `float`, `str` |
| `string` | `str` | everything else |
| XSD `date` | `datetime.date` | `datetime.datetime`, `str` |
| XSD `dateTime` | `datetime.datetime` | `datetime.date`, `str` |

- `bool` is rejected where numbers are expected, though it is an `int` subclass in Python.
- An `int` is valid for a `number` node. A `float`, even a whole one, is not valid for an `integer` node; the author uses `round`, `floor`, `ceil`, or `int`.
- Integers outside the signed 64-bit range, and `NaN` or infinity, give `#VALUE!`.
- **Dates differ between the two languages, by design.**
  - **XML nodes** typed `date` / `dateTime` hold dates as `Value::Date` / `Value::DateTime`. They read in Python as `datetime.date` / `datetime.datetime` and accept those directly. A timezone-aware `datetime` keeps its offset and a naive one stays naive.
  - **JSON nodes** are always plain strings, even with `format: date` or `date-time`. They read as `str` and accept only `str`, so the author converts, e.g. `my_datetime.isoformat()`. The `format` keyword is still checked as a constraint (the string must be valid ISO 8601), but never changes the node's kind.

**Error values** are first-class: `#TYPE!` (path plus "expected X, got Y"), `#REF!`, `#NAME!`, `#VALUE!`, `#DIV/0!`, `#CIRCULAR!`, `#SYNTAX!` (the formula does not parse), `#PYERR!` (with traceback), `#TIMEOUT!`, `#SOURCE!` (a data source failed), `#UNTRUSTED!`. Errors propagate to dependents unless handled by `IFERROR`. Each carries a message shown in a tooltip.

**Errors inside Python.** A node holding an error value is read from Python as an `ErrorValue` object, not as an exception. Python's own exceptions stay the mechanism for failure, and the `ErrorValue` carries the one that caused it.
- `ErrorValue` has `.exception` (the original exception instance, with its traceback), `.kind` (e.g. `"#DIV/0!"`), `.message`, and `.path` (the node where the error originated). It is the same object whether the node errored directly or by propagation.
- **Navigation passes the error along; use raises it.**
  - Attribute access, indexing, and calling on an `ErrorValue`, or navigating below an errored node's proxy, return the same `ErrorValue`. A chain such as `Orders.items[0].price` therefore ends in an `ErrorValue` rather than failing midway.
  - Any real *use* of the value raises a `PropagatedError`: arithmetic, comparison, `bool()`, iteration, `len()`, `str()` / formatting, hashing, and conversion to `int` / `float`. `PropagatedError` has the original exception as `__cause__`, and maps to the original's kind (so a `ZeroDivisionError` upstream still shows `#DIV/0!` downstream). Its message names the origin path.
  - Because `sum()` and comprehensions use values, `SUM(Orders.items.price)` fails if any item's price is an error. **Default aggregations** (`SUM`, `AVERAGE`, `MIN`, `MAX`, `COUNT`, ...) always propagate errors this way. None of them silently skips bad items.
- **Custom error-skipping aggregations.** Skipping is something the author opts into by writing a function in a workbook module. Two helpers make that short:
  - `ISERROR(x)` tells whether an element is an `ErrorValue`.
  - `VALID(iterable)` yields the elements that are not errors, in order.

  ```python
  def SUM_VALID(values):
      return sum(VALID(values))

  def AVERAGE_VALID(values):
      good = list(VALID(values))
      return sum(good) / len(good)   # ZeroDivisionError -> #DIV/0! if none are valid
  ```

  A function that needs more (for example counting the skipped items) can use `ISERROR` directly, or `try/except PropagatedError`. Custom functions are ordinary public callables in a module, so they are available in formulas like any built-in.
- **A formula that returns an `ErrorValue`** (for example `=Orders.total` where the source is in error) puts that same error in its own node. Errors reach dependents without any code having to handle them.
- **`IFERROR(value, fallback)`**
  - `value` may be a plain reference: `IFERROR(Orders.total, 0)` returns `0` if `Orders.total` is an `ErrorValue`.
  - `value` may be a callable, which is evaluated inside a `try`: `IFERROR(lambda: Orders.total / Orders.count, 0)`. Any exception, including `PropagatedError` and Python errors like `ZeroDivisionError`, gives the fallback. Python evaluates arguments eagerly, so a lambda is the way to guard an expression rather than a single reference.
  - `ISERROR(value)` follows the same two forms and returns a `bool`.
- **Catching in Python.** `try: ... except PropagatedError as e:` works, and `e.__cause__` is the original exception. `except Exception` also catches it. This is the escape hatch inside custom functions, which can inspect `.kind` and `.exception`.
- Reading an errored node still records the dependency, so a node recalculates when its upstream error is fixed.
- The same rules apply to form button procedures and report expressions. An error reaching a report block shows in that block.

**Array and object formulas**
- An array node's formula must return a list; the result replaces its children as computed (read-only) children.
- An object node's formula returns a dict whose keys match the schema exactly.
- A formula on a node makes its whole subtree computed; the UI greys it out and rejects edits.
- Array items may carry their own formulas only when the array itself is not computed.
- **A formula over what is inside** *(required by the owner on 2026-10-28)*. A formula entered on a node that holds anything below it, whether typed or imported values or formulas, would erase it, so the window asks first, in a dialog *Erase what is inside?* that says how many values and which formulas the node holds: **Yes** enters the formula and erases them (the formulas inside are removed, and a column formula one of them belongs to ends), as one entry of the undo history, so undo brings all of it back; **No** keeps them and drops the formula. A column formula asks the same about the values and formulas in that field of the items, apart from its own. A formula on an empty node, on a node that already has a formula, or on a leaf does not ask.

**Column formulas** *(required by the owner on 2026-10-25; built, see "Decisions made while building column formulas")*. For an array of objects, one formula can be given to a field of **every item**, as a column of a table has one formula in Excel.
- **Entering one** is done in the **tabular view of the data tree** (see Tabular view of arrays). Clicking a **column header selects the whole column**, and the **formula bar** then shows the column's formula, if it has one, and accepts a new one or an edit of it, to be applied to that field of every item. The formula is written as for an ordinary item, so `this`, `parent` and `root` work as they do there (`parent.qty * parent.price`). The sample's `total` is such a formula.
- **It owns the field.** Creating it **clears whatever the field held** in every item, and the field of every item shows as computed. The clearing, the formulas and the dependents are one entry of the undo history.
- **New items get it.** An item added to the array, by any command, has the formula on that field from the start.
- **Overriding one item** ends the column formula. Entering a literal value or a different formula in that field of one item (1) sets that item's field to what was entered; (2) turns the column formula into an ordinary formula on **each of the other existing items** (the same text, as item formulas, with their current values); (3) removes the column formula; (4) so **items added afterwards have that field blank**. This is one entry of the undo history, so undo restores the column formula.
- **Removing it** (clearing the formula) removes the formula from every item and leaves the values the formulas had produced; this is the usual *clear formula* of a cell, applied to the column.
- **Stored** in the tab's overlay as one entry per column formula (the array path, the field and the text) and not as one formula per item, so a file with 10,000 rows does not hold 10,000 copies of one expression; opening the file gives each existing item its formula. It is part of the executable content for the trust digest, as one item (`column formula Orders!items[].total`).
- **Open points** to settle before building: whether it also covers fields of an object nested in the items (`items[].price.net`) and arrays inside arrays (`orders[].lines[].total`), and how the forms show it (a form's table can show the column as computed; setting it is only in the data tree).


## Semantics: Python first, Excel second

A formula is a Python expression and the library behaves as Python programmers expect. Excel names are a convenience, not a compatibility contract.

| Area | Rule |
|---|---|
| Naming | Excel-style uppercase names (`SUM`, `IF`, `VLOOKUP`, ...) are thin aliases with Python-flavoured behaviour. Plain Python (`sum()`, `len()`, comprehensions, `x if c else y`) is equally first-class. |
| Truthiness / equality | Python's. `0`, `""`, `[]`, `None` are falsy; `==` is Python `==`; no case-insensitive string compare by default. |
| Empty / missing | `None` is the empty value. `SUM([])` is `0`; `AVERAGE([])` raises `ZeroDivisionError` (shown as `#DIV/0!`); no implicit `0` / `""` coercion. |
| Types | No implicit string-to-number coercion: `"1" + 1` is `#TYPE!`. `int` and `float` stay distinct; `/` is true division. |
| Indexing | 0-based, negative indices and slices allowed. Out of range raises, shown as `#REF!`. |
| Ranges / arrays | Python lists and iterables. No implicit array broadcasting (use comprehensions or `MAP`). |
| Strings | Python `str` with f-strings, `.format`, `%`. `TEXT` uses Python format specs, not Excel format codes. |
| Dates | Python `date` / `datetime` objects, not serial numbers. XML `date` / `dateTime` nodes read and accept them directly; JSON nodes are strings, so the author converts explicitly (e.g. `.isoformat()`). See Scalar types. |
| Lookups | `VLOOKUP`-style functions take lists of objects and field names. Missing keys raise. `#N/A` only from explicit `NA()`. |
| Errors | `ZeroDivisionError` -> `#DIV/0!`; `KeyError` / `IndexError` / `AttributeError` on a reference -> `#REF!`; `TypeError` -> `#TYPE!`; `ValueError` -> `#VALUE!`; `NameError` -> `#NAME!`; `SyntaxError` -> `#SYNTAX!`; anything else -> `#PYERR!`. Traceback goes in the tooltip. |
| Function list | Not a parity target. v1 ships a small Excel-named set that is useful over trees: `SUM`, `AVERAGE`, `MIN`, `MAX`, `COUNT`, `IF`, `IFERROR`, `VLOOKUP`, `FILTER`, `SORT`, `UNIQUE`, `CONCAT`, `ISERROR`, `VALID`, `TEXTJOIN`, `JSONPATH`, `XMLPATH`. Everything else comes from the Python standard library modules that work in the engine (`math`, `datetime`, `re`, `json`, `itertools`, ...; see Python engine). |

**Array concatenation**: `CONCAT(*arrays)` returns one list holding the items of each argument in order, e.g. `CONCAT(Orders.items, Archive.items)`. Arguments may be lists or array proxies; a non-array argument is a `#TYPE!` error. In the Python-first spirit, `CONCAT` means list concatenation, not text joining (use `TEXTJOIN` or `str.join` for text). Plain Python also works: array proxies support `+` and unpacking (`[*a, *b]`). On an array node, the result must still match the node's item type, so a mix of incompatible item types fails result checking.

Most built-ins are one-line Python over the stdlib. Only the tree-aware pieces (`JSONPATH`, `XMLPATH`, proxies) need real Rust.

**Extensibility**: custom functions live in Python modules stored in the workbook (see Python modules). Every module is available to formulas without an `import`, and its public functions can be called by bare name.

## Names and reserved words

Formulas, form button procedures, and report expressions share one flat namespace per workbook. It holds tab names (Data Tabs and Report Tabs), data source names, module-level functions, built-in functions, Python builtins, the special names `this`, `parent`, `root`, `ErrorValue`, and `PropagatedError`, workbook module names, and the exposed stdlib modules (`math`, `datetime`, ...). Every name in it must be unique and mean the same thing everywhere. **Shadowing is not permitted**, with one exception (below).

**Reserved names.** These cannot be used as tab names, report names, data source names, or module-level function names:
- Python keywords (`keyword.iskeyword`). `class` passes `isidentifier()` but is not usable.
- All Python builtins (`list`, `sum`, `len`, `str`, ...).
- The special names above and the exposed stdlib module names.
- Every built-in function name (`SUM`, `IF`, `CONCAT`, `ISERROR`, `VALID`, ...).
- Any name starting with an underscore or with `cliotree`, which are held for internal use.

**Module functions.** Public callables in workbook modules are imported into the globals (see Extensibility). A function whose name clashes with a tab, a built-in, a reserved name, or a function in another module is an error at module load. The message names both parties. Nothing silently overrides anything.

**Case.** Names are case-sensitive in Python, but **tab names must also be unique ignoring case**: `orders` and `Orders` cannot coexist. They are confusing, and tab data is stored as per-tab files in the workbook, which Windows would treat as the same file. Functions and other names stay case-sensitive.

**Where it is checked**
- On creating or renaming a tab: live in the name field, naming the clash.
- On saving or loading a module.
- On opening a file. A file that breaks the rules still opens. The offending tab or function is flagged, anything depending on the clashing name fails with `#NAME!`, and the issues panel explains.

**Future built-ins.** The file records the reserved-names version it was created against. If a later release adds a built-in whose name an existing tab already uses, the tab keeps its name and **shadows** the newer built-in in that workbook, and a warning tells the author. This is the only permitted shadowing; it stops an upgrade from breaking old workbooks. New workbooks use the current list, with no exception.

## Python modules

Custom Python lives in **modules** stored in the workbook. The design follows Excel and its Visual Basic modules: a separate code editor with a project tree, one module per code window, and public functions that cells can call by name.

**The code editor** (opened from the menu or with Alt+F11, as in Excel) is the code area that also holds the raw text of form designs.
- **Project explorer** on the left: a tree with a *Modules* branch listing the workbook's modules, and a *Forms* branch listing the customised form designs by tab (see Forms), opened as raw text. Double-click opens an item in the editor.
- **Editor panes** on the right, one tab per open module: a monospace editor with line numbers, syntax highlighting, and automatic indentation.
- **Procedure box** above the editor, like the VBE's: a drop-down listing the module's top-level functions, which jumps to the one chosen.
- **Insert > Module** creates a module, and rename and delete are in the explorer's context menu. **Export** and **Import** write and read a module as a plain `.py` file, the way Excel exports a `.bas`.
- **Compile** checks the open module and lists problems (syntax errors, import cycles) with line and column, each clickable.
- **Immediate window** at the bottom, like the VBE's: type a Python expression, press Enter, and see its result or error. It runs against the live workbook on the evaluation thread, under the same budgets, and needs the workbook to be trusted. Its history and output size are limited by options on the Code editor page (see The Options dialog).
- There is no debugger (breakpoints, stepping) in v1.

**Modules are loaded for every formula.** The formula context behaves as though it had imported all of the workbook's modules.
- A module is available **by name**, like an imported module: `Tax.vat(Orders.total)`.
- Its **public functions** (names not starting with an underscore) are also callable by **bare name**, like Excel's public functions: `vat(Orders.total)`. This is the same flat namespace described in Names and reserved words, so a clash is an error, not a silent override.
- The same applies in form button procedures, report expressions, and the Immediate window.

**Modules importing each other.** A module may `import` other workbook modules (and the allowed standard library modules). **Circular imports are not allowed.**
- Import statements are read from the module source when it is saved or loaded. If the modules form a cycle, the whole cycle fails with an error that names the cycle (`A -> B -> A`). None of the modules in it are loaded, and calling their functions gives `#NAME!`.
- Modules are loaded in dependency order.
- An import of something that exists neither as a workbook module nor as an available standard library module is a load error for that module.

**Loading and errors**
- Top-level statements in a module run once, when the module is loaded, under a load budget. Modules are for definitions (functions, constants), not for effects.
- A module with a syntax error, an import error, or an exception at load is marked failed (red in the explorer) and is listed in the error panel. Its functions are unavailable, and formulas that use them show `#NAME!` (with a message pointing at the failed module). Other modules are unaffected.
- A module's functions see the workbook the same way formulas do: they can read sheets such as `Orders.items` by name, and the reads are recorded as dependencies of whichever formula is running. This is looked up when the function is called, not when the module is loaded.

**Dependencies and recalculation.** When a formula uses a name that a module provides, it records a dependency on that module. Editing a module reloads it and recalculates exactly the formulas that depend on it, which show the pending marker until the results arrive.

**Reloading while evaluation is running.** A reload is queued as a task for the evaluation thread, and runs **between evaluations, never during one**, because the interpreter runs one thing at a time. The evaluation in progress finishes first (or is cancelled by the normal budget). Each module has a **generation number** that goes up with every reload, and it is part of the input version of every result (see Evaluation and scheduling). A result computed under an older generation of a module it used is discarded and its formula is queued again. If a reload fails (syntax error, import error, cycle), the module is marked failed and its names are removed from the namespace, so formulas that use it show `#NAME!` until the module is fixed.

**How the namespaces work.** This mechanism was prototyped in RustPython in a second spike, and the points below were observed to work.
- **One live workbook namespace** (a Python `dict`) holds everything formulas can name: tab proxies, data sources, module objects, and the public functions of modules. It is the globals dictionary of every formula evaluation.
- **Each module has its own globals** (a real module object), so its top-level names are private to it. A name that a module does not define is not found in the module's own globals and falls through to the **builtins**, and the module's builtins dictionary *is* the live workbook namespace. So a module function that mentions `Orders` finds the tab proxy **when it is called**, even if the tab was added after the module loaded, and the read is recorded as a dependency of the running formula. Looking up a workbook name this way was as fast as looking up the module's own globals (58 ms against 57 ms for 500,000 reads).
- **Publishing.** After a module loads, the module object is put in the workbook namespace under its name (`Tax`), and each public function defined in it (`vat`) is put there under its own name. Private names (leading underscore) are not published.
- **Imports inside modules** go through a replacement `__import__`, supplied by the host in Rust, which serves the workbook's modules and the allowed standard library modules, and refuses anything else with `ImportError` (so `import os` and `import socket` fail even where a module tries them). Both `import Tax` and `from Tax import vat` work.
- **Builtins are restricted explicitly.** The namespace must be given as the formula's builtins too. When it was not, Python silently supplied the real builtins and `open` and `eval` stayed reachable. With it set, `open`, `eval`, `exec`, and `compile` are plain `NameError`.
- **Reloading.** A reloaded module is re-run **in place** inside the same module object. Importers that hold the module (`import Tax`) see the new code at once. Importers that copied a function (`from Tax import vat`) keep the **old code** if the function body changed. So a reload always **reloads the modules that import it too, in dependency order**, before the formulas that depend on them are recalculated.
- **Per-evaluation names.** `this`, `parent`, and `root` change for each formula. They are set in the workbook namespace immediately before each evaluation, which is safe because evaluation is sequential. They must not be passed as evaluation locals: a comprehension sees locals but a `lambda` does not (`NameError`).
- **Assignment expressions.** A walrus (`(x := 5)`) in a formula would otherwise create a name in the shared namespace. Each evaluation therefore gets a fresh, empty locals dictionary, which absorbs such assignments. Users are **not notified**: the assignment is harmless, and the name simply does not outlive the evaluation.
- **The loader is native.** In the spike the loader was written in Python, so `__globals__` on a module function reached the loader's own state. In the application the loader and the replacement `__import__` are Rust functions with no Python globals to reach, and the double-underscore check (see Python engine) blocks `__globals__` access in the first place.
- **Cost.** In the Python prototype a proxy attribute read took about 1.9 microseconds. This is only a baseline: proxy reads in the application go through Rust and are measured in build step 3.

**Names and storage.** A module name is a valid identifier, unique ignoring case, not a reserved word, and distinct from every tab and data source name. Modules are stored as `modules/<name>.py` in the `.clio` file. Their order in the explorer is recorded in the manifest.

**Editing, undo, and trust.** Module edits are logged for undo and redo (rapid typing is merged), and the double-underscore check applies to module source. Module sources are executable content, so in an untrusted workbook they are shown and can be edited but are not loaded, and the Immediate window is disabled.

## Reports

> **Deferred to a later version.** Reports are not part of v1. This section records the intended design so that v1 does not rule it out. Other sections that mention reports (names, trust, evaluation, undo, file format) describe how they will fit in, and apply once reports exist.

A **report** is a tab that takes data from other tabs and presents it visually: tables, text, and charts such as bar, line, pie, and scatter. A report holds no data of its own and is never the target of a formula or form.

**Report design** specifies:
- **Sources**: one or more Data Tabs the report reads. Each source is exposed to the report's expressions under its sheet name, through the same proxies formulas use.
- **Layout**: a vertical flow of blocks (optionally in rows or columns). Block kinds:
  - `text`: static text or an f-string-style template filled from expressions.
  - `table`: rows from an array (or any list) with chosen columns, each column an expression over the row.
  - `chart`: a chart type, plus series. Each series gives expressions for its x and y values (or label and value for pie). Titles, axis labels, and colours are settable.
  - `group`: a titled container, optionally repeated once per item of a list (e.g. one section per customer).
- **Expressions** are Python, evaluated like formulas. Block data comes from expressions such as `[o.total for o in Orders.items]` or `AVERAGE(...)`.

The design is stored as a JSON document validated against a built-in schema (`builtin:report`), like forms. A report tab's content is that design document, and a report designer is a visual editor over it.

**Behaviour**
- A report is live. Its expressions record dependencies like formulas, so editing a source node re-renders only the affected blocks.
- An error in an expression is shown in place, in the block that failed, as an error value (`#REF!`, `#TYPE!`, ...). Other blocks still render.
- A chart series must resolve to numeric (or date) values for numeric axes and to strings for labels. A mismatch shows `#TYPE!` in the chart area.
- Reports are read-only for the data they show. They cannot write to any sheet.
- A report's name is a Python identifier like any tab, but no other formula can reference it.
- Export (image, PDF, HTML) is a later feature and is not in v1.

## Forms

A Data Tab can be shown in more than one way. Each way is a **view** of the tab. A view holds no data of its own: every view reads and edits the same tab, through the same entry path, so an edit made in one view is an ordinary tab edit that appears in the others.

**Views of a Data Tab**
- **Data tree** is the grid described under Core model and Formulas. Every Data Tab has it, and it cannot be renamed, deleted, or customised.
- **Forms** are named data-entry screens over the tab. Every Data Tab has a form called **Default**, which cannot be renamed or deleted and starts out as the **generated form** (below). The user can create more named forms (*New form...*, or *Duplicate* of an existing one). Form names follow the rules for tab names, and are unique within the tab ignoring case.
- A **view selector** beside the tab (Data tree, Default, and the other forms by name) chooses the view that the tab shows. The choice is remembered per tab in the workbook.
- **Views belong to the tab.** A form has no binding by name: it is a view of the tab it was made on, and has the tab's schema, so there is no separate output schema and no unbound-form error. Renaming the tab keeps its views, and deleting the tab deletes them.
- **What the views share.** The selection, the undo history, the pending markers, and the status bar. Switching view first enters any edit in progress (as selecting another cell does; a refused entry keeps the user where they were). Selecting a node and switching view moves to the control bound to that node, or the nearest control above it, and the other way round.
- A **Report Tab** is a different kind of tab, not a view (see Reports). Reports read Data Tabs; they do not add views to them.

**The generated form.** A form that has not been customised is not stored. It is drawn from the tab's schema each time, so it follows every change to the schema, including a field added, renamed, or deleted from a data tab (see Editing the schema from a data tab).
- An object becomes a group titled by its field name (or the schema's `title`), fields in declared order. A scalar becomes a labelled field whose editor comes from its `TypeSpec`: a toggle for booleans, a dropdown for enums, a numeric field, a date picker for dates, a text field otherwise (multi-line when the schema allows long strings). A schema `description` becomes the field's help text, and a required field is marked.
- An array becomes a **repeater**. Items of scalars, or of flat objects, are drawn as the table of the tabular view of arrays (sorting, filters, hiding, and row commands included). Other items are stacked, with a stepper (previous, next, *New*, *Delete*, "3 of 17") so that records can be entered one at a time. A map becomes a list of key and value pairs.
- An optional node that is absent shows an empty control, and a value entered creates the node. Computed nodes are read-only with the computed styling.
- The generated form has no buttons: buttons are part of customising.

**Customising a form, in place.** Any form has an *Edit form* switch that puts the view into layout mode, where the form is edited on the form itself. The first change to a generated form **materialises** it: the generated layout is saved in the workbook as a design and then edited. From then on that form no longer follows schema changes by itself.
- **Layout.** A design is a tree of controls: *field*, *group*, *repeater*, *label*, *button*, *separator*. Groups arrange their children vertically or in a number of columns, and wrap with the window; there are no pixel positions. The order in the document is the tab order. In layout mode a control is selected by clicking it, moved by dragging, added from a palette, and deleted from its menu.
- **Property page.** Selecting a control shows its properties: its label and help text; for a field, the path it binds to (chosen from the tab's schema), the editor to use, read-only, **masked** (a password box: the text field of a string shows dots instead of what is typed; it only changes what is shown, the value is stored as typed, and clearing it after use is up to the procedure that uses it), and the format of a number or a date; for a repeater, table or stacked, and the order of the columns of its table and which of them are shown; for a button, its label and the procedure it runs. Any control can have a *visible when* and an *enabled when* expression (bare Python expressions, without `=`).
- **Fonts.** Any control but a separator has a **font**: a typeface (sans, serif, monospace, condensed, script or handwriting; see Look and feel) and a size in points, each *Inherited* unless chosen. A control inherits each of the two from the group it is in, and a control in no group from the interface font. The design stores them as `font` and `font_size` (6 to 72) and leaves out what is inherited. Text that is code (a formula) takes the typeface too, except under Sans, where it stays in the monospace font and takes only the size.
- **Table columns.** Each column of a repeater's table, the row numbers (`#`) among them, has its **own properties**: its title, help text on its title, a width in points (24 to 800, or automatic), the alignment of its title (left, centre or right; left unless set) and of its cells (or automatic: numbers on the right), the editor (automatic or one line of text) and read-only, a number or date format, and a font for its cells, which they otherwise inherit from the table. **The table sets the font of its own title and the font of the titles of its columns**, each a typeface and a size inherited from the table's font unless set, so every column title is in the one font. The row numbers have the title, help, width, the two alignments and the font of their cells, and a **numbering**: `[0]`, `[1]` (the index, as a path writes it; the default), 1 2 3, a b c, A B C, i ii iii, or I II III, from a **start** that is any integer (0 for the index, 1 for the others, unless set). A number a numbering cannot write (a letter or a Roman numeral below 1, a Roman numeral over 3999) is written in digits; letters go on past z as aa, ab. **Where each column is, and whether it is shown, are properties of the table**: the table's property page lists its columns in their order, each with a check box to show it, buttons that move it up and down, and a button that opens its properties. The last column of the items that is shown cannot be hidden; the row numbers can. In layout mode a click on a column's title selects the column (outlined over its whole width, from its title to the end of the table) and shows its properties; its menu moves it left or right, past columns that are hidden, or hides it. The design stores the columns as `table_columns`, a list in screen order of `{name, hidden, ...}` with the row numbers as `#`; a field of the items that the list does not name comes after the others, shown, so a field added to the schema appears, and a list that is the default is not stored.
- **Number and date formats.** A field or a table column of a number has a **thousands separator** (commas) and a number of **decimal places** (0 to 10, or automatic: as many as the value has); one of a date or a date-time (an XSD date, or a JSON Schema string of `format: date` or `date-time`) has a **date format**, a pattern of `d`, `dd`, `ddd`, `dddd` (7, 07, Sat, Saturday), `m`, `mm`, `mmm`, `mmmm` (3, 03, Mar, March) and `yy`, `yyyy`, with any other character copied; the property page offers some patterns, and any can be typed. A date-time shows its time after the date as it is stored. A format only changes what is shown: while a field has the focus it shows the value as it is stored, and that is what is typed (the grid and formulas are not affected). The design stores `thousands`, `decimals` and `date_format`, on a control or a column.
- **Formulas appear only here.** The form view has no formula bar. A computed field shows a small *fx* marker. The property page of a field shows the formula of the node it is bound to, which can be edited there; it is the same entry as in the formula bar of the Data tree view, an undoable edit of the tab.
- **Paths are literal**, like formula references. A control whose path no longer exists in the schema (after a rename or delete) is drawn as a placeholder naming the missing path, and the rest of the form works. Layout mode lists **fields not on the form**, each with an *Add* button, and **broken controls**, each with *Re-bind* and *Remove*. *Reset to default* (on Default) and *Delete* (on the others) discard a design; Default then goes back to being generated.
- **Edits to a design** are not in the workbook's undo history in version 1, like module edits and tab operations (see Undo and redo). Layout mode has its own Undo and Redo, which last for the session in layout mode.
- **Stored** as a JSON document validated against a built-in schema (`builtin:form`), so it is diff-friendly and versioned with the workbook (see File format). The code area offers the same document as raw text in an editor pane, for direct editing and for review. A design is valid only if its field paths exist in the tab's schema; one that is not is still opened, with the broken controls as above.

**Expressions on controls** (*visible when*, *enabled when*) are executable content. They are evaluated by the same machinery as formulas: dependencies are recorded, they run on the evaluation thread, never on the UI thread, and the result is kept in memory, not written to the data. While one is out of date the control keeps its last state, with the pending marker. An expression that is an error leaves the control visible and disabled, and says why in a tooltip. In an untrusted workbook they do not run (see Trust model): a control stays visible, and a control with an *enabled when* is disabled.

**Data flow: a form reads and writes the tab directly**
- **Retrieve.** When a form is shown, and whenever the tab's data changes, it shows the tab's current values. It always reflects the last calculated values (see Evaluation and scheduling).
- **Replace on change.** When the user commits a change in a field (on Enter, or when the field loses focus), the new value **replaces** the corresponding node's data in the tab. The edit is an ordinary tab edit: it is undoable and triggers normal recalculation. A form does not hold a draft or a submit step.
- **Validation.** A field validates against its `TypeSpec` as the user types. An invalid value stays in the field with its error and is **not** written; the tab keeps the previous value.
- **Computed nodes are read-only.** A field bound to a node carrying a formula, or inside a computed subtree, is shown read-only with the computed styling. Edits cannot overwrite a formula result.
- Arrays are edited through repeaters: adding, removing, and editing items change the array in the tab directly.

**Button procedures**

A button runs a Python function `def my_procedure(form, ctx): ...` defined in a workbook module.
- `form` is a view of the tab's data. Reading it gives the current values. Changes made to it are collected during the call.
- `ctx` offers read access to the whole workbook through the same sheet proxies that formulas use, and it reports which form and which button were used (`ctx.form`, `ctx.button`), so one function can serve several buttons.
- Procedures **obtain and send data to and from wherever needed**: they can read other tabs and `form`, and they can write to the form's tab through `form` or to other tabs through `ctx`. They can also use named data sources the user has granted (see Data sources). Writes to tabs are collected during the call and applied **atomically** when it returns.
- Every written value is validated against the schema of the tab it targets. If any write is invalid, or the procedure raises an exception, **none** of the writes are applied, the message is shown to the user, and the data is unchanged. Writing into a computed (formula-driven) node is refused in the same way.
- The applied writes form one undoable edit and trigger normal recalculation.
- Return values are ignored.
- **A click first enters the field being edited**, so the procedure sees what is on the screen; a refused entry stops the click and shows why. The procedure then waits its turn on the evaluation thread and reads the tab as it is when it starts, after any evaluation ahead of it has been applied.
- **A conflicting edit refuses the writes.** If the user edits a node after the procedure started, and the procedure wrote that node, none of the writes are applied and the message names the node. This is the rule for an evaluation that an edit overtook. Fields stay editable while a procedure runs.
- Buttons run one at a time on the evaluation thread. While one runs, all buttons of the workbook are disabled and the status bar shows it.
- Procedures run under the same trust rules as formulas, with their own time limit, the **button procedure time limit** (see Settings and limits), because a procedure that loops over a large array or waits on a data source can reasonably run longer than a formula. In an untrusted workbook buttons are disabled; fields still edit the tab directly, since that runs no Python.

## Data sources

**Direction agreed for step 6b (2026-10-28).** These notes come first: where the text below says otherwise, they win, and the section is rewritten to match when 6b is built.
- **The kinds available depend on the target.** The desktop application has SQLite, PostgreSQL, MariaDB and HTTP/HTTPS; the web port has HTTP/HTTPS only (no raw database connections in a browser). A workbook that names a source of a kind its target lacks opens and works; calls to that source fail with `#SOURCE!` saying the kind is not available here.
- **Definitions belong to the user and the machine, not to the workbook.** They are stored in the per-user configuration directory, where the trust record and the other security permissions are (beside `trust.json`), and a definition may hold its password, token or API key itself.
- **A `.clio` file refers to data sources by name only.** It carries no connection details and no credentials.
- **Another user or machine sets up the same names.** A workbook used elsewhere needs its data sources defined there under the names it uses; until then each missing one fails with `#SOURCE!` saying no data source of that name is defined on this computer, and the rest of the workbook works.
- **The same name may point at a different instance.** A definition on another machine can name another server or database (a test copy, a local replica); the workbook works as long as the definition and the formulas that use it fit it. This is intended, not a fault.

What this replaces below: the specification stored in the workbook file and the secret filed under the workbook id ("Specification", "Saving"); the target confirmation for a workbook that came from a file, which was a defence against a file pointing a specification elsewhere and is not needed when the file holds no specification; and "Opening a workbook on another machine", which becomes the missing-definition case above. Settled with the user on the same day:
- **Secrets are kept in the definitions file itself,** not in the operating system's credential store. The file is in the per-user configuration directory, so it is as safe as that directory is: anything that runs as the user can read it.
- **Grants are not per workbook.** A data source is referred to by name, and its definition on the machine is what is used; there is no per-workbook grant keyed by the workbook id. (How a source is allowed at all, given that an untrusted workbook runs no Python, is settled when 6b is designed in full.)
- **Definitions cannot be exported** or imported. Each machine has its own, set up by hand or by a module (below).
- **Python can define a data source and check one** (asked for by the user on 2026-10-28). Two functions are available to module code:
  - One **creates (or replaces) a definition** on this machine, taking every setting a definition has as arguments, the password, token or API key included: the name, the kind, and the kind's connection settings (host, port, database, user name and password; base URL, headers and authentication; the SQLite path; pooling). This lets a workbook carry its own setup: a button that, on a new machine, defines the sources the workbook uses.
  - The other **says whether a named data source exists on this machine and whether it connects**, by running the same test as the definition form's *Test* button, and gives the reason when it does not.
  - Proposed, to settle when 6b is built: they are `sources.define(...)` and `sources.check(name)`, the latter returning `.exists`, `.ok` and `.message`; both run only where side effects and waiting are allowed (button procedures and the Immediate window), not in formulas, which re-run on their own; replacing an existing definition needs an explicit `replace=True`; both obey the call timeout. Like all Python, they need a trusted workbook.
  - **Where the password comes from is the module author's responsibility.** `sources.define` takes it as an argument and stores it in the definition; how it is kept before it reaches the call (written in the code, which is saved in the workbook, typed into a form field, which is tab data and saved too, or obtained some other way) is the author's choice, and ClioTree does not police it. A procedure can erase a field's value after the call. For typing a password into a form, a field control has a **masked** property (see Forms, Property page).

A **data source** is a named connection to something outside the workbook. v1 supports:
- **Databases**: SQLite (a file), PostgreSQL, and MariaDB.
- **HTTP / HTTPS endpoints**: a base URL.

Data sources are the only way Python code reaches outside the workbook. The sandbox still exposes no `socket`, `subprocess`, `os`, or file I/O modules; everything external goes through a named source and its explicit grant.

**Specification.** Each data source is one *specification*, and a specification is the unit that carries the **credentials**. It has a name, a kind, the connection details (SQLite path; database host, port, and name; endpoint base URL; default headers), the credentials to use (a user name and a password, or a token or API key), and optional pooling settings (see Connection pooling). The specifications are edited in a Data sources panel.
- **Several specifications may point at the same database or endpoint**, each with its own credentials. This is how a workbook uses, for example, a read-only account for reports and a different account for writes: two specifications, two names, each separately granted.
- **Secrets (passwords, tokens, API keys) are never stored in the workbook file.** The specification stored in the file holds the non-secret parts, including the user name. The secret itself lives in the operating system's credential store, filed under the workbook id and the specification's name, and belongs to that specification alone. Opening a workbook on another machine does not prompt for them: the specification is marked *credentials needed* until the user enters them in its form (see Creating a specification).

**Creating a specification.** Credentials are not a separate step or dialog: they are **part of the settings entered when a specification is created**, in the same form. The form is opened from the Data sources panel (*New*, or *Edit* on an existing one).
- **Fields** depend on the kind.
  - *PostgreSQL and MariaDB:* name, host, port, database, user name, password, and optional pooling settings (see Connection pooling).
  - *HTTP/HTTPS:* name, base URL, default headers, and the kind of authentication: none, basic (user name and password), bearer token, or API key (a header name or query parameter, and the key). It also has an optional *test path*.
  - *SQLite:* name and file path. It has no credentials.
- **Secret fields are masked.** When editing an existing specification the stored secret is never shown. A field offers *Change*, and leaving it alone keeps the stored value; *Clear* removes it.
- **Test button.** The form has a **Test** button, which checks the settings as entered, before they are saved.
  - Databases: it opens a single throwaway connection (never one from a pool), authenticates, and runs a trivial read-only query. It reports success with the server version and the time taken, or the reason for failure (unreachable, authentication refused, TLS problem, unknown database).
  - HTTP: it sends a `GET` to the test path (or the base URL), with the entered authentication. A 2xx or 3xx response is success; 401 or 403 is reported as an authentication failure; other statuses are shown as information.
  - SQLite: it checks that the file exists and can be opened read-only.
  - The test runs in the background with a spinner, can be cancelled, and obeys the data source call timeout (see Settings and limits). It never blocks the form.
  - The result stays on the form for the session. A passed test is not required to save, and saving after a failed test warns but is allowed.
  - Test checks connectivity and the credentials only. It cannot show whether an account may write, so it says nothing about a read-write grant.
  - It is a Rust-side check that does not run Python, so it works in an untrusted workbook. It does not need a grant and does not create one.
- **The target is always shown in full** (for example `postgres://db.example.com:5432/sales as reporting_ro`), so the user can see where the secret is going. In a workbook that came from a file, secret fields stay disabled until the user has confirmed the target once, so that a file cannot quietly point a specification at another server and have a password typed into it.
- **Saving** stores the non-secret part in the workbook and the secret in the operating system's credential store. It does not grant access. The user then grants the specification, choosing read or read-write, as a separate explicit step (see Explicit grants), which the panel offers straight after a successful save.
- **Secrets are tied to the target.** A stored secret is filed with a hash of the specification's target and user name. If either changes, the stored secret is no longer used and the specification returns to *credentials needed*, so a saved password is never sent to a different server or account without being entered again. The form can offer to keep it after showing the new target.
- **Rename, copy, and delete.** Renaming a specification moves its secret to the new name. Copying one copies the non-secret settings only; the copy needs its own credentials. Deleting one asks for confirmation and removes its secret.
- **Credential store.** Secrets are kept through a `CredentialStore` interface with two implementations. The first uses the operating system's store through the `keyring` crate (Windows Credential Manager, macOS Keychain, and the Secret Service on Linux). The second keeps secrets **in memory for the current session only**.
- **No credential store available** (for example a headless Linux session): the form says so, and the in-memory implementation is used. The secret is not persisted and must be entered again in each session.
- **Testing.** Tests use the in-memory implementation, so they run unchanged on Linux CI. The `keyring` integration is covered by a small test that runs only where an OS store exists (the Windows job, or a developer's machine) and is skipped elsewhere.
- **Credentials needed.** A specification without stored credentials on this computer is shown with a *credentials needed* badge in the panel. Nothing prompts when a workbook opens and nothing prompts during evaluation. Calls to such a source fail with `#SOURCE!` and a message saying that credentials have not been entered on this computer. Declining to enter them simply leaves that source unavailable; the rest of the workbook works.

**Names.** A source name is a Python identifier in the shared formula namespace, so it follows the rules in Names and reserved words and is available in formulas, button procedures, and report expressions as a global object.

**Explicit grants.** Every source must be **explicitly granted by the user, one by one**. There is no blanket "allow network" setting.
- A grant is recorded in user config, keyed by the workbook id, the source name, and a hash of the specification's connection definition (kind, host, port, database or path, base URL, and user name). Changing where a source points, or which account it uses, invalidates its grant, so an edited file cannot redirect an already-granted name to a different server or account. Two specifications to the same server are granted separately, each with its own level.
- A grant has a level, **read** or **read-write**, chosen by the user when granting. The grant dialog states the exact target (for example `postgres://db.example.com:5432/sales`) and the level.
- Granting needs the workbook itself to be trusted first. In an untrusted workbook no Python runs, so no source can be reached.
- Grants are listed and revoked in settings and in the Data sources panel.
- Grants are made only in that panel or settings. No dialog ever appears in the middle of an evaluation, because evaluation runs on a background thread. A call to an ungranted source fails with `#UNTRUSTED!` and a message naming the source.

**Using a source from Python**
- Databases: `Sales.query(sql, params)` returns a list of dicts, one per row. `Sales.execute(sql, params)` runs a statement that changes data and returns the number of rows affected. Parameters are always passed separately from the SQL text; there are no string-building helpers.
- HTTP: `Api.get(path, params=None)` and, for read-write grants, `Api.post`, `Api.put`, `Api.patch`, `Api.delete`. A response has `.status`, `.headers`, `.text`, and `.json()`.
- Values convert to Python types: integers, floats, strings, booleans, `date` / `datetime`, and `None` for SQL `NULL`. Result checking applies as usual when such a value reaches a node.

**Read versus read-write is enforced by the connection, not by parsing SQL**
- SQLite is opened read-only; PostgreSQL and MariaDB sessions use read-only transactions.
- With a read grant, `execute` and non-read HTTP methods are refused. A read-write grant is required for them.

**Where each kind of call may be used**
- **Reads** (`query`, `get`) may be used in formulas, button procedures, and report expressions.
- **Writes** (`execute`, `post`, `put`, `patch`, `delete`) are allowed **only in button procedures**, because formulas and reports re-run automatically and must not have side effects. Writes happen immediately during the call; they are not part of the atomic tab-write rule for procedures (see Forms), so a procedure that fails after a write does not undo it.
- Reads in formulas are slow and not deterministic, so they are treated as **volatile**: their results are cached for a recalculation pass keyed by (source, call, parameters) and refresh only on a recalculation pass or explicit "Recalculate" (see Evaluation and scheduling). Editing a source node does not by itself re-run a query, unless the query's parameters depend on it.

**Limits.** Waiting for I/O does not count against the per-formula CPU budget, but every call has its own timeout (default 30 seconds) and a maximum response size (default 16 MB), both workbook settings (see Settings and limits). A source failure (connection, authentication, SQL error, HTTP error status, timeout, oversize response) produces a new error kind, `#SOURCE!`, with the details in the message.

**Connection pooling.** Pooling is a property of a specification, off unless the specification allows it.
- **Off (the default):** each call opens a connection, uses it, and closes it.
- **On:** the specification states a **maximum connection count** (a whole number of at least 1; it is required when pooling is on). Connections are kept after use and reused, up to that many at once.
- Calls that need a connection when all are in use wait for one to be returned, and fail with `#SOURCE!` if none is returned within the call timeout.
- A pool belongs to one specification only. Two specifications to the same server never share connections, because their credentials differ.
- A connection is reset when it goes back into the pool (open transactions rolled back, session state discarded), and the read-only enforcement is applied again each time it is handed out.
- Pools are closed when the workbook is closed, when the specification is edited or its grant revoked, and when the application exits.
- **SQLite specifications cannot enable pooling**, as the database is a local file. For HTTP, pooling means keeping connections alive for reuse, up to the maximum.
- Evaluation is sequential in v1 (see Evaluation and scheduling), so a pool in practice holds about one connection in use. Its value is avoiding the cost of reconnecting. The maximum still limits the total number of connections to the server, including any held by abandoned evaluations (see Settings and limits): such a connection counts against the maximum until the abandoned call returns, and is then closed instead of being reused.

**Web port** *(later version)*. Browsers cannot open raw database connections, so SQLite, PostgreSQL, and MariaDB sources will be unavailable on the web. HTTP/HTTPS works through the browser's `fetch` and is subject to CORS.

## Trust model

**What trust covers.** Trust applies to all **executable content**: formulas, module sources, form button procedure names, the expressions of form controls, and report expressions. The trust hash is a digest of a canonical serialisation of exactly that content. Data edits do not affect it.

**Recording trust.** User config stores, per workbook, a random **workbook id** (also stored in the file) and the **content hash** at the time of trust.
- **Edits made inside the app** to executable content (typing a formula, editing a module, pasting) update the stored hash while the workbook is trusted. No re-prompt.
- **On open**, a matching id and hash opens trusted. A matching id with a different hash means the file changed outside the app, so it opens untrusted, and the banner lists what changed (which formulas, modules, buttons, report expressions) so the user can review before re-trusting.
- **Save As** gives the copy a new id and carries the trust over, since the user made it.
- Copying an id into a hostile file does nothing, because the hash must match as well.
- A new or unknown file is untrusted. The banner offers "Trust this version" or continue read-only. Trusted workbooks can be listed and revoked in settings.

**Untrusted mode**
- Data, stored values, and stored errors display, and data editing works. Formula cells show the stored value with an `#UNTRUSTED!` badge.
- Formulas can be typed or edited but are not evaluated. Dependents of anything the user edits are shown as **stale** (greyed), since they cannot recalculate. Entering a formula prompts for trust; refusing keeps the text unevaluated.
- Form buttons are disabled, since they all run Python. Form fields still edit the tab directly.
- Reports show blocks that need no Python (static text) and an `#UNTRUSTED!` placeholder elsewhere.

**What containment can and cannot do.** Trust is the real security boundary, and the trust banner says plainly that trusting a workbook allows it to run code. Containment is defence in depth against accidents and casual abuse, not a determined attacker, because sandboxing Python is notoriously leaky:
- The Python engine is built without any operating-system access: no `os`, `subprocess`, `socket`, or file I/O modules exist in it (see Python engine for what this rests on). External access is only through named data sources, each separately granted by the user (see Data sources). Trusting a workbook does not by itself grant any source.
- `open`, `exec`, `eval`, `compile`, and `__import__` are removed from the builtins formulas see, and double-underscore attribute access is rejected when a formula is entered. These catch mistakes; they are not a boundary (see Python engine).

**Resource limits.** Evaluation takes a **budget**: a deadline and optionally a step count. Exceeding it aborts the evaluation with a new error kind, `#TIMEOUT!`, distinct from other Python errors. The limits are user settings (defaults: 1 second per formula and 10 seconds per recalculation; see Settings and limits). A memory limit is not promised in v1. How the budget is enforced is described under Python engine.

## Python engine

- **RustPython**, embedded behind a small `PythonEngine` trait: `eval(expr, globals) -> Result<PyValue>` and `load_module(src)`. The trait keeps the engine swappable (e.g. PyO3 + CPython on desktop later).
- Pure Rust, so the same code compiles to wasm for the web port, with no Python install required.
- Known limits: slower than CPython, incomplete stdlib, no C extensions (no numpy). RustPython describes itself as not totally production-ready, so the engine trait matters.

**Spike results.** A spike was run in October 2026 against RustPython 0.6.1 (GitHub head), on Windows with rustc 1.99.1. It built the interpreter with `--no-default-features --features freeze-stdlib`, which leaves out the `host_env` feature (the part that gives Python access to the operating system). The findings below replace the earlier assumptions in this section.

**Building and depending on it**
- RustPython 0.6.0 from crates.io **did not build** from a fresh dependency resolution: its `ruff` parser crates resolve to 0.16.10, which breaks the code generator, and pinning them to 0.16.5 breaks the parser. RustPython 0.5.0 fails on a `malachite-bigint` version clash. On Windows, `rustpython-host_env` also needed its `ctypes` feature.
- It built only from the repository's own `Cargo.lock`, which uses a git dependency on RustPython's `ruff` fork. On Windows that checkout failed with "path too long" and needed a clone with `core.longpaths` and a `[patch]` to a local copy.
- It needs **rustc 1.97 or newer** (the stable toolchain on the test machine had to be updated from 1.94).
- Consequence: depend on RustPython by pinned git revision, together with its lock file, and vendor or mirror the `ruff` fork. Do not rely on a plain `rustpython = "0.6"` dependency (see Build and dependencies for how it is vendored). Expect to re-check this on every upgrade, and keep the `PythonEngine` trait.

**Cancelling a running formula (the budget)**
- The mechanism works: a watchdog thread sends a closure through `user_signal_channel`, and the VM raises it inside the running code. A `while True: pass` loop and a loop of builtin calls were both stopped about 300 ms after a 300 ms deadline, with the exception surfacing as an ordinary Python error. The interpreter was **reusable afterwards**.
- **A single long builtin call cannot be interrupted.** `sum(range(10**10))` ignored the signal for as long as the test ran (it was killed externally after 20 seconds), because the signal is only checked between bytecode instructions. So the budget cannot catch everything.
- Mitigation: when a cancellation does not take effect within a grace period, abandon the evaluation thread and start a fresh interpreter, accepting that the old thread runs until the call finishes. Also guard the obvious cases (for example `range` above a size limit). The abandon path is the real backstop on desktop, and the number of abandoned threads is limited by a setting (default 20); see Settings and limits.
- On **wasm32** there is no second thread, so the Web Worker termination described earlier remains the only mechanism.

**What the sandbox really is**
- With `host_env` left out, the interpreter has **no file, socket, subprocess, or OS modules at all**: `os`, `posix`, `nt`, `socket`, `subprocess`, `ctypes`, `sqlite3`, `threading`, `pathlib`, `shutil`, `urllib`, and `http` all fail to import. `_io` imports but cannot open files ("Couldn't get FileIO").
- **Removing builtins is not a boundary.** With `open`, `__import__`, `eval`, `exec`, and `compile` removed from the builtins a formula sees, direct use fails with `NameError`. But `().__class__.__base__.__subclasses__()` still reaches `BuiltinImporter`, and `create_module(find_spec('sys'))` hands back `sys.modules`. Had `host_env` been compiled in, the same route would reach file I/O.
- So the guarantee comes from **what is compiled in**, not from what is hidden. Decisions that follow:
  - The Python engine is always built **without `host_env`** (and without `ssl`, sockets, and similar features). All access to files, databases, and the network happens in Rust, through the data source layer.
  - Trimming builtins is kept as a courtesy that catches mistakes, but it is not described as security.
  - As an extra layer, formulas are scanned when entered and rejected if they use double-underscore attribute access (`__class__`, `__subclasses__`, ...). The same scan applies to module source, with a short list of allowed dunder names (`__init__`, `__name__`, ...).

**Modules that work**
- Import fine without `host_env`: `math`, `datetime`, `re`, `json`, `itertools`, `decimal`, `fractions`, `collections`, `functools`, `string`, `textwrap`, `time`, `io`, `sys`.
- **`statistics` and `random` fail** (`no os specific module found`), because they import `os`. They are therefore **not available in v1**, and no replacement is planned. The built-in aggregates (`SUM`, `AVERAGE`, ...) cover the common cases, and a workbook module can supply anything else.
- Registering only an allowlist of native modules was not tested, because nothing dangerous is compiled in. It remains an option for trimming size.

**Speed (release build, Windows)**
- One formula over a 10,000-item list of objects (`sum(o['price'] * o['qty'] for o in items)`): **about 3.6 ms** per evaluation.
- 10,000 separate formulas, each precompiled and run in a fresh scope: **about 20 ms in total** (about 2 microseconds each).
- Compiling each formula from source every time: **about 147 ms** for 10,000 (about 15 microseconds each). So **compiled code should be cached per formula**, but even uncached it is not a bottleneck.
- Not measured: the real application reads data through proxy objects with lazy member access and dependency recording, which will be slower than plain dicts. This is measured when step 3 is built, against these **budgets**:
  - a proxy attribute or index read: **5 microseconds or less** (the Python prototype took about 1.9);
  - 10,000 separate formulas, each reading a few nodes, including result checking: **250 milliseconds or less** in total (plain evaluation took 20);
  - one aggregate formula over 10,000 items read through proxies: **50 milliseconds or less** (plain evaluation took 3.6).

  The nightly performance job reports these figures and fails when a budget is exceeded. They are targets set before measurement and are revised, with the reason recorded here, if the first measurements show they were wrong. If a budget cannot be met, the mitigations are caching converted children, and native fast paths for common aggregations such as summing one field.

**Measured in step 3** (release build, Windows, `cargo test --release -p cliotree-calc --test perf -- --ignored --nocapture`):

| What | Budget set before | Measured | Budget now |
|---|---|---|---|
| One proxy attribute or index read | 5 microseconds | 0.75 to 0.9 microseconds | 5 microseconds |
| 10,000 separate formulas, each reading two array items by index, recalculated with their code already compiled | 250 ms | about 150 ms to evaluate and 70 ms to apply and record dependencies, 225 ms together | 250 ms |
| The same, calculated for the first time (10,000 different formulas to compile, 25 microseconds each) | not set | 410 to 435 ms | 500 ms |
| One aggregate over 10,000 integers, `sum(S.nums)` | 50 ms | 20 ms | 50 ms |
| One aggregate over a projection, `sum(S.items.price)` | 50 ms | 43 to 52 ms | 75 ms |
| One aggregate that goes into 10,000 objects for two fields | 50 ms | 66 to 86 ms | 100 ms |

- **Why the last two changed.** The 50 ms was set for a sum over a plain list of 10,000 numbers read through proxies. Reading an object field makes a proxy for each item (an allocation) and a read for each field, so an item costs about 5 to 8 microseconds in place of 2. The mitigations above are still there if this is not good enough: a native `sum` of one field is the first.
- **The first calculation** is slower than a recalculation because each different formula is compiled once (the engine keeps the compiled code by text). The spike measured 15 microseconds for this; it is 25 here, with the parser and the checks on top.
- **What the first measurements found.** A proxy that remembers the node it read keeps that node shared with the data, so the next edit to the data copies the node first. With a tab's proxy remembering its root, writing 10,000 results into an array copied the array 10,000 times and took 1.4 seconds. The proxies that live as long as the engine now remember nothing; only the proxies made during one evaluation do, and they are not used after it.

**Web (wasm32)** *(later version; recorded for planning)*
- RustPython's own `rustpython_wasm` crate **builds** for `wasm32-unknown-unknown`, which needs the `getrandom` `wasm_js` feature (the crate sets it).
- The unoptimised output was **54.6 MB**. That build includes features we would not use (`ssl`, documentation strings) and was not passed through `wasm-opt` or compression. The achievable size is not yet known and must be measured with a minimal feature set.
- Python was not run in a browser, so Web Worker termination remains untested.

**Not covered by the spike:** running under `wasm32` in a real browser, the proxy layer, memory use, and the effect of the `threading` feature.

## Evaluation and scheduling

All Python evaluation (formulas, form button procedures, report expressions) runs on a **background evaluation thread**, never on the egui UI thread. On the later web port the same role would be played by a Web Worker, using the same message protocol.

**The UI never waits.** Every cell is drawn from its **last calculated value**, the one stored in the tree (see Stored values). A cell whose evaluation is outstanding keeps showing that value, with a subtle pending marker, until a new result arrives. A cell that has a formula but has never been calculated shows empty with the pending marker. The same applies to reports: they render the last values and refresh as results arrive.

**Status bar.** A status bar along the bottom always shows evaluation state:
- `Ready` when nothing is outstanding.
- `Calculating... N pending` while evaluations are queued or running, optionally with a progress indicator.
- Counts of errors and invalid cells, and the workbook's trust state.

**Message flow**
1. An edit on the UI thread marks the affected formula nodes dirty and sends them to the evaluation thread.
2. The evaluation thread evaluates dirty nodes in dependency order and posts results (value or error value, plus the dependencies read) back.
3. The UI applies results at the start of a frame and requests a repaint. Dependents of a changed result are queued in turn.

**Consistency**
- Every result is tagged with the input version it was computed from. If an edit has since changed something the formula read, the result is discarded and the formula is queued again. The UI never shows a result computed from superseded inputs once it has been superseded.
- A formula never observes a half-applied edit: the evaluation thread works against a consistent snapshot of the data and picks up newer versions between evaluations.
- An in-flight evaluation whose inputs have changed may be cancelled through the same mechanism as the timeout budget (see Python engine), so a long-running formula does not delay the response to an edit.
- Per-formula and per-recalculation budgets apply as described in the trust model; a timeout is stored as `#TIMEOUT!` like any other error.

**Volatile functions.** `NOW`, `RAND` and similar are evaluated once per recalculation pass and keep that value until the next pass. A full recalculation happens when a trusted workbook is opened and when the user asks for it explicitly ("Recalculate", F9). There is no timer-driven refresh in v1.

**Saving while evaluating.** Saving waits for outstanding evaluations to finish so the file never holds half-updated values. The status bar shows that it is waiting, and the user can cancel the wait and save with the current last values, which are flagged as pending in the overlay.

**Forms.** Button procedures run on the same thread, one at a time (as already specified). While one runs, the form's buttons are disabled and the status bar shows it.

## Settings and limits

Limits are not hard-coded. The user sets them, with defaults, in two places.

- **Workbook settings** are stored in the workbook (`settings.json`) and edited in the *ClioTree Options* dialog (see The Options dialog). They govern how that workbook's Python and data sources run.
- **Application preferences** belong to the user, not to any file. They hold the limits that apply *before* a workbook is open or trusted (reading a file, importing), and a **ceiling** for each workbook setting.

**A workbook cannot raise its own limits past the user's ceilings.** A file is untrusted input, so a hostile workbook that asks for a one-hour time limit gets the ceiling instead. The dialog shows each value with its default and ceiling, rejects out-of-range input, and shows the effective value when a ceiling applies. Workbook settings are part of the executable content covered by trust, since they govern execution (see Trust model); editing them inside the application keeps trust, and a change made outside it drops trust. Changes are undoable edits.

**Workbook settings**

| Setting | Default | Meaning |
|---|---|---|
| Formula time limit | 1 s | Longest a single formula or module load step may run (CPU time, not I/O waits) before `#TIMEOUT!`. |
| Button procedure time limit | 10 s | Longest a form button procedure may run (CPU time, not I/O waits) before its writes are dropped and the message shown. |
| Recalculation time limit | 10 s | Longest one recalculation pass may run. |
| Cancel grace period | 500 ms | After a cancel signal, how long to wait for the evaluation to stop before abandoning it. |
| **Maximum abandoned threads** | **20** | How many abandoned evaluations (see below) may still be running at once. |
| Maximum range length | 1,000,000 | Largest sequence `range` may produce. |
| Data source call timeout | 30 s | Longest a data source call may take, including waiting for I/O. |
| Maximum response size | 16 MB | Largest data source response accepted. |

More settings can be added in the same way, with a default and a ceiling each.

**Application preferences** (not stored in workbooks): the ceiling for each workbook setting; and limits that apply while a file is being read or imported, namely the maximum number of zip entries, maximum total uncompressed size, maximum import file size, and maximum nesting depth; plus the undo history bounds (entry count and memory budget).

**Abandoned threads.** A formula that does not stop after a cancel signal and the grace period (for example one long builtin call, which cannot be interrupted; see Python engine) is **abandoned**: its result is discarded, its node gets `#TIMEOUT!`, and a fresh interpreter takes over so evaluation continues. The abandoned thread keeps running until its call returns, and then it is released. The number of such threads still running is limited by *Maximum abandoned threads*.
- The count appears in the status bar when it is above zero (for example `2 abandoned`).
- **At the limit, evaluation is suspended.** No new evaluation starts, pending cells keep their pending marker, and the status bar shows `Evaluation suspended: 20 abandoned threads still running`. It resumes by itself when the count drops below the limit.
- The Evaluation page of the Options dialog offers **Save and restart**, which saves the workbook (without waiting for evaluation, flagging pending cells as for any save) and restarts the application, since a thread that never returns can only be cleared that way.
- Raising the limit takes effect immediately, up to the user's ceiling.

**Guards on builtins.** The `range` builtin is replaced by a version that refuses a length above *Maximum range length*, raising `ValueError` (shown as `#VALUE!`) with a message naming the setting. This catches the accidental case such as `sum(range(10**10))` before it starts. Guards are **best effort**, not a security boundary: they cover the wrapped builtins and obvious literals, not every way to build a huge value. The abandoned-thread limit is the real backstop, and a memory limit is not promised in v1.

### The Options dialog

All settings are edited in one **ClioTree Options** dialog, laid out like Excel's Options dialog. It opens from **Tools > Options**.
- A **list of categories** runs down the left, the chosen category's settings fill the right, and **OK** and **Cancel** sit at the bottom. Enter is OK and Esc is Cancel. Nothing takes effect until OK, and Cancel discards every change in the dialog.
- Each page says in its heading **what it applies to** (and is divided into sections, see below): *This workbook* (stored in the workbook) or *All workbooks* (stored for the user). If no workbook is open, the workbook pages are hidden.
- Each setting shows its default, rejects out-of-range input inline, and has a **Reset to default** button. A workbook value that a ceiling is holding down shows the effective value beside it and says why.
- **OK applies the workbook settings as one undoable entry.** Application preferences take effect on OK and are not part of the undo history, because they are not part of the workbook.
- Other parts of the application link straight to a page: for example the status bar's *Evaluation suspended* message opens the Evaluation page.

**Pages and sections.** Each page is divided into titled **sections** (group boxes), as in Excel, so related options sit together. The defaults are in brackets.

## Undo and redo

The workbook keeps one **edit log** so that user edits can be undone and redone. The history is a single linear sequence for the whole workbook, like Excel's, not one per tab.

**What is logged.** Every edit the user makes:
- literal values, and structural changes (inserting, removing, moving, or sorting items and map entries);
- formulas, and comments (XML tabs);
- tabs: adding, removing, renaming, reordering, and rebinding schemas;
- Python modules, form designs, report designs, and data source definitions (not secrets and not grants);
- schema sheet edits, which are ordinary tree edits, and schema edits made from the data tab that uses the schema (see Editing the schema from a data tab), each together with the data changes it causes, as one entry;
- the table-wide edits made by paste, import, and button procedures.

**What is not logged.**
- Computed results, error values, and pending state. They are derived, not authored. After an undo, the formulas affected are recalculated and the new results appear as usual.
- View settings such as expanded nodes, column widths, and whether an array is shown as a table.
- Effects outside the workbook. A procedure that writes to a database or HTTP endpoint cannot be undone; its workbook edits can.
- Granting or revoking data-source access, and trust decisions.

**Entries.**
- One user gesture is one entry: committing a field, a paste, running a button procedure (all of its writes together), an import, dragging items into a new order.
- Rapid consecutive edits to the same text cell during one editing session are merged.
- Each entry has a short description, shown in the Edit menu ("Undo Set Orders.items[2].price").
- An entry records enough to reverse itself: the old and new value, or the removed subtree. Removed subtrees are held by reference, so deleting a large array does not copy it, and restoring a subtree restores its original `NodeId`s.
- Entries refer to nodes by `NodeId`, not by path, so they stay valid when other edits shift paths. Formula entries refer to a location (a path), consistent with formulas belonging to a location.

**Behaviour**
- Undo and redo are ordinary edits as far as the rest of the system is concerned. They apply on the UI thread, bump the data version, and queue recalculation. Evaluation results computed from superseded inputs are discarded by the usual version rule.
- A new edit after an undo clears the redo history. There is no branching.
- Undoing or redoing a change to executable content (a formula, module, button, or report expression) counts as an edit made in the app, so it keeps the workbook's trust (see Trust model).
- Undo and redo are disabled while a button procedure is running.
- The log tracks the saved state, so undoing back to the saved point clears the "modified" mark.
- The history lives in memory only. It is not saved in the `.clio` file and is cleared when the workbook is closed. It is bounded by an entry count and a memory budget (application preferences), and the oldest entries are dropped first.
- Keys: Ctrl+Z to undo, Ctrl+Y or Ctrl+Shift+Z to redo.

**Structure.** `cliotree-core` defines the primitive edit operations on the data tree and how to apply and invert them. The workbook-level log, which also covers the other kinds of edit above, lives in the layer above (`cliotree-calc`), and the UI only issues edits and requests undo and redo.

## Comments in the UI

Comments on XML tabs look and behave as they do in Excel.
- **Indicator.** A cell with a comment shows a small coloured **triangle in its top-right corner**.
- **Hover.** Resting the mouse pointer over the cell (after a short delay) shows the comment in a small popup beside the cell. The delay, and the popup's maximum size (long text wraps, then scrolls), are options on the Display page. It disappears when the pointer leaves. The comment can be read on any cell, including cells of computed nodes.
- **Commands.** Right-clicking a cell offers **Insert Comment**, or **Edit Comment** and **Delete Comment** when it already has one. Insert and Edit open a small text box for the comment. Enter adds a line break, and committing is done by clicking away or with Ctrl+Enter; Esc cancels. The commands are absent on JSON tabs.
- **Where.** The triangle is drawn on the node's cell in the tree grid and in the tabular view alike. For an object or array node it is on the node's own row (or on the array's header in the tabular view).
- Inserting, editing, and deleting a comment are undoable entries in the edit log, and each is a change to the document, so it marks the workbook as modified.

## Editing the schema from a data tab

When the schema sheet's **auto-update** is on (see Schema binding), the single tab that uses the schema can change the schema from its own grid, instead of switching to the schema sheet. The commands are in the context menu of an object or array node (and, for fields, on a column header in the tabular view).

**Commands in v1**
- **Reorder fields** (dragging a column header).
- **Add field**: adds a property (JSON Schema) or element or attribute (XSD) to the object type, with a name and a simple type chosen in a small dialog, and whether it is required.
- **Rename field.**
- **Delete field.**

More involved changes (changing a type, adding constraints, adding nested types) are made by editing the schema sheet directly, which is always possible.

**What each command does to the data**, so that the tab never ends up out of step with its schema:

| Command | Schema | Data |
|---|---|---|
| Reorder fields | Declared order changes. | Items are written in the new field order. No values change. |
| Add field | New optional or required field. | Existing items get no value for it: an optional field is simply absent, and a required one is shown as a missing required value (flagged, per the invalid-data rules). |
| Rename field | The field has the new name. | The key is renamed in every item, with its value, comment, and hidden or filter state. **Formulas are not rewritten**, as with any rename (see Renames do not rewrite formulas): formulas that use the old name show `#REF!`. A formula on the field stays at its location, which now has the new name. |
| Delete field | The field is removed. | The values are **removed from every item**. Because this is destructive, a confirmation states how many values will be removed. Formulas that use the field show `#REF!`. |

**One undo entry.** A command, together with its data changes, is **one entry** in the workbook's edit log, described in the Edit menu by what it did (for example *Undo Rename field "qty" to "quantity"*). Undo restores the schema, the field order, and any removed values together.
- Because the log is a single linear history, a later edit to the schema sheet (made directly on its tab) is a later entry. It must be undone first, so an entry can never be undone against a schema that has since been changed in some other way.
- Because auto-update allows only one user of the schema, a command never changes any tab other than the one it is issued from and the schema sheet.

**Details**
- **Attributes and elements (XML).** *Add field* on an XML tab asks whether the new field is an **element** or an **attribute** (attributes can only have simple types). Reordering is among elements and among attributes separately. An attribute cannot be dragged among the elements, because XSD keeps them apart. An element that holds text (`xs:simpleContent`) takes attributes only, and its text is not a field that can be renamed or deleted. See the decisions for the XML field commands.
- **Maps.** A `Map` has no declared fields (its keys are data, not schema), so the field commands are not offered on a map node. Map entries are added, renamed, and removed as data.
- **Shared types.** If the object type is a named type (`$defs` with `$ref`, or a named `xs:complexType`) that the schema uses in several places, a command changes the type, and so **every place it is used**. The confirmation lists those places (for example *also used at Orders.billing and Orders.shipping*), and the data change applies at each. Renaming a global `xs:element` rewrites every `xs:element ref` to it in the same schema.
- **The item type itself.** Renaming or deleting a type is not a command of the data tab. It is done on the schema sheet, as ordinary tree editing, and references to it are not rewritten (an unresolved reference is a schema error shown on the sheet).
- **The schema sheet is also open.** The schema sheet and the data tab are two views of the same workbook state, so the schema sheet's grid simply updates. If the schema sheet has a cell edit in progress that is not yet committed, the command is refused with a message to finish or cancel that edit first.

## Tabular view of arrays

An array whose items are objects can be shown as a table instead of as indented tree rows.
- **Toggling.** The user right-clicks the array node's row. A context menu offers **Tabular view**, a toggle that switches it on or off. The menu item appears only on arrays of objects.
- **Persistence.** The setting is per array node and saved in the tab's overlay, as view state. It is not part of the data, not undoable, and not part of the trust hash.

**What the table shows**
- One **row** per item, with the item index in a row header.
- One **column** per scalar field of the item type, in the schema's declared order, with the field name as the header. Hidden columns and rows are not drawn (see Sorting, filtering, column order, and hiding).
- A field that is itself an object is **flattened** into dotted columns (`address.city`), to any depth.
- A field that is an array or a map has a **summary cell** (for example `[5 items]`). Opening it drills into that value as an ordinary tree below the table, so tables do not nest.
- Optional fields that are absent appear as empty cells that can be filled.

**Cells are the same cells as in the tree.** A table cell is the node's cell, with all the same behaviour: literal editing with the type-aware editors, formulas, error values, the pending marker, the invalid-data outline, and comments (on XML tabs). Selecting one shows its formula in the formula bar. Formulas refer to nodes by path as always (`Orders.items[2].price`); the table is a different way of drawing the tree, not different data.

**Editing in the table**
- Add a row at the end, insert above or below, delete rows, and move rows up or down. These are structural edits and are undoable.
- **Moving a row up or down swaps it with the next visible row.** The two rows exchange positions in the array, and any hidden rows in between stay where they are. Move up is unavailable on the first visible row, and move down on the last.
- A formula on the array node itself makes the whole array computed, so the table is read-only.
- Cell ranges copy and paste as tab-separated text. A paste validates each cell and is applied as one undoable entry; cells that don't validate are rejected with a message and nothing is written.

**Sorting, filtering, column order, and hiding**

*Filtering hides the rows that do not match.* A column header menu offers **Filter**, as in Excel. Rows that are filtered out are **hidden**, and hidden in exactly the sense defined under Hiding below: they still exist logically, keep their indices, and are read, validated, saved, and recalculated as usual. A filter changes what is drawn and nothing else, so unlike a sort it is not an edit of the data and is not undoable.
- **Conditions.** A column can be filtered in two ways, which combine: by a **list of values** (checkboxes of the distinct values in the column, including `(blank)` for absent values and `(errors)`), and by a **condition** chosen for the column's type: equals, does not equal, greater or less than, between, begins with, ends with, contains (strings, with an ignore-case option), and is blank. Comparisons use Python's ordering for the type.
- **Several columns** can be filtered together. A row is shown only if it passes every column's filter.
- **Indicator.** A filtered column shows a funnel on its header, and the table shows how many rows are shown, for example `12 of 340`. The marker where rows are hidden counts them separately from rows the user hid by hand.
- **Clearing.** The header menu has **Clear filter** for a column, and the table has **Clear all filters**. Clearing makes the rows visible again unless they were also hidden by hand.
- **Live, with one exception.** A filter is re-evaluated as the data changes, including when recalculation changes a computed value. The exception is rows the user has just added or edited: such a row stays visible even if it no longer matches, until the filter is next changed or the user chooses **Reapply filter**. This stops a row vanishing while it is being typed into.
- **Filtering a computed array** is allowed, since it changes only the view.
- **Where.** Filtering is available in the tabular view only.
- **State.** Filters are view state, saved with the tab in the overlay (by field name), not part of the data, and not part of the trust hash.

*Sorting changes the data.* **Sort ascending** and **Sort descending** in the context menu of a column header sort the array's items by that column (a click on the header selects the column, see Column formulas). The sort is a real reorder of the array, so it is logical and not just visual: after sorting `Data.items`, the reference `Data.items[2]` points at whatever item is now third. References are literal (see Formulas), so nothing is adjusted.
- **It is permanent.** A sort is an edit of the data, like any other. The table holds no sort state and shows no sort indicator, and the only way back is the **Undo** command (it is one undoable entry).
- **Python's ordering, in every case.** Items are compared with Python's own ordering of the column's values (numbers numerically, strings by code point, dates chronologically). There is no special handling of absent values or error values: if the ordering raises an exception, for example comparing a string with a number, or comparing an absent value with a number, or reading an error value, **the sort does not happen**. Nothing is changed, and a message gives Python's error and the rows involved. A column with absent or error cells therefore cannot be sorted until they are filled or fixed. To help, the message has a **Show these rows** button, which applies a filter that shows only the offending rows, so they can be fixed and the sort tried again.
- **Stable.** Items with equal values keep their existing relative order (a descending sort is also stable). This is what makes a multi-column sort work with no extra feature: sort by the least important column first, and then by each more important one, so that **each new sort becomes the first key and the earlier sorts remain as the tie-breakers** among equal values.
- **All items are sorted, hidden ones included.** Hidden rows, whether hidden by hand or by a filter, still exist logically, so a sort reorders the whole array. The visible rows come out in the new order and the hidden ones are placed by the same rule.
- Formulas belong to their location, not to an item. A sort therefore moves the literal values, comments, and children of each item, but a formula stays at its position and is recalculated against the item that is now there.
- A computed (formula-driven) array is read-only and cannot be sorted. The header click explains why, and a formula can use `SORT` instead.

*Reversing the order.* The array's context menu and the table's toolbar have **Reverse row order**, which reverses the whole array without naming any column. It is a permanent edit like a sort, applies to hidden items too, and is unavailable on a computed array. It can be reversed in either of two ways: with the **Undo** command, or by **executing Reverse row order again**, since reversing twice restores the original order exactly. Executing it again is a new edit of its own, so it adds another entry to the history rather than removing one, and Redo is not available afterwards.

*Column order changes the field order.* With auto-update on for the tab's schema, dragging a column header to a new position reorders the **fields** of the item type, and so the field order of every item (see Editing the schema from a data tab). Without auto-update the columns cannot be dragged, and the tooltip explains why.
- The field order is what Python sees when it iterates an object's fields, and what files are written with. For XSD it is also the order of elements in the XML.
- Dotted columns (fields of a nested object) can be reordered only among the fields of the same parent. A column cannot be dragged to a different parent.

*Hiding.* Columns, rows, and any other data value can be **hidden**, and any hidden value can be **unhidden**.
- **Hidden values still exist logically.** Hiding, whether by hand or by a filter, changes only what is drawn. A hidden row keeps its index (`Data.items[2]` is still the third item), formulas read hidden values as usual, they are validated, saved, exported, and recalculated like any other, and their errors still count in the status bar.
- **Where.** Hide a column from its header menu, a row from its row header menu, and any node from its context menu in the tree view. Hiding a node or row hides everything inside it.
- **Marker.** Where something is hidden, a thin marker sits between its visible neighbours (as in Excel). A hidden node's parent shows the count, for example `(3 hidden)`; in a filtered table the marker gives the two counts apart, for example `(3 hidden, 5 filtered)`.
- **Unhiding.** The marker, and the context menu of the parent or array node, open a list of the hidden items with **Show** for each and **Show all**, which cancels only manual hiding. Rows hidden by a filter come back by clearing the filter.
- **State.** Hidden state is view state. It is saved with the tab (in the overlay) but is not part of the data, is not undoable, and is not part of the trust hash. A hidden row or node stays hidden when it moves, for example after a sort, because the state is attached to the item and is saved by path. Hidden columns are recorded by field name.
- **Keyboard navigation skips hidden items.** The arrow keys, Tab, Home and End, and Page Up and Down move only among items that are shown, in both the table and the tree view. If the selected item becomes hidden, because the user hid it or a filter changed, the selection moves to the nearest shown item.
- **Copy and paste** include hidden items. A copied range is the whole logical rectangle between the selection's corners, so hidden rows (whether hidden by hand or by a filter) and hidden columns inside it are copied along with the visible ones. A paste is likewise cell for cell by logical position from the target cell, writing into hidden cells in the same way, so what is pasted matches what was copied. The same validation applies to every pasted cell, hidden or not.

**Performance.** Both the table and the tree view only draw the rows that are on screen, so arrays of many thousands of items stay responsive. The table can be built on `egui_extras`' virtualised table support.

## Import and export

**Importing a standalone file** creates new tabs in the workbook: a data tab, bound to a schema sheet. *File > Import...* chooses the file, and **dropping files on the window** imports each of them the same way (a dropped `.clio` file is opened instead). **If the data fits a schema sheet already in the workbook, it is given that one; if it fits none, a schema is inferred from it** and becomes a new schema sheet, to which the data tab is bound by the normal sheet-reference rule.

| File | Data tab format | Inferred schema |
|---|---|---|
| `.json` | JSON | JSON Schema |
| `.xml` | XML | XSD |
| `.csv` (comma-separated), `.tsv` or `.tab` (tab-separated) | JSON | JSON Schema for an array of objects, one per row |
| anything else (plain text) | JSON | JSON Schema for an array of strings |

- **CSV and TSV** *(required by the owner on 2026-10-28)* import as an array with an object for each row (`delimited.rs` in `cliotree-core`). Cells are read as RFC 4180 has them: a cell in double quotes may hold the separator, line breaks and `""` for a quote; unquoted cells are trimmed of spaces, and blank lines are skipped.
  - **A header row is assumed**, and its cells name the fields. **Only when it cannot be a header, because one of its cells is a number or `true`/`false`, is it data**, and the columns are named `column_1`, `column_2`, `column_3`, ... An empty header cell is named the same way (`column_N` for its place), and a name that repeats gets `_2`, `_3`. Cells beyond the header's names are named from their place too. The report says which way the first row was read.
  - **Each column is typed as a whole**: whole numbers if every value in it is one, numbers if every value is a number, yes or no if every value is `true` or `false` (in any case), and text otherwise. So a column of codes keeps `007` as text, and a column with one word in it is all text. A quoted value is text. **An empty cell leaves the field out**, so a column with an empty cell is an optional field.
  - The fields of the schema keep the order of the columns.
- **Pasting** *(required by the owner on 2026-10-28)*. **Ctrl+V in the Raw view imports the clipboard as if it were a file** dropped on the window: the import dialog opens for it, titled *Import the pasted text*, and the tab is called `Pasted` (`Pasted2`, ...). With no file name, the format is told from the text: `{` or `[` first is JSON, `<` is XML, a tab in the first line is TSV (a range copied from a spreadsheet), a comma CSV, and anything else lines of text. When the paste is in the format of the tab shown (JSON on a JSON tab, XML on an XML tab), the dialog offers one more choice, **replacing that tab's data** instead of making a new tab, which is what a paste in the Raw view did before: the document must conform to the tab's schema, or it is refused with the reasons, and it is one undoable edit. A new tab stays the default.
- **Plain text** imports as though it were a JSON array of strings, one per line. Line endings are normalised, a final newline does not add an empty item, and blank lines in the middle are kept as empty strings. The text must be UTF-8 (a BOM is stripped); anything else is refused with a message.
- **Matching existing schemas.** Every schema sheet of the file's format (JSON Schema for JSON and text, XSD for XML) is tried: the data is read against it and validated. The dialog lists them with how many values would not fit each (an XSD whose root element is not the file's is left out), and starts on the first that the data fits completely, in tab order, or on the inferred schema when none does. The user may still choose any of them, or the inferred schema; data loaded against a schema it does not fit follows the normal invalid-data rules (kept, flagged, unrecognised content preserved).
- **Names.** The tabs are named from the file name, sanitised to a valid identifier (invalid characters become `_`; a leading digit, a leading underscore, a reserved word, or a clash with an existing name gets a prefix or numeric suffix). The schema sheet is `<Name>Schema`. The dialog lets the user change both before importing.
- **Import report.** A dialog shows the inferred schema and every warning (dropped nulls, type conflicts, oversized integers, a dropped DOCTYPE) before the user confirms. Nothing is added to the workbook until then. Several dropped files get one dialog each, in turn.
- **Undo.** An import is one entry in the edit log, *Import orders.json*, which takes out both tabs. An inferred schema sheet starts with auto-update off, so that the next file of the same shape can be given it as well.
- Parsing is bounded: limits on file size and nesting depth guard against hostile input (application preferences; see Settings and limits). Importing never runs Python.

**Schema inference** always produces a schema inside the v1 subset (closed objects, arrays, simple types, no unions or nulls). It is a starting point; the user can edit the schema sheet afterwards.

| Observed data | Inferred schema |
|---|---|
| Object | Object with properties in observed order. A property present in every observed instance is `required`; otherwise optional. |
| Array of objects | One item type; properties merged across all items, required only if present in every item. |
| Scalars | `string`, `integer`, `number`, or `boolean`. A mix of integers and non-integers is `number`. |
| Empty array | Items typed `string`, and flagged in the report as "inferred from no data". |
| `null` | Cannot be represented (no nulls in v1). Treated as absent: the property becomes optional; a null array item is dropped. Both are reported. This holds whichever schema the data is given. A property that is only ever null is an optional `string`, reported as inferred from no data. |
| JSON strings | Plain `string`. Date-like strings are not given a `format`. |

- **Conflicts.** If the same position holds different kinds of value, the **most common kind wins** (a tie goes to the more general: string over number over integer over boolean). Values of the other kinds are not converted or discarded: they stay in the tree as invalid literals, flagged. A conflict between structures (an object where most instances have a string, or vice versa) keeps the minority subtree as unrecognised content, flagged.
- **XML** specifics:
  - The root element becomes the single global element. Nested elements are anonymous types.
  - An element that repeats under its parent anywhere in the data becomes an array (`maxOccurs="unbounded"`); an attribute becomes `xs:attribute`, required if always present.
  - Element text is typed by its values: integers → `integer`, decimals → `decimal`, `true`/`false` → `boolean`, ISO 8601 dates and datetimes → `date` / `dateTime`, otherwise `string`. Values with leading zeros (other than `0`) are strings, so identifiers like `007` are not turned into numbers.
  - Child order is the merge of the orders seen across instances; if instances disagree irreconcilably, the first-seen order is used and the report says so.
  - **Refused with a clear message:** mixed content (non-whitespace text next to child elements), and more than one namespace. These are outside the v1 XSD subset.

**Exporting.** Any tree tab exports as a standalone file in its own format.
- Everything the user gave the tab is written: field order, array order, XML attributes and elements as the schema maps them, XML comments (the comments on nodes), namespace prefix and XML declaration, and **unrecognised content** that was preserved on import. The result is what the tab shows, including the latest computed values. Errored nodes are absent (see Stored values).
- Dates are written in their XML lexical forms, floats with their shortest round-trip spelling, and JSON/XML indentation is two spaces by default with a compact option.
- Formulas and tab settings are not part of a standalone export; the `.clio` is the format that keeps them.
- A schema sheet exports as a standalone `.json` or `.xsd`/`.xml` file in the same way, and the export dialog offers to include the schema alongside the data: the schema tab the data tab is bound to, written beside the file and named after it, `<name>.schema.json` or `<name>.xsd`.
- A tab whose root is an array of strings can also be exported as a plain text file, one string per line, mirroring text import.

## File format

A workbook is saved as a **zip archive with the extension `.clio`**. It is an ordinary zip, so any zip tool can open it, and the data inside is plain JSON, XML, and Python source.

**Layout**

```
manifest.json            first entry in the archive
sheets/<Tab>/data.json   (or data.xml)   the tab's data tree, with stored values
sheets/<Tab>/overlay.json                formulas and their status
sheets/<Tab>/forms/<Form>.json           a customised form design of the tab
reports/<Report>.json                    report design (later version; reserved)
modules/<name>.py                        Python modules
datasources.json                         data source definitions, no secrets
settings.json                            workbook settings that differ from the defaults (see Settings and limits)
view.json                                view state of the whole workbook: the font of the data views
```

- **Tabs** are one directory each. Tab names are valid identifiers and unique ignoring case (see Names and reserved words), so they are safe as file names on every platform. A schema sheet is stored the same way as any tree sheet (JSON or XML data, according to its meta-schema).
- **Data files** hold the plain data, including the latest computed values, exactly as other tools would expect (see Stored values). Errored nodes are absent from them.
- **Overlay** holds, per node path: the formula text, and its status (ok, pending, or the error kind, message, and traceback). Entries are sorted by path. It also holds the tab's view state, such as which view is current and which arrays are shown as tables. Comments are not in the overlay: they are XML comments in `data.xml`.
- **Reports** are the design documents described in their section, with the report name as the file name. **Forms** are stored under the tab they are views of: `sheets/<Tab>/forms/<Form>.json`. A form that has not been customised has no file, so the generated Default form is never stored.
- **Modules** are plain `.py` files, so they can be edited, diffed, and linted with ordinary tools.

**Manifest** (`manifest.json`) records:
- `format_version` (major.minor), and the application version that wrote the file.
- The **workbook id** used by the trust model.
- The **reserved-names version** (see Names and reserved words).
- The **Python engine and its version**, so a file written against one RustPython release can be flagged when opened with another.
- The list of tabs in tab order, each with its kind (`data` in v1; `report` is reserved for the later version) and, for tree sheets, its **schema binding**: `builtin:jsonschema`, `builtin:xsd`, or `sheet:<Tab>`.
- The list of modules in display order, and for each Data Tab the customised forms in display order.

**Writing**
- Text is UTF-8 with LF line endings. JSON is pretty-printed with a stable key order; data keeps the schema's declared field order.
- Archive entries are written in a fixed order, with a fixed timestamp and no per-save metadata. Saving a workbook whose content hasn't changed produces identical bytes, so a `.clio` file behaves well in version control, and unzipped it diffs cleanly.
- Saves are atomic: write to a temporary file in the same directory, then rename over the original.
- Saving waits for outstanding evaluation (see Evaluation and scheduling).

**Reading**
- The zip is treated as untrusted input. Entry paths that are absolute or contain `..` are rejected, and limits apply to the number of entries and to total uncompressed size (to guard against zip bombs; these are application preferences, see Settings and limits). Opening a file never runs anything; Python only runs after the trust check.
- **Versioning.** The same major version opens. A newer minor version opens with a warning, and unknown entries are kept and written back unchanged on save. A newer major version is refused with a message saying which version is needed. Older formats are upgraded in memory on open, and the user is warned before the upgraded file overwrites the original.
- The trust hash is computed from the parsed executable content (see Trust model), not from the bytes of the archive. Reordering entries or changing whitespace does not change it.

**Plain data.** Because data files are ordinary JSON or XML, users can extract a tab's data from the archive directly. Importing and exporting standalone files is described in Import and export.

## Application structure

Cargo workspace:
- `cliotree-core`: `Value`, `TypeSpec`, paths, schema lowering (JSON Schema, XSD), format adapters, validation. No UI, no Python.
- `cliotree-calc`: formula storage, dependency graph, recalculation, error values, proxy objects, `PythonEngine` trait and RustPython implementation.
- `cliotree-std`: built-in functions.
- `cliotree-app`: egui frontend and file I/O. The only crate touching `eframe` or the filesystem, so that a later wasm port needs only a different `main` and storage layer. Keeping these crates free of UI and filesystem code is a v1 design constraint for that reason.

**Workbook file format**: a zip with the extension `.clio` (see File format).

**UI**
- Sheet tabs along the bottom; formula bar above a tree grid. (In a later version, a report tab will show the rendered report instead, with charts drawn through `egui_plot`.)
- Tree grid columns: `Name | Type | Value | Formula`; expandable nodes, array items as indexed rows.
- Type-aware editors: toggles for booleans, dropdowns for enums, numeric fields.
- Schema violations get a red outline; computed cells get a distinct fill.
- Side panels for the error list, and for modules and trust state.
- A view selector for each Data Tab (the Data tree and its forms), and a code area holding Python modules and the raw text of form designs (see Forms).

### Renaming a tab

A tab is renamed from the window, as in Excel.
- **Where.** Double-clicking a sheet tab, or *Rename tab...* in the tab's context menu (right-click on the sheet tab) or in the Edit menu (for the current tab). Each opens the same small dialog, *Rename tab Orders*, with the name field holding the current name, selected.
- **The name is checked live** as it is typed, by the rules of Names and reserved words: a valid Python identifier, not a reserved word, and unique ignoring case. The message under the field names the problem or the clash (for example *A tab called orders already exists*), and *Rename* is disabled until the name is valid. Changing only the case of the name (`orders` to `Orders`) is allowed. A name equal to the current one closes the dialog without an edit. Enter renames, Esc cancels.
- **What the dialog warns about.** Formulas are not rewritten (see Renames do not rewrite formulas), so the dialog says how many formulas and modules mention the old name as an identifier (a button names a module function, never a tab), for example *3 formulas and 1 module use Orders. They are not changed, and will show #NAME! until they are edited.* It is a count, not a list, and the rename goes ahead regardless. A find-and-replace over formulas may be offered later as a separate command, never as part of the rename.
- **What follows the tab.** Everything that belongs to the tab rather than naming it:
  - its data, formulas (each stays at its location), comments, forms and their designs, the current view and the rest of its view state, and its place in the tab order;
  - **schema bindings.** A binding is a reference held by the workbook, not text the user wrote, so it follows the tab: renaming the schema tab `Orders_schema` rebinds every tab bound to `sheet:Orders_schema` to the new name, and the schema bar's *Used by:* line shows the new name of a renamed data tab. Nothing is re-lowered or revalidated, because no schema changes;
  - on save, the tab's directory in the archive (`sheets/<Tab>/`) and its entry in the manifest are written under the new name. The old directory is not kept.
- **What does not follow.** Formula text, button procedures, module source and report expressions that mention the old name are left as they are. After the rename they are recalculated: references to the old name give `#NAME!`, naming it, and anything that already used the new name (and failed) now finds the tab.
- **A name that broke the rules.** A tab opened from a file with a name that breaks the rules (warned about on opening, as described under Where it is checked) is fixed by renaming it: the dialog accepts any valid name, and the next save writes it, so the warning does not come back.
- **Undo.** A rename is one entry in the edit log, *Undo Rename tab Orders_schema to OrderTypes*, and undoing it restores the old name, the old bindings and the old view state together. It is refused while a button procedure is running, like other edits.
- **Trust.** A rename changes no formula, module or setting. It is an edit made in the app, so it keeps the workbook's trust, and the next save records the digest again (the digest names each formula by its tab, so it does change).
- **The control channel** gets a `rename_tab` command (old name, new name) for the end-to-end tests, answering with the problem when the name is refused.

### Managing tabs

Tabs are added, deleted and given another schema from the window. The commands are in the Edit menu (for the current tab) and in a sheet tab's context menu, together with *Rename tab...* and *Import...*; a `+` after the last tab is *New tab...*.
- **New tab...** asks for the name and the schema: **its own schema**, a new empty JSON Schema sheet `<Name>Schema` with auto-update on, so that its fields are added from the data tab (as *File > New* makes), or **the schema of** a schema sheet already there, in which case the tab starts with what a new item of that type holds (required fields filled in). Both names are checked as a rename is. New tabs go at the end, and the new tab is shown.
- **Delete tab...** asks first, and says how many formulas and modules use the tab's name (*3 formulas use Orders; they will show #NAME! until the tab is back*). It is refused for the only tab of a workbook, and for a schema sheet that tabs use (*Orders uses this schema; delete that tab or give it another schema first*). The tab after it is shown, or the one before for the last tab.
- **Change schema...** binds a data tab to another schema sheet of the same format: JSON data takes a JSON Schema and XML data an XSD, because a tab keeps its format. The data is not changed; the dialog says how many values would not fit, and they are flagged. A schema sheet with auto-update on that another tab uses is refused, as for any binding.
- **Undo.** Each is one entry in the edit log (*New tab Notes*, *Delete tab Orders*, *Bind Prices to Orders_schema*). Undoing a delete puts the tab back with its data, formulas, column formulas, forms and place; formulas that named it find it again. What the window kept for a deleted tab (open nodes, tables, the current view) is not kept.
- **Trust.** Like a rename, these are edits made in the app and keep the workbook's trust.
- **The control channel** gets `new_tab`, `delete_tab`, `bind_schema` and `import` for the end-to-end tests.

### Look and feel

ClioTree should look like a precise desktop utility, not a web page: flat fills, 1 px borders, small corner radii, and shadows only on menus, tooltips, popups and windows. The design started from a mockup and token list worked out with Canva AI and was then fitted to egui. Every colour, size and font is in one file, `cliotree-app/src/style.rs`, which installs the fonts and the styles of both themes on the first frame.

- **Two themes, the same layout.** Light and dark differ only in colour. Each theme is a `Palette` of named colours: chrome (the bars), panel, field, border, row stripe, control, hover, selection and its outline, accent, primary button, text and weak text, computed tint, error and error fill, warning, success, pending, stale, trust banner fill and text, and the type badges. The window follows the system theme until the Options dialog lets the user choose.
- **Cell states** are told apart by more than colour: a formula's value has a translucent tint (so it still shows on a striped, hovered or selected row), an error value has red text on a red fill, invalid data has a 1 px red outline, a cell waiting to be calculated has a small amber dot, and a stale value under an untrusted workbook has grey text.
- **Type badges.** The Type column shows each type as a small rounded badge in the colour of its kind: string (and enum) violet, number blue, integer teal, boolean amber, object (and map) green, array purple, date and date-time pink.
- **Sizes.** Rows are 28 points high (more for a larger data or form font: the text height plus 11) and header rows 30. Body text is 14 points, small text and column titles 12, badges 11, headings 16, and formulas and paths 13 in a monospace font. Controls and badges have a corner radius of 4, panels and popups 6.
- **Fonts** are bundled, all under the SIL Open Font License and all variable fonts, so one file gives every weight (egui 0.37 sets the weight through variation coordinates: `FontTweak::coords` for a family, `RichText::variation` for one piece of text). Inter is the interface font, with a *medium* family at weight 560 for titles, badges and the current tab; Geist Mono is the font of formulas and paths (chosen to match Inter, and it has no coding ligatures, so a formula shows the characters typed), with egui's Hack after it. Source Serif 4 (serif), Oswald (condensed), Dancing Script (script) and Caveat (handwriting) are registered as named families. Behind each are egui's own fonts, for symbols and emoji, and the Phosphor icons. **The bundled text fonts are loaded without the characters of the private use area** (U+E000 to U+F8FF), where the icons are: Inter has 745 glyphs of its own there, which were drawn instead of the icons in text that is not in the icon font (the file dialog's, whose icons are plain text). Their character maps are rebuilt when the fonts are made (`style::without_private_use`, with `skrifa`, which egui reads fonts with); the files are unchanged, and the glyphs stay in the font. Putting the icon font first in each family would not do, since egui takes the line height of a family from its first font (the icons' is 14 points where Inter's is 16.9 at 14 points). Where they came from is in `assets/fonts/FONTS.md`.
- **Choosing a font.** The six typefaces can be chosen in two places. *View > Font* sets the typeface and size of the **data views** (the Data tree with its tabular pane, and the Raw view) for every tab of the workbook at once, from 10 to 28 points [Sans, 14 pt]; it is kept in the workbook (`view.json`), so the file opens in the font it was saved in. A **form** has no workbook font: each control has its own (see Forms). The type badges in the grid and the formulas take the chosen font too; under Sans, formulas and code stay in Geist Mono. The menus, bars, column titles and the formula bar stay in the interface font.

## Testing and CI

The project has automated tests at several levels, and **all of them run in a CI pipeline on Linux** with no manual steps. A developer on Windows runs the same default tests locally. Tests that need extra services (databases) or a display are opt-in locally and always on in CI.

**Principles**
- **Test the real thing.** Application-level tests drive the actual application code, including the evaluation thread and the RustPython engine, not mocks. The Python engine is real in every test above the unit level.
- **No sleeping.** The status bar's pending count is observable (see Evaluation and scheduling), and the application exposes "wait until idle" for tests. Tests wait for that condition with a timeout, never for a fixed delay.
- **Deterministic.** The clock and random numbers are injected, so `NOW` and `RAND` can be fixed. Fonts used in rendered tests are bundled. Tests use temporary directories and never touch the network except to local servers they start.
- **Every rule in this document gets a test**, and every fixed bug gets a regression test. Test names refer to the section of this document that they check.

**Levels**

1. **Unit tests** (`cargo test`, per crate). `cliotree-core`: `Value`, `TypeSpec`, JSON Schema and XSD lowering, validation, scalar-type checks, the XML mapping, inference, import and export. `cliotree-calc`: the dependency graph, evaluation order, cycle detection, error values and propagation, version tagging of results, the edit log, the trust hash.
2. **Conformance and fixture tests.**
   - *JSON Schema:* a selected part of the official JSON Schema Test Suite, vendored at a pinned version. Only cases for keywords in the v1 subset are run as pass/fail checks. For every excluded keyword there is a test that checks it is **rejected at load with an error naming it**, which is what this document requires.
   - *XSD:* a curated corpus of schemas and instances covering the subset, and a test for each excluded construct. The built-in meta-schemas are validated by loading them through the normal path.
   - *Workbooks:* `.clio` fixtures in the repository, one per file-format version, for upgrade tests, plus hostile files (zip paths with `..`, zip bombs, DTD entity expansion, very deep nesting, oversized input).
3. **Data-driven formula tests.** A case file (schema, data, formulas, expected values or error kinds) is loaded and checked, in a table-driven format that is easy to add to. This covers the Python semantics table, error mapping, `IFERROR` and `ISERROR` in both forms, `CONCAT`, `VALID`, syntax errors, and literal references.
4. **Property-based tests** (`proptest`).
   - Data round-trips through JSON and XML, and through save and load.
   - Saving twice gives identical bytes.
   - A random sequence of edits followed by undoing all of them restores the original state, and redo restores the final one.
   - A tree inferred from random data validates it, apart from the conflicts the inference reports.
5. **Python engine tests.** The error mapping table; the propagation rules for `ErrorValue`; module loading, including import cycles, failed modules, and `#NAME!` results; timeouts, with a tight loop that is cancelled and a long builtin call that is abandoned; and the **sandbox probes from the spike** kept as permanent regression tests (no `os`, `socket`, or file access reachable, including through `BuiltinImporter`).
6. **In-process UI tests.** The application's UI is written so that its top-level `update` function can be driven by `egui_kittest`, which runs egui headlessly and finds widgets through AccessKit, the way a screen reader would. This needs no display. Tests do what a user does: open a workbook, select a node, type `=...` into the formula bar and press Enter, wait until idle, and check the cell's text, error, and pending marker. Cases include the tabular view toggle from the context menu, undo and redo keys, the trust banner and untrusted mode, forms (field commits, button procedures), the code editor and the Immediate window, import and export dialogs, and the status bar. This is the main level for UI behaviour.
7. **Visual snapshot tests** (`egui_kittest` with its `snapshot` and `wgpu` features). Key screens are rendered and compared with stored images with a small tolerance. On Linux CI the rendering uses a software Vulkan driver (Mesa lavapipe), so no GPU is needed. They run as a separate job and fail only on a clear difference; differences are uploaded as artifacts. Snapshots start as advisory and become a gate once they are stable.
8. **End-to-end tests on the running application.** The real binary is started on Linux under a virtual display (`xvfb-run`) and driven through a **test control channel**: a loopback-only JSON command interface that exists only when the application is built with the `test-control` cargo feature, which release builds never enable. Commands include: open a workbook, select a node, enter text, press a key, read a cell's value, formula, error, and pending state, wait until idle, take a screenshot, and quit. Because the channel is compiled out of release builds, it adds no remote-control surface to the shipped product. A small number of tests, written as a Rust client against that channel, cover startup, open and save, edit-and-recalculate, and shutdown on the real windowing backend. Most behaviour is tested at level 6, which is faster and more stable.
9. **Data source tests.** SQLite runs everywhere. PostgreSQL and MariaDB run in CI against service containers. HTTP uses a mock server started by the test on a local port. Cases include grants (an ungranted call gives `#UNTRUSTED!`), read versus read-write enforcement, `#SOURCE!` errors, timeouts, oversize responses, and a check that a saved `.clio` file contains no secrets. These are skipped locally unless the matching environment variable is set.
10. **Security and robustness.** The hostile-file fixtures above; the sandbox probes; trust-hash tests (a change outside the application drops trust, a change inside keeps it); and **fuzzing** with `cargo-fuzz` on the parsers: JSON and XML import, zip reading, schema lowering, and formula parsing. Fuzzing runs on a nightly schedule and does not block merges; any crash found becomes a regression test.
11. **Performance checks.** Benchmarks for the cases measured in the spike (a formula over 10,000 items, 10,000 separate formulas, loading and saving a large workbook) run on a schedule and report trends. They are not merge gates, because shared CI machines are noisy; a very generous threshold in an ordinary test catches only gross regressions.

**The test-control protocol.** The channel used by level 8 listens on a loopback port chosen by the operating system, which the application writes to a file named by `CLIOTREE_TEST_PORT_FILE`, and it requires the token in `CLIOTREE_TEST_TOKEN` in every request. It speaks **JSON lines**: one request per line, `{"id": 1, "cmd": "...", "args": {...}}`, and one response per request, `{"id": 1, "ok": true, "result": ...}` or `{"id": 1, "ok": false, "error": "..."}`. A first `hello` request returns the protocol version.

| Command | Purpose |
|---|---|
| `open_workbook`, `new_workbook`, `save`, `save_as`, `close` | File operations. |
| `select` (a path) | Select a node, in the grid or the table. |
| `enter` (text), `key` (a chord), `menu` (a menu path), `context_menu` (a path and an item) | What a user types and clicks. |
| `view` (a name), `set_field` (a path and text), `click_button` (a label) | Switch the tab to the Data tree or a form, and do what a user does on a form. |
| `cell` (a path) | Returns the value, formula text, error, pending state, comment, hidden or filtered state, and validity. |
| `tree` (a path and a depth) | Returns a snapshot of a subtree. |
| `status` | Returns the status bar text, the pending count, and the abandoned-thread count. |
| `wait_idle` (a timeout) | Waits until nothing is pending. |
| `set_option`, `grant`, `trust` | Preferences, data source grants, and the trust decision, so tests can set up state without driving dialogs. |
| `screenshot` (a path) | Saves an image of the window. |
| `quit` | Exits cleanly. |

The same command set is implemented over the in-process harness used by level 6, so a scenario can be written once and run at either level.

**Selecting JSON Schema Test Suite cases.** The suite is vendored at a pinned commit, recorded in `vendor.lock` as a further item (a test-only one) when the suite is first added. A checked-in selection file lists the allowed keywords: `type`, `properties`, `required`, `items`, `minItems`, `maxItems`, `minimum`, `maximum`, `minLength`, `maxLength`, `pattern`, `enum`, local `$ref` and `$defs`, schema-valued `additionalProperties`, and `format` for `date` and `date-time`. A test group is run as pass or fail only if its schema, searched recursively, uses nothing outside that list. Every other group is run as a **must-reject** test: loading its schema has to fail with an error that names the excluded keyword. A group that is neither is listed in the selection file with the reason, so that nothing is skipped silently.

**Tests for auto-update and schema editing.** Switching on with zero, one, and two users; refusing a second binding while it is on; a file that breaks the rule opening with it treated as off; each of the four commands with its effect on the data and on formulas; shared-type confirmations; undo and redo of each as one entry; a later direct edit of the schema sheet having to be undone first; and the refusal while a schema-sheet cell edit is in progress.

**Pipeline** (GitHub Actions, since the repository is on GitHub)

The jobs run on a self-hosted GitHub Actions runner (label `cliotree`; see the README, "CI runner"), not on GitHub-hosted runners. That keeps the cost off GitHub's minutes allowance and keeps the cache local. It also means that the runner's machine must provide `git`, a C toolchain and `rustup`, and that later jobs needing a display (the snapshot tests) or containers (level 9) depend on what the runner's machine offers.

| Job | Runs | Blocks merge |
|---|---|---|
| Lint | `cargo fmt --check`, `cargo clippy -D warnings`, and `cargo deny` (licences, advisories) once its configuration is verified | yes |
| Vendor | `cargo xtask vendor fetch` and `verify` on Linux | yes |
| Test | `cargo test --workspace` on Linux: levels 1 to 6 | yes |
| Services | level 9 with PostgreSQL and MariaDB containers | yes |
| E2E | level 8 under `xvfb-run` | yes |
| Snapshots | level 7 with software rendering | advisory at first |
| Windows installer | an unsigned x64 MSI, cross-built on Linux, on pushes to main | advisory |
| Nightly | fuzzing, performance, `cargo audit` | no |

- The Rust toolchain is pinned in `rust-toolchain.toml` (1.97 or newer is required, as RustPython requires) and the dependency set is locked, including the RustPython git revision and the `ruff` fork (see Build and dependencies).
- Runs stay short because the runner is persistent: `target/` and `vendor/` stay in its workspace (the checkout is told not to clean them), and RustPython takes several minutes to build only the first time. `Swatinem/rust-cache` is not used, because its cleanup deletes `rustup` from `~/.cargo/bin` on a shared machine. A job on a throwaway runner would need a cache.
- On failure the job uploads logs, snapshot diffs, and screenshots as artifacts.
- **The Windows installer** is built on the Linux runner: `packaging/windows/build-msi.sh` cross-compiles the release application for `x86_64-pc-windows-msvc` with `cargo-xwin` (which downloads the Microsoft CRT and Windows SDK once, accepting their licence terms, into `~/.cache/cliotree-msi`) and packages it with `wixl` from msitools, from `packaging/windows/cliotree.wxs` (the WiX 3 dialect wixl reads). Nothing is installed system-wide, so the runner needs no root. The MSI installs `cliotree.exe` and the licence under Program Files, adds a Start Menu shortcut, and upgrades in place (`UpgradeCode` never changes; the version is the workspace version). The release exe is a GUI program (no console window); debug builds and the test control build keep the console. Not yet: code signing (SmartScreen will warn), an icon, a version resource in the exe, and the `.clio` file association (with the workbook layer). The job is advisory and uploads the MSI as the `windows-installer` artifact.
- Coverage is reported with `cargo llvm-cov` for information, not as a gate.
- Because development happens on Windows, a Windows job running levels 1 to 3 is added once the basic pipeline is stable. It exists to catch path, case-sensitivity, and line-ending differences, which this design has several rules about (tab names unique ignoring case, per-tab files).

## Build and dependencies

**Required Rust version.** The project requires **Rust 1.97 or newer**. This is a project requirement for every developer and for CI, not just a CI detail. It comes from RustPython and its `ruff` fork (see Python engine), and it is re-checked whenever they are upgraded.
- The workspace `Cargo.toml` declares `rust-version = "1.97"`, so Cargo itself refuses to build with an older compiler and says why.
- `rust-toolchain.toml` pins the exact toolchain used by developers and CI. It starts at 1.99.1, the version the spike was run with, and is raised deliberately, not automatically.
- The README states the requirement, and a developer on an older toolchain is told to update with `rustup update stable`.

**The vendor folder.** Dependencies that cannot come from crates.io as published (RustPython, and the `ruff` fork it needs) live in a `vendor/` folder at the root of the repository.
- **Not committed.** `vendor/` is in `.gitignore`. Its contents are downloaded, never stored in the repository.
- **Not cleared between builds.** An ordinary build, rebuild, or `cargo clean` leaves it alone, so a build does not download anything again.
- **Cleared by the project's `clean`.** The project's own clean command (`cargo xtask clean`) removes `vendor/` as well as the build output. After it, the next build fetches everything again.
- **Fetched on demand, before Cargo starts.** The workspace declares which vendor items it needs (`[workspace.metadata.cliotree] vendor = [...]` in the root `Cargo.toml`). Before `cargo xtask lint`, `test`, or `ci` runs Cargo, it checks that each of those items exists under `vendor/` and matches `vendor.lock`, and calls the **fetch script** for any that is missing or out of date.
- **Why not a build script.** The first design had a build script do the fetching. That cannot work: Cargo needs the manifest of every path dependency to exist before it runs any build script, so a build script can never create a path dependency of its own workspace. (This was confirmed by experiment: Cargo stops with `no matching package named ... found` before the build script starts.) The fetch therefore happens in `cargo xtask`, which is in a separate workspace and so runs on a fresh clone. A plain `cargo build` on a fresh clone, once the workspace depends on `vendor/`, needs one `cargo xtask vendor fetch` first, and the README says so.

**What is pinned.** A committed file, `vendor.lock`, lists each vendor item with its source URL and **exact commit hash**. The content is not committed, but its identity is, so every developer and CI build gets the same code.
- Items at first:
  - **RustPython** at commit `e5554e23abfbaee85508c32fc22e5074f88aebdd`, the revision the spike built and tested (version 0.6.1).
  - The **`ruff` fork** (`https://github.com/RustPython/ruff.git`) at commit `9290a8849542134d83f77e9360e7f0b93897fd93`, the revision that RustPython's own lock file names, with a sparse checkout of the crates it needs.
- The fetch script checks out that exact commit and verifies it against `vendor.lock`. A mismatch is an error.
- Each item gets a stamp file (`.complete`) holding the pinned hash. It is written only after the download and any build steps succeed, so an interrupted fetch is detected and redone. If `vendor.lock` changes, the stamp no longer matches and the item is fetched again.
- To upgrade, a developer runs `cargo xtask vendor update <item> <commit>`, which edits `vendor.lock` for review in the usual way.
- The URL in `vendor.lock` can point at a mirror if an upstream repository disappears.

**The format of `vendor.lock`.** A TOML file, one table per item:

```toml
version = 1

[[item]]
name   = "rustpython"
url    = "https://github.com/RustPython/RustPython"
rev    = "e5554e23abfbaee85508c32fc22e5074f88aebdd"   # full 40-character commit hash

[[item]]
name   = "ruff"
url    = "https://github.com/RustPython/ruff.git"
rev    = "9290a8849542134d83f77e9360e7f0b93897fd93"
sparse = ["crates/ruff_python_ast", "crates/ruff_python_parser", "crates/ruff_python_trivia",
          "crates/ruff_source_file", "crates/ruff_text_size"]
```

`name` is the directory under `vendor/`, `rev` must be a full commit hash (a branch or tag is rejected), and `sparse` is optional. The fetch script fails if the checked-out commit differs from `rev`.

**The `cargo xtask` commands.** The project's helper commands, all cross-platform:

| Command | Does |
|---|---|
| `cargo xtask clean` | Removes the build output and `vendor/`. |
| `cargo xtask vendor fetch` | Fetches any missing or out-of-date vendor item. |
| `cargo xtask vendor status` | Lists each item, its pinned revision, and whether `vendor/` matches it. |
| `cargo xtask vendor verify` | Checks every checked-out item against `vendor.lock`. |
| `cargo xtask vendor update <item> <rev>` | Changes a pin in `vendor.lock`, for review. |
| `cargo xtask lint` | Formatting and clippy (and `cargo deny` once its configuration is verified): the Lint job. |
| `cargo xtask test` | The default test levels: the Test job. |
| `cargo xtask e2e` | The end-to-end tests on the running application: under `xvfb-run` on Linux without a display, in a real window elsewhere. |
| `cargo xtask snapshots` | The visual snapshot tests (they need a graphics adapter). |
| `cargo xtask ci` | Everything the blocking CI jobs run, in order. |

**The fetch script is cross-platform.** It is a small Rust program in its own package (`tools/fetch-vendor`), so it runs the same on Windows, Linux, and in CI, with no shell scripting. It lives in its own workspace (`tools/`) with `cargo xtask`, which is what lets it run before `vendor/` exists, and the same code is available as a standalone `fetch-vendor` binary.

**Windows long paths.** The spike found that checking out the whole `ruff` repository fails on Windows because of very long test file names. The fetch script avoids the problem by **sparse checkout**: it fetches only the crates RustPython needs and none of the rest, and it sets git's `core.longpaths` as well. Nothing else about the layout depends on the platform.

**How Cargo uses it.** The workspace refers to the vendored sources by path (`vendor/rustpython/...`). All other dependencies come from crates.io in the usual way, locked by `Cargo.lock`.

**Patching a vendored item.** An item in `vendor.lock` may name a patch file (`patch = "vendor-patches/rustpython.patch"`, relative to the repository root). The fetch applies it with `git apply` after checking the commit, and the stamp records a fingerprint of the patch (and of the sparse list) together with the commit, so changing either fetches the item again. `vendor verify` checks that the patch is applied. The fetch also sets `core.autocrlf false`, so the files are the same bytes on every platform and the patch applies the same way. A patch file is kept with LF line endings by `.gitattributes`.
- **Why RustPython needs one.** RustPython names the `ruff` fork as a git dependency. Cargo checks such a dependency out itself, and on Windows the checkout fails on very long file names in the full repository (`path too long`, unless the operating system's long-path setting is on). A `[patch]` section does not help, because Cargo still reads the original source to resolve. The patch (4 lines in `Cargo.toml`) turns those four git dependencies into path dependencies on `vendor/ruff`, which is the sparse checkout. Cargo then never touches the ruff repository, and a build needs no network for it.
- **What the sparse list holds** for `ruff`: `ruff_python_ast`, `ruff_python_parser`, `ruff_python_trivia`, `ruff_source_file`, `ruff_text_size`, `ruff_unicode_names2` and `ruff_unicode_names2_generator` (the parser needs the last two).
- **Other pieces of the build.** `pymath`, a small crate RustPython takes from git, is still fetched by Cargo. `cliotree-calc` depends on `rustpython-vm` as well as on `rustpython`, because RustPython's derive macros write `rustpython_vm::` into the code they generate. Dependencies are built with optimisation in every profile (`[profile.dev.package."*"]`), as RustPython does in its own workspace: unoptimised, its evaluator keeps oversized native frames and the interpreter overflows the stack while it starts. `cargo fmt` is run without `--all` (that would also format the vendored crates).

**Offline and failure.** If a fetch fails, for example without network access, the build stops with a message that names the item, the URL, and the directory. The environment variable `CLIOTREE_VENDOR_DIR` can point at a copy of the vendor folder prepared elsewhere.

**CI.** The pipeline uses the same `cargo xtask` commands, so there is no separate CI procedure, and a separate *Vendor* job fetches and verifies every pinned item on Linux. On the persistent runner the `vendor/` folder simply stays in the workspace between runs, and a change to `vendor.lock` makes the next run fetch the item again (see Testing and CI).

**Security.** Fetching does not run anything from the downloaded repositories. Cargo does run the build scripts of dependencies when it builds them, as it does for any crate, which is why the pins are exact commits and changes to `vendor.lock` are reviewed.

## Decisions for implementation, and risks

**Decisions made now so that step 1 can start**
- **Snapshots.** The data tree uses reference-counted nodes with copy-on-write (`Arc`-based), so the evaluation thread takes a consistent snapshot by cloning the root, and the UI thread copies only the path it edits. This is settled in step 1 when `Value` is defined.
- **Dependency granularity.** Version 1 records dependencies at the node level (a read of an array or object depends on its structure and children). Path-prefix subscriptions are added only if the step 3 measurements show recalculation doing too much work.
- **Computed children.** An array item may carry its own formula only when the array itself is not computed, as specified under Formulas. Nothing more is needed unless real use shows otherwise.
- **Views and forms (design review of 2026-10-24).** A Data Tab has views: the Data tree, and named forms, of which Default always exists and is generated until customised. Customising is in place and copy-on-write. The form view has no formula bar; formulas appear on the property page of a control. Views belong to the tab, so there is no binding by name. A Report Tab is a different kind of tab.
- **Forms and XML.** Form field paths use element and attribute names. The `@attr` and `#text` mapping stays inside the XML adapter and is not shown to the user.
- **Button procedure power.** Procedures may write to other tabs through `ctx`, atomically, as specified under Forms. Writes to databases and HTTP endpoints are immediate and are not undone.

**Decisions made while building step 1** (JSON Schema lowering and validation; they refine the subset above and do not widen it)
- **`type` is required**, except on a schema that is only a `$ref` or only an `enum` (which is a string enumeration). In JSON Schema a keyword without a type applies to some instances and is ignored for others (`{"minimum": 1}` accepts the string `"x"`), which a typed tree cannot express. This is why most keyword-only groups of the JSON Schema Test Suite are listed as skipped, with that reason.
- **A keyword that does not apply to the schema's type is an error** (`minimum` on a string, `items` on an object), as are unknown keywords.
- **Excluded keywords are reported first.** Lowering scans the whole document for keywords outside the subset before it looks at structure, so `oneOf` is reported as `oneOf`, not as a missing `type` beside it.
- **`additionalProperties: false` is accepted**, as the explicit form of what objects already are. `true` is open content and is refused. A schema-valued `additionalProperties` makes a map and cannot sit beside `properties` or `required`.
- **`{"type": "object"}` with no `properties` is refused**: in JSON Schema it means any object, which the closed model cannot express. An empty record is written `"properties": {}` or `"additionalProperties": false`.
- **References.** `$ref` is `#` or `#/$defs/Name` (JSON pointer escapes apply); `$defs` is read at the root only. A `$ref` may carry `title` and `description` and nothing else. A chain of plain aliases resolves to the final type; aliases that only point at each other are an error. Every definition is lowered, used or not, so mistakes in it surface.
- **Root `$schema`** may be given if it names draft 2020-12, and nowhere else. `$comment`, `default`, `examples`, `deprecated`, and the other annotations are refused (only `title` and `description` are accepted), as are `$id` and `$anchor`.
- **Whole-number counts.** `minItems`, `maxLength` and the like accept `3` or `3.0`, never `-1` or `1.5`.
- **Patterns** are compiled by the `regex` crate, so look-ahead, look-behind and back-references are refused at load with an error naming `pattern`. JSON Schema specifies ECMA 262 regular expressions, so a schema from elsewhere may use features that are not available.
- **An integer field holds only integers.** Loaded data that has `3.0` in an `integer` field is flagged as invalid (kept, red outline), consistent with Scalar types; the suite's case "a float with zero fractional part is an integer" is skipped for that reason.
- **Validation** reports four kinds of problem (wrong kind, missing required field, undeclared field, broken constraint), each with the path of the node, and skips nodes that hold an error value. Closed objects mean that a suite case expecting extra properties to be valid passes when the only complaint is about undeclared fields; the test counts these separately.
- **Node ids** come from a process-wide counter and are never saved.
- **Floats** must be parsed with `serde_json`'s `float_roundtrip` feature, or a value changes in its last digit on a save and reload. The property test for JSON round trips found this.
- **Conformance** at this revision of the suite: 10 groups (55 cases) run as pass or fail, 308 groups are checked to be refused by name, and 66 groups plus one case are skipped with a stated reason each. The selection file fails the test if an entry is stale or a reason is unused.

**Decisions made while building step 2** (`cliotree-calc`; they settle details the sections above leave open)
- **The engine boundary.** *(Step 3 moved `check` into a separate `Syntax` trait and made the context shared; see the step 3 decisions.)* An `Engine` has two methods: `check(text)`, which only parses, and `eval(text, context)`, which runs. The `Context` it is given offers `read(tab, path)`, and every read is recorded as a dependency whether or not it finds a node. A read never fails, so an engine has nothing to catch or pass on; the calculation layer decides afterwards what a read meant. A failure is a `Failure` (an error kind and message, plus the engine's own traceback, kept beside the data and not in it). A formula that returns an error found in the data returns it as a value, which is how `=Orders.total` gives the same error.
- **Formula text has no leading `=`.** The calculation layer stores and evaluates the expression. Telling a formula from a literal, and the apostrophe rule, belong to the entry layer in the application.
- **Dependencies are by path prefix.** An edit at a path concerns every formula that read that path, a path above it, or a path below it. So a formula that reads a whole tab (`root`, or `JSONPATH` over everything) depends on every formula in that tab, including itself, and is circular with them. This is the node-level granularity chosen earlier; it is also why the cycle rule below needs no special case for arrays.
- **Evaluation works on a snapshot.** `Calc::snapshot()` shares the data and the formulas with the live workbook (the tree is copy-on-write), `Snapshot::evaluate(engine)` can run anywhere, and `Calc::apply(evaluation)` takes the results. A result is dropped, and its formula stays out of date, if an edit made after the snapshot touched anything the formula read or the formula's own node, or if it read a result that was dropped. The last 10,000 edits are kept for this; an evaluation older than that is dropped whole. `Calc::recalc()` does all of it on the calling thread. The thread and its messages are built with the application.
- **Order of evaluation.** Dependencies are found as formulas run, so a formula that reads a node an out-of-date formula is still to compute is thrown away and run again after that one. Its first run is made on the old values, and the run is not kept. To keep such reruns rare, formulas are first visited in an order guessed from what they read last time. The search for what to run next is kept in a vector, not on the call stack, so a chain of 20,000 formulas does not overflow it (the test does exactly that).
- **Cycles.** Every formula that is on a cycle gets `#CIRCULAR!`, whichever of them the search enters by; the search is a depth-first search in the manner of Tarjan's algorithm, so a formula that only reads a cycle and handles the error with `IFERROR` is not on it, and one that is read by a member and reads it back is. The message lists the formulas. Only reads made before the formula saw a value that is still out of date count as certain; a later read is a guess made on old values, and a formula reached only by a guess is given up again instead of joining a cycle. A cycle whose only link is such a guess is therefore judged on the next run. The property test (below) compares edit-by-edit recalculation with one calculation at the end, cycles and `IFERROR` included.
- **Checking a result.** The result is checked against the type at the formula's node and nothing is coerced: `None` leaves an optional node absent and is `#TYPE!` on a required one, an `int` is accepted for a number, a `float` is not accepted for an integer, a `bool` is accepted only for a boolean. A node the schema does not define gives `#REF!`. A missing object or array above the node is created empty; an array item can only be added at the end, otherwise the result is `#REF!`. An error's `origin` is the path of the node where it arose; the tab is named in the message (the core `ErrorValue` has no field for it yet).
- **Syntax errors** are found when the formula is entered: the node holds `#SYNTAX!` at once, the text stays, the formula is not run, and a full recalculation skips it.
- **What the calculation layer refuses.** A formula on a node the schema does not define; a formula on a node inside the result of another formula (the outermost such formula is named); a formula on a node that has formulas inside it, unless the caller asked to replace them (`Calc::set_formula_replacing`, which the window uses after its question, see "A formula over what is inside"); and any edit, removal or insertion inside a computed subtree. A literal written to a node with a formula replaces the formula. Formulas stay where they are when items are inserted or removed.
- **Stale and pending.** `Calc::cell(tab, path)` gives the node, the formula text, the error, the traceback, whether an evaluation is outstanding for it or for the formula that computes it, and which formula computes it (so the grid can draw it read-only).
- **Not yet built**, and where it goes: trust and untrusted mode (step 5), time budgets and `#TIMEOUT!` (step 3), volatile functions and an injected clock (step 5), the evaluation thread, its message protocol and "wait until idle" (step 4), the proxy objects and the Python error mapping (step 3). The stand-in engine understands only numbers, strings, references, `+ - * /`, comparisons and `SUM`, `IF`, `IFERROR`, `ISERROR`.
- **Tests.** 53 unit tests, including a property test that applies random edits to six formula cells and checks that recalculating after each edit gives the same result as making all the edits and recalculating once.

**Decisions made while building step 3** (the Python engine; they settle details the sections above leave open)
- **Two traits.** `Syntax` reads formula text and needs no interpreter, so it is used where a formula is entered, on any thread; the implementation parses with the `ruff` parser and rejects double-underscore names and attributes (a formula `().__class__` is `#SYNTAX!` with a message that says so). `Engine` runs formulas and is not `Send`, because an interpreter cannot move between threads; the evaluation thread makes its own. `Calc::new` takes the `Syntax`, and `recalc` takes an `&dyn Engine`.
- **A formula's context is shared, not borrowed.** The objects a formula works with (proxies) keep hold of it, so it is an `Rc`. The evaluator no longer asks the formula to wait: a read always returns the node, the reads are logged, and afterwards the log is checked for reads of nodes that out-of-date formulas still have to compute (the same rule as before, applied afterwards).
- **Shallow and deep reads.** A read is deep (the node and everything in it) or shallow (the node's own structure: that it exists, what kind it is, how many items, which fields). Moving through a proxy reads shallowly, and a plain value is read where it is. So `Orders.items[2].price` depends on that price, a count of items does not depend on their values, and a formula on one item can read another without being circular with the array. Returning a proxy, or `PLAIN` or `JSONPATH`, reads deeply. A shallow read still waits for a formula that computes the node itself or something above it.
- **What a proxy is.** A proxy stands for an array or an object. `.name` and `[key]` give the child: a plain Python value for a scalar, another proxy for a container, an `ErrorValue` for a node that holds an error. `Orders.items.price` on an array is the list of that field of every item. An object's attributes are only its fields (so a field may be called `items` or `keys`); `len()`, iteration (items of an array, keys of an object), slices and negative indexes work. A field that the schema declares and the data lacks reads as `None`; anything else that is missing is `AttributeError`, `KeyError` or `IndexError`, which is `#REF!`. Proxies are read-only.
- **`parent` and `root`** (and `this`) are available by those names. They read when first used, so that a formula that does not use `this` does not depend on its own node.
- **Errors in Python** are as the Errors inside Python section says. `ErrorValue` and `PropagatedError` are written in Python (the engine's prelude), `IFERROR`, `ISERROR` and `VALID` too. A formula's timeout is raised as `KeyboardInterrupt`, which is not an `Exception`, so `IFERROR` and `except Exception` do not catch it. `.exception` is `None` for now: the original exception is kept as the traceback text beside the cell, not as an object the formula can reach.
- **Names.** The tabs are available by name and are added and removed as tabs come and go; a name that is not defined also becomes a dependency, so adding a tab by that name runs the formula again. The modules `math`, `datetime`, `re`, `json`, `itertools`, `decimal`, `fractions`, `collections`, `functools`, `string` and `textwrap` are available without `import`. Removed from the builtins: `open`, `exec`, `eval`, `compile`, `__import__`, `__build_class__`, `input`, `breakpoint`, `help`, `exit`, `quit`, `globals`, `locals`, `vars`, `setattr`, `delattr`. `range` is replaced by a version that refuses a length above the limit (default 1,000,000).
- **Results** are converted strictly, as in Scalar types: `bool` is checked before `int`, an integer beyond 64 bits and NaN or infinity are `#VALUE!`, `list` and `tuple` become arrays, `dict` an object (a `None` value leaves the field out), a date or datetime becomes `Value::Date` or `Value::DateTime` (with its offset if it has one), and a proxy is read in full and copied with new node ids.
- **Time limit.** `PythonEngine::set_time_limit`. A thread waits for the deadline and sends the interpreter a signal, which the interpreter acts on between instructions; the signal is sent again every 25 ms until the formula stops, because the flag that tells an interpreter to look for signals is shared by every interpreter in the process and another one may clear it first (found as a hang when tests ran in parallel). A formula that makes one long call into the interpreter's own code is not stopped; abandoning it is the evaluation thread's job (step 4).
- **`JSONPATH(query, node)`** supports names, indexes, slices, wildcards, the descendant operator, unions, and filters with comparison, `&&`, `||`, `!`, parentheses and tests for existence; functions inside a filter and `$` inside a filter are refused with a message. It reads all of `node`, so a formula that searches its own tab is circular with the formulas in it; search another tab, or a part that has no formulas.
- **Probes kept as tests.** From inside a formula, `getattr` chains still reach the classes of the interpreter and its importer, as the spike found; the test shows that `find_spec` finds none of `os`, `posix`, `_socket`, `subprocess` or `nt`, that nineteen modules that touch the machine do not import, and that `io.open` fails.
- **Tests.** 109 in `cliotree-calc` (all the above, run through the real calculation layer with the real interpreter), and the performance test above.

**Decisions made while building step 4a** (undo and redo, the evaluation thread, the session)
- **The log lives in `Calc`.** Every edit method records what it needs to be reversed; `undo` and `redo` run an entry backwards or forwards through the same code, so they mark dependents out of date and bump the version like any other edit. An entry is a list of operations: a node replaced (the old and the new `Node`), a node added or removed (with its place among its parent's children), a formula changed. Removed and replaced subtrees are held by reference, and putting one back restores its `NodeId`. Entries refer to paths, not ids: in one linear history, an entry is only ever undone when the state is the one it was made in.
- **What a formula overwrote is put back.** A formula's results overwrite whatever the node held, and results are not logged. So `set_formula` keeps the node as it was, and undoing it puts that back; typing a literal over a formula keeps the formula, and undoing brings it back.
- **Items that move under a formula.** A formula belongs to a location, so when an insert or a removal shifts items, the item that arrives where a formula is gets overwritten by its result. The insert or removal remembers those items as they were, and undoing puts them back. (A property test of random edits found this: undoing everything did not restore the original.)
- **A formula does not add array items.** A formula on `items[5]` when the array has four items gives `#REF!`, where earlier a result at the end of an array added an item. It makes undo exact and means a stray item cannot appear from a computation. Objects and optional fields are still created (with their absent parents).
- **Entries.** `begin_entry` and `end_entry` make several edits one entry and nest; `set_value_merging` joins typing in one cell into one entry until `seal_history`; refused edits leave no entry; undo and redo are refused while an entry is being built. The history is bounded by a count (default 1,000) and a rough weight (5,000,000, counting a held node as one plus its direct children), oldest dropped first. The saved state is tracked by position, so undoing back to it clears `is_modified`, and an edit after undoing past it makes it unreachable.
- **Not in the log yet:** adding, removing, renaming and rebinding tabs, modules, and the other kinds of edit listed above, which arrive with the things they edit. Sorting and reversing a table are one replaced array each, and will need the same care for formulas on the items.
- **The evaluation thread** (`Evaluator`) takes a snapshot, runs it on a thread with a 64 MB stack that makes its own engine from a factory, and returns the evaluation; `Calc::apply` then drops what an edit overtook. The settings are the formula time limit (1 s), the pass limit (10 s: formulas not reached get `#TIMEOUT!`), the grace period (500 ms), and the maximum of abandoned threads (20).
- **Abandoning.** If a formula has run longer than its limit plus the grace period, the thread is given up: its node gets `#TIMEOUT!`, a fresh thread with a fresh interpreter takes over, and the old thread counts as abandoned until it ends. At the maximum, evaluation is suspended and starts again by itself when threads end. (Tested with a formula made of long calls into the interpreter's own code, which signals cannot stop.)
- **`Session`** joins a `Calc` and an `Evaluator`. The interface calls `tick` once per frame: it takes finished results and starts the next evaluation if formulas are out of date, and says whether anything changed. `status` gives the pending count, whether one is running, the abandoned count and whether evaluation is suspended, for the status bar; `wait_idle` is "wait until idle" for tests and for saving.
- **Tests.** 138 in `cliotree-calc` now: 20 of them for the history, two of which are property tests (undoing everything restores the original; redoing everything gives the final state), and 9 for the session.

**Decisions made while building step 4b** (the window)
- **Library and binary.** `cliotree-app` is a library (`ClioApp` with a `show(ui)` that draws one frame) and a small binary. The tests call `show` through `egui_kittest`, which runs egui without a display and finds widgets through AccessKit. It refuses a text field that has no accessible name, so every field is named (`Formula bar`, `Cell editor`, `Search functions`); that is also what a screen reader needs.
- **What the window is.** A menu (File, Edit with the undo and redo labels, View), the formula bar, the grid, the tabs of the workbook along the bottom, and a status bar with `Ready` or `Calculating... N pending`, the abandoned-thread notice, the counts of errors and invalid values, and `Modified`. An issues panel (View) lists the nodes that hold an error and the data that does not fit the schema; clicking one opens the tree to it. The window asks for another frame while something is calculating, and `Session::tick` takes the results once per frame, so the window never waits for Python.
- **The grid** has the columns Name, Type, Value and Formula, draws only the rows on screen, and is laid out from the schema (`rows.rs`): every node the schema defines has a row, in declared order, whether or not it has data; an absent optional field is an empty cell that can be filled, a missing required one reads `(missing)` and is outlined; content the schema does not define comes after, greyed and marked `unrecognised`. Only the rows of open nodes are made, and they are made again only when the workbook's `revision` or the open nodes change. (`Calc::revision` counts every change, including results taken from an evaluation; `version`, which the stale-result rule uses, counts only edits.) Values are shown in Python's canonical form: `True`, `2.0`, `[3 items]`, dates in ISO form.
- **Marks on a cell.** An error shows in red with its message and traceback on hover; invalid data is kept and drawn with a red outline; a cell with a formula or inside a formula's result has a tinted background, and a node inside a result says `computed by` and the formula's name in the Formula column; a cell that is waiting for an evaluation shows `…` beside its last value.
- **Entering.** The formula bar and the cell edit the same text. Clicking in the bar, pressing F2, double-clicking a value, or just typing on a selected cell starts editing (typing replaces the content, as in Excel). Enter enters, Esc cancels, and selecting another cell enters what was typed first. A refused entry keeps the text, shows the reason under the bar, and does not move the selection. A boolean is a checkbox and a choice from an enumeration is a drop-down, entered at once. Delete clears the cell. A cell inside a formula's result is read-only, and the reason names the formula.
- **Entry rules** are in `cliotree-calc` (`entry.rs`) and tested there: `=` starts a formula; on a text node a single leading apostrophe is removed (so `'=total` is the text `=total`); the bar shows text that starts with `=` or an apostrophe with an apostrophe in front, so that entering what the bar shows changes nothing; a literal is read as the node's type and checked against its constraints before it is accepted; an empty entry clears a node (a required one then reads as missing; an item of an array cannot be left empty, except a text item, which becomes empty text).
- **Name completion** (`python::completion`) works from the schema: after a tab name and a dot it offers the fields, through the path (`Orders.items[0].`), the fields of the items on an array, and `this`, `parent` and `root`; otherwise tab names, the catalogue of functions, and the standard library modules. It is not offered inside a string, for a field that cannot be written as an attribute, or for a map. Arrows and Tab or Enter choose, Esc dismisses until the text changes.
- **Insert Function** lists the catalogue (`python::catalog`): the error functions, `PLAIN`, `JSONPATH`, the useful Python builtins and the exposed modules, with a signature and one line each, a search box, and Insert at the cursor. The Excel-named functions and the workbook's modules join it in step 5.
- **Structure commands** on the context menu: add an item to an array, insert an item above, delete an item, a map entry or an optional field. A new item has its required fields filled with defaults (the lower bound of a range, the first choice of an enumeration). Each is one entry in the history.
- **Clicking does not take keyboard focus** (`Sense::CLICK`, not `Sense::click()`), because a focused widget would take the arrow keys for moving focus. The arrows move the selection and open and close nodes when no text field has the keyboard.
- **A bug the tests found.** A table cell's layout was top-down, so the indentation of a name spread downwards and clicks missed the label. The table now sets a left-to-right cell layout.
- **For a picture** of the window, `cargo test -p cliotree-app --test ui picture -- --ignored` renders it to a file (set `CLIOTREE_PICTURE`); it needs a graphics adapter. The visual snapshot tests of step 4e build on it.
- **Tests.** 26 in the library (rows, status words, editing, completion, Insert Function) and 12 through the window; 159 in `cliotree-calc` with the entry rules and the completion.

**Decisions made while building step 4c** (the tabular view)
- **The table is a pane under the tree, not drawn in place of the array's rows.** The tree grid is one virtualised table with four fixed columns, and a table with the item's own columns cannot share it. A pane under the tree (resizable, one table at a time, the one the selection is in, or the last one chosen) keeps both virtualised and keeps the formula bar, selection and editing the same. The cost is that the table is not at the array's place in the tree; the array's row stays there with its type, and the context menu of that row switches the table on and off. If this proves awkward it can be revisited with a custom layout.
- **Cells are the tree's cells.** A table cell is built as a `Row` and drawn by the same `value_column` code as a tree row, so tint, outline, error hover, pending marker, drop-downs, check boxes and in-cell editing are the same code, and the selection is the cell's node path, so the formula bar works unchanged. Up, down, left and right move among the cells that are shown; F2, Delete and typing work as in the tree.
- **Columns** (`table.rs`) are the scalar fields of the item type in declared order, with objects flattened into dotted names (a type that contains itself is cut off) and arrays and maps as summary columns. A summary column cannot be sorted or filtered. Drilling in: double-clicking a summary cell opens the node in the tree above, where the array's row shows the item and the fields that were opened and nothing else (the other items are only in the table); switching the table on or off closes what was opened.
- **Sorting is a reorder of the array** (`Calc::reorder`): one history entry holding the array before and after, so undo is exact, node identities travel with the items, formulas stay at their places and are calculated again against what is there (tested, including undo). Move row, reverse and sort all use it. It is refused for an array that is computed by a formula, or inside one.
- **Python's ordering is done in Rust**, with the same classes and messages, so that sorting needs no trust and no engine: numbers and booleans order together, text by code point, dates and date-times each among themselves (a date with a time zone and one without cannot be compared, as in Python). Anything else, an absent value, an error value, an array, or a mix of classes, refuses the sort with Python's wording (`'<' not supported between instances of 'NoneType' and 'float'`). The rows named are those whose class differs from the first row that can be ordered. Descending is a stable sort with the order reversed, not the ascending result turned round. **Show these rows** sets a filter on the values the offending rows hold. The column that was last clicked and its direction are remembered, but not shown, so that a second click reverses.
- **Filters** are a list of values and a condition, both must hold, one filter per column, all columns must pass. The operands are read as the column's type; the dialog refuses an operand that is not one (`a whole number is expected here`), and a filter that has become invalid is ignored rather than hiding everything. Blank is an absent value or empty text; errors have their own entry. A row that was added or edited stays shown until a filter changes or **Reapply filter** is pressed. Filters are re-evaluated whenever the data changes, including by recalculation (tested).
- **Hiding.** Rows are hidden by the identity of the item, so a hidden row stays hidden when it moves, whether by a sort, a reverse or a move. Columns are hidden by name. The toolbar shows `12 of 340 rows (3 hidden, 5 filtered)`, the **Hidden** menu lists what was hidden by hand with Show for each and Show all, and where something is hidden between two shown neighbours the header or row label starts with `..` (a thin marker like Excel's needs a custom header). If the selected row becomes hidden, the selection moves to the nearest shown row.
- **View state is not in the workbook yet.** Tabular on or off, filters and hiding live in memory for the session, are not undoable, and are keyed by node identity; saving them in the tab's overlay (by path and field name, as designed) comes with the workbook layer.
- **Not done in this step, and why.** Copy and paste of ranges as tab-separated text (needs the clipboard and a rectangle selection, so it goes with the selection work); hiding a node in the tree view with its `(3 hidden)` count; dragging a column to reorder the fields (it is a schema edit, so it is step 4d); the funnel on a filtered header is a small triangle, not Excel's funnel.
- **Tests.** 50 in the library (of which 10 for the columns, ordering, filters and visibility in `table.rs`, 13 through the app for the commands), 17 through the window, and 4 new in `cliotree-calc` for `reorder`.

**Decisions made while building step 4d** (schema tabs, auto-update, field commands)
- **There was no schema tab before this step, so it is built here.** `Calc` now knows three kinds of tab: one that was handed a type directly (kept for tests and for the stand-in until the workbook layer), a **schema tab** (its data is a schema document, described by the bundled meta-schema), and a tab **bound** to a schema tab. Whenever a schema tab changes, by an edit, an undo or a redo, the tabs bound to it take the newly lowered type; a document that does not lower is reported (`Calc::schema_error`, shown in the bar above the tab) and leaves them with the type they had. This is done in `Calc::changed`, so there is no path that forgets it.
- **`builtin:jsonschema`** (`cliotree-core/src/metaschema.rs`) is the meta-schema, written in the subset and lowered like any schema. A schema that validates against it need not lower (the meta-schema cannot say that `required` names real properties, or that `type: array` needs `items`), and lowering stays the authority, as the design says. Two approximations: `additionalProperties` is a schema (the `false` form is not offered), and `$ref` is any string. The XSD meta-schema came with step 6.
- **A field command is an edit of the schema document together with the edits it causes**, recorded as one entry (`Calc::begin_entry`). It changes the object type's schema node in one replacement (so the tabs never see a half-changed type), then the data, then the formulas. Undo runs the same operations backwards, so the schema comes back before the data does. The type is found through the source pointer that lowering keeps on each type (`#/$defs/Address`), so a type shared through `$ref` is changed once and in every place it is used; `Calc::field_places` lists those places (`Orders.billing`, `Orders.items[]`) for the confirmation, and the data objects of the type, found by walking the data with the type.
- **What each command does, as built.** *Reorder* rewrites the keys of every object in the new order and keeps the value nodes (their identities). *Add* appends the field to `properties` (and to `required` if asked) and touches no data. *Rename* renames the key in `properties`, `required` and every object, keeping the value nodes; **a formula on the field (or inside it) moves to the new name** and is evaluated again; formulas that read the old name are not rewritten. *Delete* removes the formulas on the field first, then the values, then the field; the dialog states how many values and formulas go. A record cannot lose its last field.
- **Refused before anything changes** (`check_objects_free`): an object of the type that a formula computes, or that is inside a formula's result. The commands also need a tab that is bound, auto-update on, and a schema that lowers; the reason is given in the tooltip of the unavailable menu item and names the tab (`switch on auto-update on Orders_schema`).
- **Auto-update** (`Calc::set_auto_update`) can be switched on only with exactly one user, is an undoable entry, and `Calc::bind_schema` refuses a second tab while it is on. The bar above a schema tab has the checkbox and `Used by: Orders`. **Not done:** storing the setting in the manifest, and a file that breaks the rule opening with it treated as off, because there are no files yet; there is also no way yet to bind or rebind a tab from the window (tab management), only through `bind_schema`.
- **Where the commands are.** The context menu of an object row, of an array row (which adds to the item type) and of a field row has *Add field...*, *Rename field...* and *Delete field...*, and so has the menu of a column header, where *Add field...* adds to the item type. They are shown on every tab that has a schema tab and are unavailable, with the reason, when they cannot be used. **Dragging a column header** onto another moves the field there (the dragged field takes the target's place; a thin line shows where) among the fields of the same record only; a dialog is shown only if the type is shared, because moving is cheap to undo. Rename and delete follow the selection, the open nodes, hidden columns, filters and the remembered sort to the new name (columns are paired by position, since a rename keeps their number and order).
- **Not done in this step, and why.** *Add field* asks element or attribute on an XML tab and reordering keeps the two apart (step 6); undoing a rename gives the field its old name again but the hidden, filter and sort state of the column keeps the new one, because view state is not undoable; the refusal while a schema-tab cell edit is in progress is implemented (`schema_edit_allowed`) but cannot happen from the window yet, because switching tabs cancels an edit; the sample workbook now has a schema tab for each of its tabs, after the data tabs.
- **Tests.** 12 in `cliotree-calc` (binding, relowering, auto-update rules and undo, each command and its undo, shared types, refusal, undo order after a direct edit of the schema tab), 2 for the meta-schema in `cliotree-core`, 8 through the app without a window, and 4 through the window (the bar, unavailable items, rename from a column header, delete with its confirmation). The stand-in engine reads a name that is gone as the item that held it, so the `#REF!` kind of a formula that read a renamed field is asserted only as an error until the Python engine is used in that test.

**Decisions made while building step 5a** (the Excel-named functions)
- **`cliotree-std` owns them.** It holds the Python source (`functions.py`, run by the engine in the namespace of its prelude, so it can use `ErrorValue`, `Node` and `PLAIN`), the list of names, and the description of each for the Insert Function dialog and for name completion. `Function` and `Group` moved there from `cliotree-calc`, which re-exports them and adds its own entries after these. The groups are Math, Logic, Lookup and lists, Text, Errors, Data, Python and Standard library modules.
- **Nothing is turned into another kind, and nothing is skipped.** The functions follow the rules of the semantics table. `SUM` and `AVERAGE` of text are `#TYPE!`; `AVERAGE` of nothing is `#DIV/0!`; `MIN` and `MAX` of nothing are `#VALUE!` unless `default=` is given; and an `ErrorValue` among the elements is raised by every aggregate, `COUNT` included, so that no function hides a bad item.
- **Arguments are flattened one level.** A list, a tuple or an array is opened; text, a dict and any other value count as one element. So `SUM(Orders.items.price, 5, [1, 2])` works. An object is not opened (`SUM(Orders.by_name)` is an error, not the sum of its keys).
- **`COUNT` counts the elements that are not `None`**, which is how an absent optional field counts as nothing; it is not Excel's count of numbers.
- **`IF(condition, then, otherwise=None)`** works out both branches before the call. The plain `a if c else b` works out one; the description says so.
- **`VLOOKUP(key, items, key_field, result_field)`** takes field names, and raises `KeyError` (`#REF!`) when no item matches. **`FILTER(items, condition)`** takes a function of one item or a list of flags of the same length (`#VALUE!` if the lengths differ). **`SORT(items, key=None, reverse=False)`** takes a function or the name of a field. **`UNIQUE(items)`** keeps the first of each, and compares objects and lists by what is in them. All four return lists.
- **`CONCAT(*arrays)`** is list concatenation, as specified: lists, tuples and array proxies, and `#TYPE!` for anything else, an object included. Array proxies tell what they are through a new `__kind__()` method.
- **`TEXTJOIN(delimiter, *values)`** joins text only; a number among the values is `#TYPE!` (use `TEXT` or an f-string). **`TEXT(value, spec='')`** is `format()`, a Python format spec, not an Excel format code.
- **`NA()`** is the only source of `#N/A`: it raises `NotAvailable`, which the engine maps to the new kind. `IFERROR` catches it like any other error.
- **Not done in this part, and why.** `XMLPATH` came with step 6. The reserved-names checks (a tab or a function that clashes with these names) come with the modules, in 5b.
- **Tests.** 15 in `cliotree-calc` (`python/tests_std.rs`: each function, its error cases, and that an error among the items is raised by every aggregate), 3 in `cliotree-std`, and one more window test for the Insert Function dialog (the list is long now, so the existing test searches for its function).

**Found by running the real window on Windows (after step 4e)**
- **A window dragged between monitors of different scale grew.** With a 125% monitor and a 100% one, each round trip made the window about 1.25 times larger, and the scale flipped every frame while the window straddled both. With both at 125% it did not happen, so the cause is the mixed scale, and not the layout or the minimum size (removing the 640 by 400 minimum did not stop it). It looks like Windows and winit disagreeing about the size on a scale change; this has not been checked in winit's source or reported to it.
- **The guard** (`keep_size_across_monitors` in `lib.rs`) remembers the window's size in points from before a change of scale, and for one second after the change puts the window back to it if it has moved by more than 1.5 points. It does nothing for a maximised or full-screen window. It stopped the growing in the owner's test. **Known flaw:** the grip on the title bar slips a little while the window is dragged across, because the guard resizes the window under the pointer.
- **`CLIOTREE_LOG_WINDOW`**, when set, prints the scale and size of the window to standard error each time they change, and each correction the guard makes. It is how this was found.
- **To revisit** if winit fixes this, or if the slipping bothers: correct the size once when the drag ends instead of during it.

**Decisions made while building step 5b** (workbook modules)
- **A module is a tab that has no data, as far as dependencies go.** A formula that mentions a module, or a function one defines, has read the "tab" of the module's name, and editing the module is an edit of it. So the edit log and the index of readers that already existed do all the work: exactly the formulas that used the module are out of date (`editing_a_module_makes_exactly_the_formulas_that_used_it_out_of_date`), and a result computed from an older generation is dropped like one that an edit overtook. A module and a tab never share a name, so the two cannot be confused. What a formula mentions is found by scanning its text for names (strings and comments included), which can only find too many.
- **Modules use each other transitively.** Editing a module also makes out of date, and loads again, every module that imports it or mentions it or one of its functions, and through them the formulas that use those. Importers have to be loaded again because `from Base import helper` copies the function.
- **`Calc` keeps the modules** (`add_module`, `set_module_source`, `remove_module`, `rename_module`, `module_status`, `module_issues`, `pending_modules`, and so on): their sources, a generation for each change, what loading each came to (`Pending`, `Loaded`, `Failed(message)`), and what each source says about itself (its top-level imports and functions, from the `Syntax` trait, parsed without running anything). A source edit is one undoable entry ("Edit module X"); adding, removing and renaming are not undoable, like the same operations on tabs. Rapid typing is not merged yet, because there is no editor to type in.
- **Loading is the engine's, between evaluations.** The snapshot carries the modules (`ModuleSpec`: name, source, generation, imports, functions, and a reason if the workbook already knows the module cannot load: a syntax error, or an import cycle named as `A -> B -> A`). `Engine::sync_modules` runs at the start of every evaluation, before any formula, so a reload never happens during one; the evaluation returns a report for every module, and a report for a generation that has since been replaced is ignored. A module that no formula uses is still loaded, because the session starts an evaluation when a module is `Pending`. `Session::is_idle` waits for that too.
- **One flat namespace, as designed.** The engine's namespace is now a single dictionary: the globals of every formula, and also its own `__builtins__` and the builtins of every module. A module therefore finds a tab or another module's function by name when it is called, even one added after the module loaded, and the read is a dependency of the formula that is running (`a_tab_added_after_the_module_loaded_is_found_when_the_function_is_called`).
- **`__import__` is native.** It is an object of a class defined in Rust (no Python globals to reach), put in the namespace. `import` inside a module serves the workbook's own modules (in dependency order; a failed one raises `ImportError` saying so) and the exposed standard library modules, which are already loaded, and refuses everything else. Dotted names are refused too, so `import collections.abc` fails; only the names in the list are allowed. It cannot go through `vm.import`, which asks the frame's `__import__` and so the replacement again (this overflowed the stack when first tried). A formula can not name `__import__` because the syntax check rejects it, so the replacement being in the namespace widens nothing.
- **Failure.** A module that does not parse, raises at load, imports something it may not, is on a cycle, runs out of time (the formula time limit applies to loading), or takes a name that is in use, is `Failed` with a message that says where (the line, for an exception). Its names are removed, and a formula that uses one of its functions shows `#NAME!` with "f comes from module M, which failed to load: ...", which is why the functions a module declares are known from its source even when it did not run. Double-underscore access in a module is refused as in a formula.
- **Names** (`names.rs`). One list of the names the engine holds: Python keywords and builtins, the special names, every function of `cliotree-std` and of the prelude, the exposed standard library modules, and, for tabs, modules and functions, anything starting with an underscore or `cliotree`. `names::problem(name, subject)` gives the reason a name cannot be used, and is applied to module names (a module name must also differ from every module and tab, ignoring case). **A test lists the builtins of the interpreter and requires each to be reserved**, and it found three newer than the list (`frozendict`, `sentinel`, `ImportCycleError`), so the list is checked, not remembered.
- **A function may not take any name that is in use**: a built-in name, a tab, another module's function or a module. The module loaded later fails, and the message names both (`function vat in module Q clashes with function vat in module P`); modules load in display order, so the first keeps the name. A tab never takes the place of a name the engine holds or a module provides either: it is not published, and formulas see the other thing.
- **Name completion offers the workbook's modules** (`Tax.`) **and their functions** (`vat(`, and after `Tax.`). The signature is not shown, because only the names are known without running the source. The status bar shows "N modules failed" and the issues panel lists each failure.
- **Not done in this part, and why.**
  - **The code editor** (project explorer, editor panes, procedure box, *Compile*, the Immediate window, *Insert > Module*, export and import of `.py` files) is a window of its own, and has no workbook layer to open modules from yet.
  - **Storing modules** in `modules/<name>.py`, and their order in the manifest, wait for the workbook layer.
  - **Trust.** Done in 5c: modules are not loaded while the workbook is not trusted.
  - **Tab names are not checked** against the same rules when a tab is added, because `names::problem` is new and tabs such as "Orders schema" were made before it. It is applied when tabs can be created and renamed in the window (the workbook layer), and a file that breaks the rules is to open with the problem flagged, as the design says.
  - **Merging rapid typing** in the undo history waits for the editor.
- **Tests.** 24 in `cliotree-calc` (`python/tests_modules.rs`: availability, imports and reloading, cycles, import limits, failures, clashes, names, undo, generations, completion), 2 for names and identifiers, 1 for reading a module, and 1 window test for the status bar and the issues panel.

**Decisions made while building step 5c** (trust)
- **What the digest covers** (`trust.rs`, `Calc::fingerprint`): the text of every formula (by tab and path), the source of every module, and the order of the modules, since the order decides who keeps a name. It is a SHA-256 over a canonical serialisation: the items sorted by name, each as its length, its name and its own digest, behind a format label so that another version of the format never matches. Data, view state, the order of tabs and a formula's stored result are not in it. Formulas that do not parse are in it, because fixing one makes it executable. Button procedure names, the expressions of controls, report expressions and workbook settings join it when those exist (steps 7 and later); the item list is the one place to add them.
- **A digest for each item as well as for the whole.** `Fingerprint` keeps `formula Orders!items[0].total`, `module Tax` and `order of modules` with a digest each. That is what lets the banner list what changed, as the design asks, without keeping the old text in the user's configuration.
- **The record** (`TrustStore`): per workbook id, the fingerprint it was trusted with. `decide(id, fingerprint)` answers `Trusted` (id and digest match), `Unknown` (no such id: a new file, or one from elsewhere) or `Changed(list)` (the id is known and the digest is not, with each item `Added`, `Edited` or `Removed`). An id copied into another file does nothing, because the digest has to match too. `update` is what an edit made inside the application does for a workbook that is trusted, and does nothing for one that is not recorded, so editing never turns an untrusted workbook into a trusted one. `carry` is Save As (the copy gets a new id and the trust of the original). `revoke` and `ids` serve the list in the settings. Undoing an edit gives back the digest it had, so undo and redo keep trust without a rule of their own (`undo_returns_to_the_digest_it_had`).
- **The state is `Calc::is_trusted`, and a workbook made in the application is trusted.** The layer that opens files will call `set_trusted(false)` for `Unknown` and `Changed`; nothing does yet because nothing opens files.
- **Untrusted mode is decided in one place: the snapshot.** An untrusted `Calc` hands the evaluator no formulas and no modules, so nothing can run on any thread and no code path has to remember to ask. `pending()` is then zero and the session is idle; what is out of date is counted by `stale()` instead. Formulas can still be typed, stored and edited (parsing runs nothing), data edits still work, and everything that depends on an edit is marked out of date, which is what *stale* means.
- **Modules.** While untrusted their status is `ModuleStatus::Untrusted` (not a failure, so it is not counted or listed as one), they are not loaded, and their source can still be shown and edited. **Trusting** (`set_trusted(true)`) gives every module a new generation, so the engine loads it again whatever it held from before, and makes every formula out of date, as opening a trusted workbook does. Setting the state a workbook already has does nothing.
- **The window.** A banner under the menu says what trusting allows, lists what changed when the file was trusted before and has changed, and offers *Trust this version* and *Continue read-only*. The second puts the banner away; the status bar keeps saying *Not trusted* (with the number of stale formulas), because the state stays. A formula cell shows the value it was stored with and a `#UNTRUSTED!` badge, greyed when something it uses has changed since (the tooltip says which). The badge is on the cell, not in it: the stored value is not replaced by an error, so reading the data does not need trust.
- **Entering a formula prompts for trust** as the design says, with the banner rather than a dialog: the formula is stored unevaluated, the notice under the formula bar says so, and the banner comes back if it had been put away. Refusing is carrying on, and the text stays. (A modal question would block typing; the banner asks the same thing and keeps the work.)
- **Not done in this part, and why.**
  - **Reading and writing the record**, and the workbook id in the file: the record lives in the user's configuration directory and the id in the manifest; both wait for the preferences and the workbook layer. `TrustStore` is in memory and has no file format yet. The list of trusted workbooks and *Revoke* in the settings wait for the settings dialog.
  - **Opening a file** is where `decide` is called and `set_trusted` gets its answer, with the reasons in the banner.
  - **What does not exist yet and will be disabled when it does:** form buttons and control expressions (step 7), the Immediate window and Compile (the code editor), report placeholders (reports are deferred).
  - **Data source grants** (step 6b) are separate from trust: trusting a workbook grants no source.
- **Tests.** 15 in `cliotree-calc` (`python/tests_trust.rs`: what the digest covers and ignores, order, undo, the record's three answers and the list of changes, update, carry and revoke, untrusted mode running nothing and keeping stored values, stale cells, trusting calculating what waited, modules not loading and loading again), 1 in the application for the wording, and 4 window tests (banner and badges, continuing read-only, editing data while untrusted, entering a formula while untrusted). The `trust` control command is used by them.

**Decisions made while building step 6** (XSD, the XML adapter, `XMLPATH`)
- **The XML layer** (`cliotree-core/src/xmltree.rs`) reads text into a tree of elements with `quick-xml` underneath and writes it back by hand. It keeps the declaration, prefixes and namespace declarations, attribute order, element order and comments; it drops processing instructions and the document type declaration with a warning; CDATA becomes text. Only the five predefined entities and character references are understood, so an entity declared in a DTD is an error (it is not expanded, and nothing external is fetched). Elements nested deeper than 128 are refused, and the tree is built without recursion, so depth cannot overflow the stack. The text arrives already decoded: checking the declared encoding belongs to the layer that reads files.
- **How XML maps onto the tree** (`xsd.rs` for the types, `xml.rs` for the data), as the data-tree section says: an attribute is the field `@name`, the text of an element that has attributes is `#text`, a child element is a field named after it, and an element that may repeat is an array, even when only one occurrence is there. An element of a simple type with no attributes is just its value. Fields are in the order of the schema (attributes first, then `#text`, then the elements), whatever the order in the file. **A path to such a field is written in Python's subscript form**, as every key that is not an identifier already was: `Orders.line[0]["@id"]`, `price["#text"]`. A formula can sit on an attribute like on any other node.
- **Invalid data is kept, as for JSON.** Text that does not fit its type stays a string and validation flags it (`two` in an integer element, `soon` in a date); an attribute or element the schema does not define is kept under its own name (a repeated unknown element as an array, simple values as strings) and flagged as undeclared; a missing required one is flagged. Text is read as XML spells it: booleans `true false 1 0`, numbers with `INF -INF NaN` and not Rust's `inf` or `infinity`, dates exactly `yyyy-mm-dd`, date-times with an offset (kept) or without (naive). Text is kept exactly, including its whitespace.
- **Comments.** A comment before an element is that node's comment (several are joined with a line break), and the comment before the root is the root node's. `Node` now carries an optional comment; editing a value keeps it, it moves with the node, and formulas cannot see it. Comments after the root are kept with the document (`XmlDocument.after`). **Not kept, and reported as a warning on reading:** a comment at the end of an element, and a comment next to text; the design promised these a place, and they get one with the window for comments. **Design correction:** an attribute cannot have a comment, because XML has no place to write one (a comment cannot sit inside a tag), so only elements carry comments.
- **What a document says about itself** is `XmlDocument`: the declaration, the root's prefix and namespace declarations, and the comments after the root. A tab keeps it beside its data (`Calc::xml_document`, `set_xml_document`) so that it is written the way it was read. A new tab gets a UTF-8 declaration, and a new XSD starts with the prefix `xs` bound (`xsd::default_document`), which the `type="xs:string"` of its declarations rely on.
- **Writing.** An errored node, and a null, is absent. Dates and date-times are written in their lexical forms; floats in Rust's shortest round-trip spelling (so `24.0` is `24`, which is a valid `decimal` and `double`). Pretty output indents by two spaces and writes an element that has text on one line, so text is never changed by indentation.
- **The XSD subset as built** (`xsd.rs`), within the design's table. **One global `xs:element`**, the root; the other global declarations are named types, and `ref` may name the root (the way a folder holds folders). **One namespace at most**: with a `targetNamespace` the root must be in it (checked on reading), local elements are matched by their local name, and `elementFormDefault` says whether they are written in the namespace. A document with no prefix of its own for an unqualified schema is written with the prefix `tns`, so the unqualified local elements do not fall into a default namespace. `attributeFormDefault` must be `unqualified`. **Built-in types**: string-like (`string`, `token`, `normalizedString`, `anyURI`, `NCName`, `Name`, `ID`, `language`, `NMTOKEN`), `boolean`, integers (`integer`, `int`, `long`, `short`, `byte`, the `unsigned...` ones, and `nonNegativeInteger`, `positiveInteger`, `nonPositiveInteger`, `negativeInteger`, which carry their bound), `decimal`, `double`, `float`, `date`, `dateTime`; `time`, `duration`, `anyType`, binary types and the rest are refused by name. **Facets**: `enumeration` (strings only), `pattern`, `minInclusive`, `maxInclusive`, `minLength`, `maxLength`; `length`, `totalDigits`, `fractionDigits`, `whiteSpace` and the exclusive bounds are refused. A pattern is anchored at both ends as XSD requires, and several `xs:pattern` facets in one restriction are alternatives. A restriction of a restriction can only tighten a bound or a length and cannot add a pattern to one that has it. **Occurrence**: `minOccurs`/`maxOccurs` on an element make an array (`minOccurs="2" maxOccurs="5"` is an array of 2 to 5; `minOccurs="0"` makes the field optional); on a `sequence` they must be 1. **`#text` is never required**, since an empty element is a valid empty string. Documentation in an `xs:annotation` becomes the description of the type it is in; `appinfo` is refused. Every unknown element or attribute, and every excluded one (`choice`, `all`, `any`, `group`, `complexContent`, `extension` of a complex type, `nillable`, `default`, `fixed`, `mixed`, `key`, `import`, `list`, `union`, ...), fails with its name, where it was written, and why.
- **`builtin:xsd`** (`metaschema::xsd_meta`) is an XSD, written in the subset and lowered like any schema, with the XML Schema namespace as its target and `xs:` for both its own types and the built-ins. A name in that namespace is one of its own types if the schema declares such a type, and a built-in otherwise; that rule is only for this one case. It describes the elements and attributes the subset accepts (`schema`, `element`, `complexType`, `sequence`, `simpleContent`/`extension`, `attribute`, `simpleType`/`restriction` with its six facets, `annotation`/`documentation`) and flags the rest as undeclared. Lowering stays the authority: it checks what the structure cannot say (`maxOccurs` below `minOccurs`, a missing type name).
- **XSD tabs** (`Calc::add_xsd_sheet`, `SchemaFormat`, `schema_format`): a schema tab holds the XSD as the tree the meta-schema types, is edited, validated and given formulas like any tab, and lowers (`xsd::lower_node`) every time it is edited; a document that does not lower says why and leaves the tabs bound to it as they were, as for JSON Schema. The prefixes in `type="xs:string"` are resolved against the namespaces declared on the document's root (the tab's `XmlDocument`).
- **`XMLPATH(query, node)`** is a subset of XPath 1.0 over the same tree (`python/xmlpath.rs`): the steps `name`, `*`, `@name`, `@*`, `text()` and `.`, with `/` and `//`; predicates with a position, `last()`, comparisons, `and`, `or`, `not()`, a path alone (it exists), and `position()`, `count()`, `contains()` and `starts-with()`. **The node it is given is the context**, and a leading `/` means the same, so `/line/sku` is `line/sku` with the tab as the root element; given a repeated element it runs on each occurrence (`XMLPATH('.[qty > 1]/sku', Orders.line)`). It returns the matches in document order, once each, as the values and proxies a formula would get by walking there. Like `JSONPATH` it reads all of `node`, so a query over a whole tab is circular with the formulas on it (`Orders.line`, not `Orders`, in the tests). The parent axis, other axes, unions and arithmetic are refused with a message. Comparisons follow XPath: a number against anything compares as numbers, a set of nodes is true if any member is.
- **Not done in this part, and why.**
  - **The XML forms of the field commands** (add an element or an attribute, rename, delete, reorder among elements and among attributes separately) and *Change the schema from a data tab* for an XSD: the commands of 4d find a type in the schema document by a JSON pointer and edit `properties` and `required`; the XSD document needs its own way to find and edit a type. *(Done later, 2026-10-28: see the decisions for the XML field commands.)*
  - **Comments in the window** and the comment commands: the model, the reading and the writing are done; the cell comment, the context menu items and the indicator wait for the workbook layer's look at the window.
  - **Inference of a schema from XML data** and the import and export dialogs belong to the workbook layer.
  - **Files:** `data.xml` in the archive and the manifest wait for the workbook layer. Nothing yet decides, from a file, that a tab is XML; a tab is XML because its schema is an XSD.
  - **The sample workbook** is still all JSON.
  - **Formats the subset leaves out** stay out, as the design says: mixed content (refused in a schema; in data, text next to child elements is kept as `#text` and flagged as undeclared), more than one namespace, `xsi:` attributes.
- **Tests.** In `cliotree-core`: 11 for the XML layer, 20 for XSD lowering (what lowers, each excluded construct by name, the shape of the document, facets), 23 for the data adapter (reading, invalid data, unknown content, comments, writing, namespaces, simple content, dates, numbers), and 4 for the XSD meta-schema (it lowers; the sample reads as a tree it accepts and that lowers the same as the text; it flags what is outside the subset; a schema tree written as XML is the schema again). In `cliotree-calc`: 9 for the `XMLPATH` parser and evaluator and 10 through the real engine (XML tabs, attributes and formulas on them, `XMLPATH` and its dependencies and errors, editing the XSD relowering the tab, a schema that does not lower, the field commands on an XML tab, writing the tab back as XML).

**Decisions made while building step 7a** (the view selector and the generated Default form)
- **The view selector** is the **View > Show as** submenu, with a radio item for each view: **Data tree**, **Default** and **Raw**. The choice is per tab (`ClioApp::views`, a tab not in the map shows its tree), and a tab keeps it while the window is open; saving it in the workbook waits for the workbook layer, like the other view state. Only the Default form exists yet; named forms come in 7b and will be listed between Default and Raw.
- **The Raw view** (`raw.rs`) shows the tab's data as the document it is stored as, pretty printed: JSON for a JSON Schema tab, XML (with the declaration, prefix, namespaces and comments the tab keeps) for an XSD tab. The text is read only but can be selected and copied, and a **Copy** button copies the whole document. **A paste (Ctrl+V) in this view is imported as a file is** (see Import and export, "Pasting"); one choice of the import dialog **replaces the whole document**, if the pasted text parses and has no problems against the tab's schema; otherwise it is refused, nothing changes, and the reason is shown in red above the text (the parse error with its line, or the number of problems with the first six, each with its path). An accepted paste is one undoable edit of the tab (the XML document details of the pasted text are kept and are not part of the undo). Formulas stay where they are and are calculated against the pasted data. The clipboard cannot be read by a button (egui only receives it as a paste), so the paste is the keyboard command, as the hint beside the Copy button says. The control channel has `paste` for it. The view has no formula bar, as the form has none.
- **Switching** first enters what is being typed (the cell being edited, and the text of every field of the tab that was typed and not yet committed). A refused entry keeps the user in the view and says why. Going from the form to the tree selects, and opens the tree down to, the node whose field had the focus; going to the form scrolls to the field bound to the selected node. Only that exact node is looked for: the *nearest control above* the design promises for a node that has no control of its own (an item the stepper is not on) is not done yet.
- **What the form view leaves out of the window:** the formula bar, the schema bar and the table pane, since they belong to the tree. The arrow-key movement of the tree is off in the form, where the keyboard works as it does in any form (Tab and Shift+Tab between fields). The status bar, the trust banner, the issues panel and the menu stay. Undo and redo (the menu, and the keys while no text field has the focus) are the workbook's own.
- **The generated form is drawn from the schema each time** (`form.rs`, one `Painter` over the `TypeSpec` and the data). The root is a heading, the schema's `title` or the tab's name; an object is a group titled by its field name; the help text of the schema is on the label (and under the title of a group); a required field has a red mark. Fields of an object that the schema does not define are not drawn (the tree shows them). Data that is not of the field's type (an array where a number should be) is shown as its summary and is read only.
- **Editors by type:** a toggle for a boolean; a dropdown for an enumeration (with *(none)* when the field is optional); a text field for numbers, dates, date-times and strings, with a hint for the form of the text, and several lines for a string whose `maxLength` is over 200. **A date is a text field with the hint `yyyy-mm-dd`, not a date picker**: the picker is a separate `egui_extras` feature, and a field that validates as typed is what the design asks for first; the picker can be added without changing anything else. An error value shows as its code in red with the message on hover and cannot be edited.
- **Reading and writing.** A field shows the tab's current value, so it follows every edit, recalculation and undo. **A text is a draft only while it is being typed:** each change is checked as it is typed (`entry::classify`, so with the same rules and messages as the grid); a text that does not fit stays in the field, outlined in red with the reason under it and on hover, and is not written; a text that fits is entered when Enter is pressed or the field loses the focus, as one ordinary undoable edit, and Escape drops the draft. A toggle or a choice is entered at once. An empty text clears the node (an optional field becomes absent, as in the grid), and typing into an absent optional field creates it. A field also gets the outline when the data in the tab does not fit, as the grid does.
- **A form has no formulas.** A text that starts with `=` is refused in a field of a number, a date or the like, with a message that says so; in a text field it is the text. A field bound to a node that has a formula, or is inside the result of one, is read only, tinted as computed, with the small *fx* marker (the formula, or what computes it, on hover); the waiting marker shows while it is out of date. Formulas are edited in the property page of 7b and in the tree until then.
- **Repeaters.** An array whose items are scalars, or objects with no array or map inside, is a table with a header row and a narrow row header (`[0]`), and *New* in the title. **The row commands *Move up*, *Move down* and *Delete row* are in the context menu of the row** (right click on the row header or on the background of a row), not buttons, which took too much width. A click on the header of a column of objects sorts the array by it, as in the tabular view (a real, undoable reorder, with the same refusal rules). **Filtering, hiding, and showing the counts of hidden and filtered rows are not in the form's tables yet**; the tabular view of the tree has them. Any other array is stacked: one item at a time with *Previous item*, *Next item*, "3 of 17", *Delete*, and *New*, which goes to the new item. A move swaps neighbours, since a form's table has no hidden rows. An array that is computed (a formula on the array node) cannot be added to, deleted from, sorted or reordered.
- **Absent containers.** An optional or missing object is a label with *Add*, which makes it with its required fields filled in, as the tree's defaults do. An absent array is made by *New*.
- **Numbers are right aligned** in their fields, in the form's tables as well (the grid of the data tree and the tabular view still show them to the left; they can follow).
- **Icons** are the Phosphor Icons font (MIT, public and free to use and ship), taken unchanged from the `egui-phosphor` 0.14.0 crate, which cannot be used itself since it is built for an earlier egui; the licence notice is in `crates/cliotree-app/assets/PHOSPHOR-NOTICE.txt`. It is added to egui on the first frame as a font family of its own (so it never replaces a text glyph) and takes effect on the next, and an icon button draws a letter on the first frame. A button's name (for a screen reader and the tests) and its tip are what it does, not the glyph.
- **Maps** are a list of entries (the key, the value's editor, *Delete entry*) and a field for the key of a new entry with *Add entry*. An empty key or one that is there already is refused with a message.
- **Control channel:** `view` (`{"name": "Default"}` or `"Data tree"`), `status` reports `view`, and `enter` types into the selected node's field when the view is a form (so one scenario drives either view).
- **Not done in 7a, and why.** Saving the view and the stepper position in the workbook (the workbook layer); the marks of an untrusted workbook on the fields (the grid has `#UNTRUSTED!`; a form field shows the stored value without the mark yet); filters and hiding in the form's tables; a date picker; XML forms of the field and the comment commands (as for the tree).
- **Tests.** `tests/forms.rs`: 16 that drive the window (the selector and the view kept per tab; a committed field being an undoable tab edit; a value that does not fit staying in the field with the reason, the view refusing to change until it is corrected; no formulas; computed fields; the toggle and the choice; an absent optional field; the table with new, delete and move; sorting; maps; the selection carried back to the tree; the control commands; the Raw view showing JSON and XML, a conforming paste being accepted and undone, and a paste that does not conform, or is not JSON or XML, being refused with the reasons) and two new visual snapshot tests with three images (the Default form of Orders and of Prices, and the Raw view). Other snapshot images changed because the tab row lost the label and the menu has a new item; the Linux ones are made on the runner.

**Decisions made while building step 7b** (named forms, layout mode and the property page)
- **The design** is `cliotree_core::form`: `FormDesign {version, title, controls}`, a tree of `Control`s (field, group, repeater, label, button, separator) with a flat serde struct, validated against the `builtin:form` schema (`form_schema()`) when read; a newer `version` is refused. A control is addressed by its place in the tree (`Address`, a list of indexes), which is also how the selection is kept.
- **Default is generated until it is changed.** `generate(spec)` makes it from the schema; the first edit stores it (*materialises* it) and from then on it no longer follows the schema. Undoing back to nothing leaves it generated again. *Reset Default form...* discards the stored design. Other forms are always stored. Per tab, `FormStore` (in `cliotree-calc`) maps name to design, Default first; names follow the rules of a tab name and also refuse `Raw`.
- **View > Forms** holds *New form...*, *Duplicate form...*, *Rename form...*, *Delete form...*, *Reset Default form...* and the *Edit form* check box. New and Duplicate start from the form shown and show the copy. A dialog that is refused keeps its reason in the dialog. The view selector lists Data tree, Default, the tab's forms, Raw. A form that is gone shows Default.
- **Layout mode** (*Edit form*, also a check box above the form) draws every control disabled and selectable: click to select, a selection and hover outline, a context menu (Move up, Move down, Move into the group above, Move out of the group, Delete control). A strip of buttons adds a field, group, repeater, label, button or separator: into the selected group, after the selected control, or at the end. Layout mode has its own **Undo layout** and **Redo layout**; design edits are not in the workbook's undo history and do not change its revision.
- **The property page** is a right panel: path (a combo of what can be bound), label, help, editor (Automatic, Text, Multiline), read only, group columns (1 to 6), repeater table or stacked and its columns, label text, button label and procedure, visible-when and enabled-when, the move buttons, and the **formula** of the bound node (entered through the ordinary entry path, so undoable in the workbook). It also lists **Fields not on the form** (with *Add*) and **Broken controls** (with *Re-bind* and *Remove*). A broken control is drawn as a red placeholder that says why.

**Decisions made while building step 7c** (button procedures)
- **The call** is `Engine::call(&Call, ctx) -> Result<Vec<Write>, Failure>`, beside `eval`, so the language stays behind the engine trait. A `Call` is the procedure name, the tab, the name of the form, the label of the button and the time limit. A `Write` is a place and an operation: `Set(value)`, `Remove`, or `Append(value)` to an array. The engine gives the writes back and applies nothing; an engine without procedures fails with `#NAME!`.
- **Which function runs.** Only a public function of a workbook module: `name`, or `module.name` when two modules define the same name. A built-in, a tab, a module itself and a name that starts with an underscore are refused with *there is no procedure called ...*. A function of a module that failed to load says so.
- **`form` and `ctx`.** `form` is the proxy of the root of the tab, the same object a formula reaches by tab name. **Writing goes through the same proxies**: `form.customer.status = 'shipped'`, `form.items[0] = {...}`, `del form.note`, `form.items.append({...})`. A write to an object takes a field name, to an array an index that exists (`append` adds; an index past the end is refused), and `None` clears an optional field. While a procedure runs, `append` on an array is the method, not the field of its items. **A formula cannot write**: the proxies raise `TypeError` ("a formula cannot change data; only a button procedure can") unless a procedure's list of writes is open. `ctx` has `form` (the name of the form), `button` (its label) and `tab(name)`, which gives the proxy of another tab, for reading and writing. Return values are ignored.
- **What a procedure reads** is the data as it was when it started. **It does not see its own writes**: `form.count = 10` then `form.count` still reads the old value, since the writes are collected and applied after the call. A procedure that needs a running value keeps it in a variable.
- **Applying** is `Calc::apply_procedure`, on the thread that owns the workbook. Every write is checked against the schema of its place (`validate_at`, as an entry is) and refused if it is in the result of a formula or on a formula; removing a required field is refused (an item of an array, or an optional field, may go). The writes run inside one entry of the history, `Run <button>`; if any is refused, the entry is taken back (`History::abort`) and leaves nothing to undo or redo, and the message names the place and the reason. Writes are applied in the order they were made, so an append followed by a write to the new item works.
- **The conflict rule** is the one for an evaluation that an edit overtook: if a node the procedure wrote, or one above or below it, was edited after the procedure started (`edited_since` its version), none of the writes are applied and the message names the node. An edit to another node does not refuse them.
- **When it runs.** Clicking asks the session (`Session::run_procedure`). The call waits until nothing is out of date and nothing is running, then takes a fresh snapshot, so it reads what is on the screen with every formula brought up to date. Only one is waiting or running at a time; another click is refused with a message, and undo and redo (the keys and the menu items) do nothing in the meantime. In an untrusted workbook `run_procedure` refuses, and a procedure that was waiting when trust was taken back finishes with a message and does not run.
- **The thread.** The evaluation thread takes `Job::Evaluate` and `Job::Call`; a call comes back as `ProcedureResult` (`Evaluator::take_calls`). It has its own limit, `EvalSettings::procedure_limit` (10 s, the design's button procedure time limit), given to the engine's watchdog for that call; a procedure that does not stop within the limit and the grace period is abandoned like a formula, with a message and no writes. `Session::take_finished` gives the outcomes (`Finished { call, outcome }`), and `Status::procedure` is the label of the button that is waiting or running, which the status bar shows as `Running <label>...`.
- **The button in the form.** A click first enters what is being typed (the text of the cell being edited and every draft of the form; a refused entry stops the click and shows why), then asks for the procedure. A button is disabled, with the reason as its tip, when it has no procedure, when the workbook is not trusted, and while any procedure waits or runs (so all the buttons of the workbook are disabled). A failure, or a refused write, shows as `<button>: <message>` in the line above the form, and the data is as it was. In layout mode buttons are drawn disabled, as before.
- **Control channel:** `click_button {label}` clicks the button of that label on the form shown, and `status` reports `procedure`; `wait_idle` waits for a procedure as it does for evaluation and takes its outcome into `notice`.
- **Not done in this step, and why.** *Visible when* and *enabled when* are still stored and edited but not evaluated: they are expressions on controls with dependencies, results kept in memory and the pending marker, which is a second use of the evaluator and is the next part of the form work. The property page offers a text box for the procedure, not a list of the functions of the modules. The Immediate window and data source writes (6b) are not here. A procedure's writes through `append` and a numbered index only reach arrays that exist; making an absent optional array or object is `Set` of the whole value.
- **Tests.** In `cliotree-calc`, `procedure_tests.rs`, 16 against the real interpreter: the writes as one undoable entry; reading the data as it was and knowing the form and the button; writing to another tab through `ctx`; a write that does not fit refusing all of them and leaving no entry; an exception; a computed node; removing an optional field and refusing a required one; replacing and removing items; which names can be procedures; a formula that tries to write; waiting for the workbook to be up to date; one at a time; an untrusted workbook; the time limit; and the conflict rule both ways. In `cliotree-app`, `tests/buttons.rs`, 9 that drive the window (a click and its one undo, a field typed but not entered, an exception shown, a refused write, a missing procedure, untrusted and no-procedure buttons disabled, undo waiting, the control channel) and one on the status text.

**Decisions made while building step 8a and 8b** (the workbook layer, files)
- **Entries are made in memory.** `cliotree-calc` builds and reads a `Package`, an ordered list of `(path, bytes)`; `cliotree-app` turns it into a zip and into a file. The calculation crate still touches no filesystem. `Calc::to_package(&Meta)` and `Calc::from_package(syntax, &Package)` are the two ends; `Meta` is what the application adds (workbook id, application version, the state of each tab's view, and the entries this version does not know).
- **The layout is the design's**, with the entries in a fixed order (manifest, then each tab's data, overlay and forms in tab order, then the modules, then unknown entries in path order), JSON pretty-printed with a stable key order, LF, UTF-8, a trailing newline, and the zip written with one fixed time (1 January 1980), fixed permissions and one compression level. Saving what has not changed gives the same bytes (tested at both levels). The overlay is left out when a tab has no formulas and no view state.
- **The manifest** records `format_version` (`1.0`), `app_version`, `workbook_id`, `reserved_names_version`, the engine (`rustpython` and the revision pinned in `vendor.lock`, which is a constant to keep in step with it), the tabs in order (name, kind `data`, schema binding `builtin:jsonschema`, `builtin:xsd` or `sheet:<Tab>`, `auto_update` when on, and the forms in display order) and the modules in order.
- **Reading is in two passes**: schema tabs first, so that the tabs bound to them can be typed, then the rest; then the tabs are put in manifest order, auto-update is switched on (it needs the tabs that use the schema to be there), the forms are read and the modules added. Nothing is run and nothing is evaluated. Afterwards nothing is out of date, there is nothing to undo, and the workbook counts as saved; the caller decides about trust and then calls `recalc_all` if the workbook is trusted.
- **Stored errors.** The data file leaves an errored node out; the overlay keeps the error (code, message, origin, traceback) and reading puts the error value back into the node, so an untrusted workbook shows its errors without running anything. A formula that does not parse comes back as `#SYNTAX!`. A formula saved while out of date is saved as `pending`.
- **Versions.** The same major version opens; a newer minor version opens with a warning and keeps what it does not know (including `settings.json`, `datasources.json` and `reports/`, which this version does not read yet and writes back unchanged); a newer major version is refused with the version it needs. A different engine revision gives a warning.
- **A file that breaks the rules still opens, with a warning**, for a tab name that is not a valid name (such as `Orders schema`), a form that cannot be read (dropped), a module that cannot be added, and a formula the schema cannot hold (dropped). It is refused for what cannot be repaired: no manifest, an unreadable manifest, a tab name that is not safe as a file name or two that differ only in case, a missing data file, and a tab whose schema tab is missing or cannot be used as a type.
- **Safety of reading.** `Package::insert` refuses a path that is empty, absolute, has `..` or `.` or an empty part, a backslash, a colon or a control character. The zip reader (`file.rs`) limits the entries (10,000), the bytes of an entry (512 MiB) and the total (1 GiB), reads at most one byte beyond the limit whatever the header says, and refuses duplicates and encrypted entries. These are constants until the preferences exist. The `zip` crate is used with only `deflate-flate2` (pure Rust, no encryption, no C library).
- **Saving** waits for outstanding evaluation, writes to a temporary file beside the target and renames it over the original, then marks the workbook saved. *Save As* with a new path gives the workbook a new id and carries the trust of the original; saving to the same path keeps the id. A tab that was given its type directly (no schema tab) cannot be saved, which only the tests can make.
- **Unsaved changes** are the history's modified flag, or a change to the forms (`Calc::forms_version`, because form designs are not in the undo history). The window title is the file name, `*` when there are unsaved changes, and `- ClioTree`. *Open...*, *Quit* and the window's close button ask *Save the changes?* (Save, Don't save, Cancel); a workbook with no name goes through *Save As* first.
- **Trust on opening.** The id and the content digest are looked up in the trust record: a match, or a workbook with no formulas and no modules, opens trusted and is calculated; an id that is not recorded opens untrusted with the banner; an id that is recorded with other content opens untrusted and the banner lists what changed. Saving a trusted workbook records its digest. The record is in memory for now.
- **The file browser is `egui-file-dialog`** (MIT; egui only, so no GTK, portal or native dialog is needed, and it works on the runner), vendored from the branch that moves it to egui 0.37 (`vendor.lock`, pinned to a commit; its release 0.15.0 is for egui 0.36; switch to the crates.io release when one for 0.37 exists). *Open...*, *Save As...* and Ctrl+O, Ctrl+S, Ctrl+Shift+S open it, with a `.clio` filter or save extension and the folder of the workbook as the start. Its answer goes through the same `open_path` and `save_as`; if that fails, the text dialog opens with the chosen path and the reason. The text dialog is also what the commands open when `files.browse` is off, which is how the tests type a name. The browser was written with emoji and symbols that the window's fonts lack, and egui 0.37 stops on a character no font has, so its labels and icons are replaced with the Phosphor icons (the font is now also a fallback of the text families, and a character nothing has is drawn as a box); the three symbols it draws without a setting (the OK and cancel marks of its *new folder* and rename dialogs) show as boxes.
- **Control channel:** `open_workbook {path}`, `save`, `save_as {path}` (and `file` and `modified` in `status`) work; `new_workbook`, `close`, `menu`, `context_menu`, `set_option` and `grant` still say they are not supported yet (`new_workbook` came with 8c and `set_option` with 8g).
- **Not done, and why.** The state of each tab's view is carried through the file unchanged but nothing produces or reads it yet (8c); the trust record and preferences are not on disk (8c); `New` waits for a way to create a tab; formulas read from a file have no recorded dependencies until they run, so in an untrusted workbook an edit does not yet mark their dependents stale; a tab whose schema tab cannot be used as a type refuses the file instead of opening flagged.
- **Tests.** In `cliotree-calc`, 18 on the package (round trip of JSON and XML tabs with formulas, forms and modules; identical bytes; the fixed order; the manifest; errors, syntax errors and pending formulas; carried view state and unknown entries; versions; unsafe names and paths; missing files; warnings). In `cliotree-app`, 7 on the zip and the atomic save, 15 without a window on opening, saving, trust, the title, the dialogs and the control channel, and 5 that drive the window (*Save As*, *Open* with the question, cancelling, quitting, and the banner for a file not seen before).

**Decisions made while building column formulas**
- **A rule on top of ordinary formulas.** `Calc` keeps, per tab, a list of rules (`ColumnFormula`: the array, the field, the text), and every item of the array has an ordinary formula on that field with the rule's text, so evaluation, dependencies, errors, display and `parent` are the ones item formulas already have. The rule is what makes a new item get its formula and what is saved. `Calc::set_column_formula`, `remove_column_formula`, `column_formulas`, `column_formula`, `column_of`.
- **Every edit that can add or remove items keeps the items in step** (insert, remove, setting a value on the array or an item): the items that lack the formula get it and a formula past the end of the array is dropped, as operations of the same history entry, so one undo takes an inserted item and its formula back.
- **Overriding one item** (a literal, a different formula, clearing the formula, removing the field) ends the rule in the same entry, and the other items keep their formulas as ordinary ones. Entering the same text again changes nothing.
- **One entry in the history** each for creating, changing and removing a column formula (an `Op::Column` and the item formulas it made); undo puts back the rule, the old formulas and the values the field held.
- **Removing it keeps the values** the formulas produced.
- **Where it can be used:** a field of the items themselves (not inside an object of the items: `items[].price.net` is refused), of an array that is not inside another array (`orders[].lines[].total` is refused), where the schema allows a formula and nothing above the array is computed. These are the open points of the specification, left refused until they are needed.
- **Saved once.** The overlay has a `columns` list (array path, field, text); the items that are as the rule makes them have no entry, and an item whose formula ended in an error keeps an entry without text (status and error only). Reading gives every item without an entry the formula, marks nothing out of date and runs nothing. Saving what was read gives the same bytes.
- **The trust record** has one item for the column (`column formula Orders!items[].total`) and none for its items.
- **In the window:** a click on a header of the tabular view **selects the column** (outlined header, tinted cells; the name box shows `items[].total`), and the formula bar shows `=` and the rule, or nothing; typing a formula and pressing Enter sets it, and clearing the bar removes it. Anything but a formula is refused with the reason. Fields inside objects of the items and summary columns say why they cannot have one. **Sorting moved to the header's context menu** (Sort ascending, Sort descending), because the click is the selection now; the form tables still sort on click. The sample's three item totals are now one column formula.
- **Not done:** a mark on the cells of a column that tells they belong to a formula (they have the computed tint), the forms setting a column formula, and a column formula for a nested array.

**Decisions made while building step 8c** (what a file carries besides the tabs, and what the user keeps apart from it)
- **Workbook settings** are `WorkbookSettings` in `cliotree-calc` (`settings.rs`): the eight settings of the table under Settings and limits, each with its key, default, default ceiling and smallest value (1, or 0 for the grace period). Times are whole milliseconds and sizes whole bytes, so the keys say so (`formula_time_limit_ms`, `max_response_bytes`).
- **`settings.json` holds only what differs from the defaults**, in the order of the table, then the keys this version does not know, in key order, which are kept and written back. A workbook with default settings has no `settings.json`, so its files stay as they were, and a later change of a default reaches it. A value that cannot be used (not a whole number, below the smallest value) is left at its default, with a warning; a file that is not a JSON object is the defaults, with a warning. Either way the workbook opens.
- **Trust.** The settings are one item of the digest, `workbook settings`, when they are not the defaults. So a workbook with no formulas and no modules still has no executable content and opens trusted, and a settings file edited outside the application is listed in the banner like a changed formula.
- **Changing the settings** is `Calc::set_settings`, one entry of the history (`Change the workbook settings`). Nothing in the window calls it yet: that is the Options dialog. Undo and redo put the settings back, and the window passes the new values on (below).
- **Ceilings and what is in force.** `Ceilings` is the user's maximum for each setting, and `WorkbookSettings::effective` gives each setting held down to its ceiling. Opening a file whose settings a ceiling holds down says so in the notice (*The workbook asks for a formula time limit of 5000; your ceiling of 2000 is used.*).
- **The evaluation thread follows the settings.** The window compares what is in force with what the thread was last given, every frame, and on a change calls `Evaluator::reconfigure` with a new engine factory (for the `range` guard) and new limits. The thread's interpreter was made with the old ones, so the thread is retired: at once if it is idle, otherwise when what it runs comes back, and the next evaluation starts a fresh one, which loads the modules again, as it does after an abandoned thread. The data source settings are kept and checked but not used until data sources exist (6b).
- **The user's files** (`prefs.rs` in `cliotree-app`) are `preferences.json` and `trust.json`, in `%APPDATA%\ClioTree` on Windows, `~/Library/Application Support/ClioTree` on macOS and `$XDG_CONFIG_HOME/cliotree` (or `~/.config/cliotree`) elsewhere, or in the folder named by `CLIOTREE_CONFIG_DIR`, which the end-to-end tests set so that they never touch the user's own. Two files rather than one, so that a change to the recent files does not rewrite the trust record. Both are versioned (`"version": 1`); a newer version is read for what this one knows, everything it does not know (top-level keys and keys inside the sections) is written back, and the higher version number is kept. A missing file is the defaults and is not created until something changes. A file that cannot be read is renamed to `*.json.unreadable` with a warning, so that writing the defaults later does not destroy it.
- **What the preferences hold now:** the ceilings, the limits for reading a workbook (zip entries, total and per-entry size), the bounds of the undo history, and the recent files. Every known value is written, so the file shows the user what can be set. The appearance, display, editor and import preferences of the Options dialog arrive with it.
- **Another window may write the files.** Every change reads the file again, makes the change, and writes it atomically, so two windows that each trust a workbook keep both decisions. The change holds in memory even if writing fails, and the notice says so.
- **When trust is recorded:** on saving a trusted workbook (as before), and now also on *Trust this version*, so that a workbook trusted from the banner opens trusted the next time even if it is not saved. *Save As* of a workbook that is not trusted carries the original's record to the copy's new id, so the copy opens with the same list of changes.
- **The view state** of a tab is the `view` object of its overlay (`view_state.rs`): `show` (`"raw"` or `{"form": name}`, left out for the data tree), `tables` (one entry per array shown as a table, in path order, with `hidden_columns`, `hidden_rows` and `filters`), and `table`, the one in the pane. Rows hidden by hand are saved by position and become the items at those positions when the file is read, so they stay with their items through a sort as before. Filters are saved with their condition and operands as typed. Changing view state is not an unsaved change, as it is not an edit; it is written with the next save. Keys of the object this version does not know are kept. State that no longer fits (a form or an array that is gone, a row past the end) is dropped without a warning, since it changes only what is drawn. Which nodes are open in the tree is not saved.
- **File > New** (Ctrl+N), after the question about unsaved changes, makes a workbook with a data tab `Data` bound to a schema tab `DataSchema` whose record has no fields yet (`{"type": "object", "properties": {}}`), with auto-update on, so that the fields are added from the data tab with the commands of 4d. It has no file, a new id, nothing to undo, and is trusted, having no executable content. Making tabs of other kinds, and adding tabs to a workbook, wait for a design of their own; import (a later step) is the other way tabs arrive. The application still starts with the sample.
- **Recent files** are the ten workbooks opened or saved last, newest first, as absolute paths, in the preferences; the same file is listed once (ignoring case on Windows). *File > Open Recent* lists them by name, with the folder on hover, and *Clear the list*; choosing one asks about unsaved changes first. A file that is no longer there is taken off the list when it is chosen, and the notice says why it did not open.
- **Control channel:** `new_workbook` works (it does not ask about unsaved changes, as `open_workbook` does not), and `status` reports `recent_files`.
- **Not done, and why.** Nothing edits the workbook settings or the preferences in the window yet, apart from the recent files: that is the Options dialog, as is the list of trusted workbooks with *Revoke* (`TrustStore::revoke` exists). The import limits (file size, nesting depth) come with import. *Save and restart* comes with the Options dialog.
- **Tests.** In `cliotree-calc`, 9 on the settings (`settings_tests.rs`: the file, only what differs, unknown keys, values that cannot be used, a file that cannot be read, undo and redo, the digest, ceilings, the defaults of the design) and 2 on reconfiguring the evaluation thread, idle and while running. In `cliotree-app`, 8 on the user's files (`prefs.rs`: defaults with no files, trust kept for the next session, two windows, unknown keys and a newer version kept, values that cannot be used, a file moved aside, the recent list, memory only) and 15 without a window (`workbook_state_tests.rs`: view state saved and restored with the same bytes, hidden rows after a sort, a form view and one that is gone, unknown view keys; trust from a save and from the banner read by a later session, a copy that is not trusted; settings reaching the thread and back on undo, a ceiling on opening, reading limits from the preferences; *New*, its question, and the control channel; the recent list kept on disk, and a file that is gone). The shared control scenario now ends with `new_workbook`, in process and on the running application.

**Decisions made while adding table columns and number and date formats**
- **One list in screen order**, `Control.table_columns`, holds the order, the visibility and the properties of the columns, with the row numbers as an entry named `#` so that they are a column like the others (a field of the items named `#` would be shadowed by them). `Control::arrange_columns` gives the columns as the screen has them: those listed that the items have, in order; `#` first if it is not listed; then the fields not listed, shown. A listed name the items do not have is not drawn but is kept, so a field that is renamed back gets its properties back. `Control::set_columns` stores a list that is the default (every column shown, in the schema's order, with no properties) as nothing.
- **The first designs' `show`** (the columns shown, in order, the others hidden) is still read; the first change to the columns writes `table_columns` instead and drops `show`. The design version stays 1.
- **A column is selected through its control.** Layout mode keeps the selected control and, beside it, the name of a column of its table; selecting anything else clears it. Changes to columns are design edits like any other, each one step of *Undo layout*, and typing into a column's title or help is one step. The column page has *Back to the table*.
- **Row numbers** are stored as `numbering` (`index`, `decimal`, `lower-alpha`, `upper-alpha`, `lower-roman`, `upper-roman`) and `start` on the `#` column, each left out when it is the default; a start that was not set follows the numbering when it changes (0 for the index, 1 otherwise), and one that was set is kept. They only label the rows: sorting, moving and the paths are unchanged, and the row's menu is the same.
- **The title of a column in layout mode** spans the column, or its title where that is wider (an automatic column, the row numbers): the cell's `max_rect` joined with the space its title used. The response of the cell is not used, since it reaches past the column by the spacing, into the next title.
- **Title fonts belong to the table** (`title_font`, `title_font_size`, `header_font`, `header_font_size` on the repeater), and a column's `font` is the font of its cells only: the titles of a table are one row, and read best in one font. The header row is as tall as its font needs, and the rows as tall as the largest cell font. A column's title has its own alignment (`title_align`), apart from the cells' (`align`), so a column of numbers can have its cells on the right and its title on either side.
- **The column page offers only one-line editors** (automatic, or one line of text): a cell of a table has the height of a row, so several lines do not fit.
- **Formats are in `cliotree-core`** (`format.rs`, with `form::Format` for a control's or a column's three properties), English month and day names, and are applied by the form only. A format is shown while the field does not have the focus, and the stored value while it does; the field's editor keeps its own id, so that the change of text when the focus arrives does not make it another widget. A string that is not a date (in a field that has a date format) is shown as it is.
- **Not done:** formats in the data tree and its tabular pane, a format by locale (the separator is always a comma and the decimal point a point), typing a value in its format (`1,234.50`), resizing columns by dragging their edge, and dragging a column to move it.
- **Tests.** In `cliotree-core`, the formatting of numbers, dates, date-times and date strings; the columns and formats in the design document and their bounds; the arrangement from the list, from the old `show`, and by default; and a default list stored as nothing. In `cliotree-app` without a window, moving (by one, and past hidden columns), showing and hiding, the last column of the items kept shown, a column's properties, and undo. In `tests/forms.rs`, selecting a column by its title and setting its title and the alignment of the row numbers; hiding and ordering columns from the table's page; a number shown in its format and typed as stored; the number format on a field's page, and none for a text field; and dates in a field and a column of a JSON tab. **Decisions made while building the renaming of a tab** (step 8d)
- **One operation in `cliotree-calc`**, `Calc::rename_sheet`, recorded as `Op::RenameSheet`. The history needs nothing rewritten: its entries name tabs, but they are undone in order, so an entry made before a rename is only reached after the rename has been undone, when the tab has its old name again.
- **What moves with the tab** is moved by name: its place in the order, the bindings (`sheet:<Tab>`) of the tabs that use it, its forms (`FormStore::rename_tab`), and what the dependency index knows of its formulas (their places include the tab's name). The formulas that read the old name, those that looked for the new one, and the tab's own formulas are made out of date; nothing is rewritten. An evaluation that was running is dropped as overtaken, as after any edit.
- **The window follows renames, not the rename.** `Calc::take_renames` gives the renames since it was last called, undoing and redoing included, and the window moves what it keeps for a tab (the current tab, open nodes, views, tables and their filters, form drafts, layout mode, the view state read from the file) at the start of each frame and after its own undo, redo and rename.
- **The name check** is `Calc::tab_name_problem`: the rules of a tab name, unique among the tabs ignoring case (the tab's own name in other letters is allowed), and not the name of a module. Adding a tab still does not use it (see step 5b's decisions): no command adds tabs yet.
- **The warning counts identifiers** (`Calc::mentions`, with the same tokenizer that finds what a module uses), so a field or a word in a string with the tab's name is counted too. A column formula counts once.
- **The dialog selects the name** when it opens, so typing replaces it, and *Rename* is disabled while the name has a problem. A double-click on a sheet tab, its context menu, and *Edit > Rename tab...* open it; typing in progress is entered first, and nothing opens while a button procedure runs. The control channel has `rename_tab` (`from`, `to`).
- **Tests.** In `cliotree-calc`, the place, data and formulas kept; the old name missing and the new one found; one entry to undo and redo; earlier edits undone after the rename; refused names; a change of case; bindings and forms following. In `cliotree-app` without a window, the window's state following a rename and its undo, a renamed tab saved under its new name with its binding and view and opened again, the dialog's checks and wording, and the control command; in the window, renaming from the context menu with a refused name on the way.

**Decisions made while building tab management and import** (step 8e)
- **Three recorded operations in `cliotree-calc`**: `Op::AddSheet` and `Op::RemoveSheet` hold the whole tab as it was (`SavedTab`: its data, formulas, column formulas, schema role, XML document, forms and index), so adding and deleting are each other's reverse; `Op::Bind` holds the schema before and after. Nodes are shared, not copied, so a tab put back has the same node ids. Putting a tab back registers what its formulas read again and calculates them again, since what they read may have changed meanwhile.
- **New tabs are made by `create_data_tab`, `create_json_schema_tab` and `create_xsd_schema_tab`**, which check the name as a rename does (the check that step 5b left for when tabs could be made) and record the entry. Loading a file still uses the unrecorded `add_sheet` family, since opening a file is not an edit.
- **Deleting a schema sheet that tabs use is refused** rather than unbinding them, so a delete never changes another tab and undoing one never has to rebind.
- **The window follows tabs as it follows renames.** `Calc::take_removed` gives the tabs taken out since it was last called, undoing and redoing included; the window forgets what it kept for them, opens the root of any new tab, and shows the last tab if the current one is gone. `follow_renames` became `follow_tabs`.
- **Inference is in `cliotree-core` (`infer.rs`)**: `infer_json` gives a JSON Schema document and the data without its nulls, `infer_xsd` gives XSD text, and `text_lines` the array of a text file's lines. The XSD text is read with the XSD meta-schema to become the schema sheet's tree, and lowered to read the data, so an inferred schema goes through the same path as one written by hand. Ties between kinds go string, number, integer, boolean, object, array. XML text is typed by a type that every value fits (integer, then decimal, boolean, date, dateTime, else string), so no value of an inferred XML schema is invalid; an empty value makes the type a string. Child order is merged across instances: a name not seen before goes after the name before it, and instances that disagree, or elements of one name that are apart, are reported.
- **Matching tries every schema sheet** by reading and validating the whole file against it, when the file is read; the dialog keeps the counts. The data that is matched is the data without nulls (see the inference table).
- **An inferred schema starts with auto-update off.** With it on, no second tab could use it, and the next file of the same shape would get another schema of its own.
- **JSON written by hand is read leniently on import** (`json::parse_lenient`): a comma before a closing `]` or `}`, and `//` and `/* */` comments, are passed over and listed in the report, since files like the randomuser.me sample have them. They are blanked rather than removed, so a real error is still reported at its line and column in the file. Opening a workbook stays strict.
- **The import is one history entry** built with `begin_entry`; if its second tab fails (which the checks before it should prevent), the first is undone.
- **Dropping files.** egui gives the paths of dropped files; each is read at once and its dialog waits its turn (`ClioApp::imports`). While files are dragged over the window, a layer says what dropping them does. The web port will need the bytes instead of the path.
- **Scroll bars are solid** (`ScrollStyle::solid`): egui's floating ones are hidden until the pointer is near, so a wide imported table did not look as if it scrolled. A form scrolls both ways, and a table in a form has its own horizontal scroll bar, as the tabular pane does. All the Windows snapshot images changed with this; the Linux ones must be made again on the runner.
- **The file dialog's `save` flag became a purpose** (`Browsing::Open`, `SaveAs`, `Import`), shared by the file browser and the text dialog that the tests use.
- **Not done, and why.** Export, which is a step of its own; importing a `.xsd` or a JSON Schema file as a schema sheet (it imports as data, with a schema inferred for it); a new tab with its own XSD (there is no blank XSD to start from yet; an XML tab comes from importing or from an XSD sheet already there); reordering tabs by dragging; reading a dropped file's bytes on the web.
- **Tests.** In `cliotree-core`, 11 for inference: objects, arrays and required fields; nulls; the most common kind and ties; mixed numbers; empty arrays; text lines; XML elements, attributes, repeats and order; namespaces; disagreeing orders; what is refused; typing of text; and 1 for lenient JSON. Each inferred schema is lowered and the data validated against it. In `cliotree-calc`, 6 more in `tabs_tests.rs`: new tabs and their entry, an import as one entry, names checked, a deleted tab coming back with its formulas, forms and place, what cannot be deleted, rebinding and its undo. In `cliotree-app`, 14 in `tab_commands_tests.rs` (both kinds of new tab, deleting the current tab, the delete warning, rebinding, names from file names, data fitting a schema, data fitting none and the next file fitting the inferred one, XML with an inferred XSD and the next file fitting it, refused files, JSON with a trailing comma, text, dropped files and a dropped workbook, the control commands), and one window test: `+` makes a tab and its context menu deletes it.

**Decisions made while building export** (step 8f)
- **`Calc::export_text`** (`cliotree-calc/src/export.rs`) gives the text of a tab's file with the same writers a save uses, so an exported file is the tab's `data.json` or `data.xml` as the workbook holds it, indented (two spaces) or compact. `export_formats` says what a tab can be written as: its own format, and text too when its root is a JSON array of strings. `export_schema` names the schema tab that can go beside it: the one the tab is bound to. A schema tab has none, since its schema is built in.
- **The format follows the schema**: XML for a tab whose schema is an XSD, an XSD schema tab included (written as `.xsd`), and JSON for the rest. Writing one as the other is refused.
- **Text** is one line for each string with a newline after each, so text import reads back the same array. Errored items are left out, as they are from JSON. A string with a line break in it would come back as two lines, so text is not offered for such a tab, and asking for it is refused with the item's index.
- **The dialog comes first, then the file.** *Export...* in the dialog opens the file browser to save, starting on `<Tab>.<ext>` in the workbook's folder. A name without an extension is given the format's. The choices are kept while the file is chosen, so a write that fails shows its reason in the file-name dialog and the user can try another name.
- **The schema file is named after the data file** (`orders.json` gives `orders.schema.json`, `orders.xml` gives `orders.xsd`) and replaces a file of that name, which the dialog says. The browser asks only about the data file. If the two names would be the same (exporting XML data as `a.xsd` with its schema), the export is refused. The schema is not offered with text. Both files are written atomically, the data first.
- **Nothing is recorded**: an export changes nothing in the workbook, so it is not an undo entry and does not make the workbook dirty. Success shows no message, as a save shows none.
- **The control channel** gets `export` (`tab`, `path`, `format`, `compact`, `schema`), which answers with the path of the schema file, if one was written.
- **Not done, and why.** A recent-folder memory for exports (the browser starts where the workbook is); exporting several tabs at once.
- **Tests.** In `cliotree-calc`, 3 in `package_tests.rs`: JSON with computed values and no formula or errored node, indented and compact, and its schema tab lowered again; XML and its XSD read back, compact, and refusing JSON; an array of strings as text, errored items left out, and a line break refused. In `cliotree-app`, 6 in `export_tests.rs`: what the dialog starts with; the dialog's way through the file-name dialog, the extension added, the schema beside the file, and importing the file again choosing the schema it was exported with; an imported XML file exported with its XSD and read back to the same text, comments included; a text file out again as the same lines; a schema file that would be the data file; a failed write keeping the dialog and the choices.

**Decisions made while building the code editor window** (step 10a)
- **A second operating-system window** (`code.rs`), shown with egui's immediate viewports, so it can sit on another monitor as Excel's Visual Basic editor can. It opens at 900 by 600 points. Where a backend cannot open windows (the headless tests), egui draws it as a window inside the main one, which is how the tests drive it. Closing it, or *File > Close and return to ClioTree*, hides it; Alt+F11 in it brings the main window to the front. Opening another workbook keeps it open, with no module in it.
- **Typing goes to the workbook after a pause.** Each open tab holds its text as typed. It goes to the workbook (`Calc::set_module_source`, one undoable *Edit module X*) once typing has paused for a second, and at once before undo, redo, saving, opening, a new workbook, quitting, closing a tab or the window, and the module commands. This is how "rapid typing is merged": a burst is one entry, and a module is not reloaded, nor its formulas recalculated, at every key. The history is not changed for it. The status line says *loading...* while text waits to go in.
- **One history.** Undo and redo in the editor (Ctrl+Z, Ctrl+Y, Ctrl+Shift+Z and the *Edit* menu) are the workbook's, not the text box's own, so there is one history for both windows. What was typed and has not gone in yet is undone first, as one entry (*Undo typing*). After an undo or redo the tab shows the source the workbook now has.
- **Inserting, removing and renaming a module are undoable now** (`Op::AddModule`, `Op::RemoveModule`, `Op::RenameModule`), as tabs became in 8e; step 5b had them outside the history. Being in the history also makes them changes to save, which they were not: a new module could be lost without the question about unsaved changes. Removing puts the module back in its place on undo. Opening a file clears the history, so loading modules is not an edit.
- **Insert > Module** makes an empty module named `Module1`, `Module2`, ... (the first free number; names ignore case), as Excel does, opens it and puts the cursor in it. Rename asks for the name in a dialog that says why a name cannot be used as it is typed (`Calc::module_name_problem`); remove asks first and says that *Edit > Undo* puts it back. Renames reach the open tabs through `Calc::take_module_renames`, undone and redone ones included.
- **The explorer** lists the modules in their order, the one shown selected and a failed one in red with the reason on hover. A click opens a module (a double click too). The context menu of a module has *Open*, *Rename...*, *Remove...* and *Insert module*, and the *Modules* branch has *Insert module*.
- **The text** is egui's text box with egui_extras' Python highlighting (the simple highlighter, no new dependency) in the monospace font at 13 points, with the line numbers beside it, and long lines not wrapped: the pane scrolls both ways. Enter keeps the indentation of the line and adds a level after a line whose code ends with a colon (a colon in a comment or a string does not count); Tab inserts spaces to the next stop of four, or indents every selected line; Shift+Tab takes up to four spaces off each line touched (`code_text.rs`). Indentation is always spaces.
- **The procedure box** lists the module's top-level functions (`def` and `async def` at the start of a line, read from the text as typed) and shows the one the cursor is in, or *(General)* above the first, as the VBE does. Choosing one puts the cursor on its line and scrolls to it.
- **The status line** says what loading the module shown came to: *loaded*, *loading...*, *failed to load:* with the reason in red, or *not loaded, because the workbook is not trusted*. In an untrusted workbook modules are shown and edited as usual and nothing is loaded, as 5c decided.
- **A jump waits for a frame without a click**, and for the window's second frame: egui takes the focus from every text box a click is not on, and a window's first frame only measures it, so asking for the focus then is lost.
- **Not done here, and why.** *Compile*, export and import of `.py` files and the *Forms* branch are 10b; the Immediate window and the *Code editor* page of the Options dialog (font, indent width, line numbers, highlighting, wrapping) are 10c, so the editor uses the defaults that page will have. Name completion in the editor, a search box, and a mark on a tab whose text has not gone in yet are not built.

In `cliotree-app`, 5 in `code_text_tests.rs` (Enter, Tab, Shift+Tab, the procedure box's functions, line numbers) and 6 window tests in `tests/code.rs` (Alt+F11 and *Insert > Module*, a burst of typing as one entry with undo and redo, Tab and Shift+Tab, the procedure box, renaming and removing from the explorer with undo, the status line for a failed module and in an untrusted workbook). **The Tools menu**

**Decisions made for a formula over what is inside**
- **The question is the window's; the refusal stays in the calculation layer.** `Calc::set_formula` still refuses a formula over formulas (`EditError::ContainsFormulas`), so a script or a caller that did not ask cannot erase them by accident. The window asks before entering, from `Calc::detail_inside` (or `detail_inside_column`), which counts the values no formula computes and lists the formulas, stopping at each formula; it then enters with `set_formula_replacing` or `set_column_formula_replacing`.
- **Values count, not only formulas.** Typed and imported values are detail as much as formulas are (the owner's correction): a formula over an array of items asks, though the calculation layer has always allowed it. Nulls do not count. Changing a formula already on the node does not ask, since what is inside it is its own result.
- **One entry.** The formulas removed and the formula entered are one undoable *Set formula at X*; the old values come back with undo because the formula's entry keeps the node as it was.
- **Where it is asked.** Entering in the cell or the formula bar, the formula of a column, and the formula box of the form designer. While the question is open the text being typed waits: Enter does nothing more, and Escape cancels the edit as No does. *No* ends the edit, as Escape does. The control channel gets the question as its error.
- **Tests.** In `cliotree-calc`, 2 in `calc_tests.rs` (replacing the formulas inside, with undo and redo; what `detail_inside` counts) and 3 in `columns_tests.rs` (a formula on the array replacing its column formula, with undo; one item's formulas; what a column formula would erase). In `cliotree-app`, 1 window test in `tests/ui.rs` (No keeps everything, Yes enters and erases, undo brings it back, and a formula on a leaf does not ask); the test of typing a column formula now answers the question, since the column held typed quantities.

**Decisions made for checking and files in the code editor** (step 10b, 2026-10-28)
- **Compile is *Debug > Compile Module1*,** as in the Visual Basic editor, and in a module's context menu. There is no debugger, so it is the only item of *Debug*. It puts what was typed in the workbook first, then shows a list under the code: *Compile Tax: 2 problems*, one line each, *Line 2, column 8: ...*. A click opens the module and puts the cursor at that line and column. The list is closed with its x.
- **The list is live, not a picture taken at the click.** It is worked out each frame from `Calc::module_problems`, so a fix makes its problem go, and a failure found when the module loads comes in when loading ends (*loading...* until then). In a workbook that is not trusted nothing is loaded, and the list says that it holds only what can be found without running the module.
- **What it finds** (`Calc::module_problems`): a syntax error, alone, since nothing else can be read then (the double-underscore check is one); in a module on a cycle of imports, the import that closes the cycle, with the cycle named; an import of something that is neither a workbook module nor one of the standard library modules formulas may use (`Syntax::standard_modules`, so it is found before loading, and in an untrusted workbook); and a failure while loading (an exception, a name that clashes), with the line Python names in it. An unknown import is not listed a second time as the load failure it causes. The places of imports come from the parser (`ModuleInfo::import_at`).
- **Export and Import** are in the editor's *File* menu, as in the Visual Basic editor, and *Export...* in a module's context menu. They use the same file browser as the workbook's files, drawn in the editor's own window. Export writes the source as it is, UTF-8, `.py` added to a name without an extension. Import reads a UTF-8 file of at most the import size limit, drops a byte order mark, turns CRLF line ends into LF, and adds a module after the others, named after the file: characters that cannot be in a name become `_`, a name taken or reserved gets a number (`Tax2`), and a name kept for internal use (`_x`, `cliotree...`) gets `Module_` before it. It is one entry in the history (*Insert module Tax2*) and the module opens.
- **The *Forms* branch** lists the customised forms under their tabs; a generated form has no design to show. A form opens in a tab of its own, titled `Orders: Entry`, as the JSON it is stored as, highlighted as JSON and indented by two spaces. Typing goes in after the same pause as a module's, but **only a text that is a usable design replaces the design** (`FormDesign::from_json`: JSON that conforms to `builtin:form`). Otherwise the form keeps its design, the status line says why in red, and the text stays as typed until it is fixed. A change made in layout mode is shown in the tab. Forms are not in the workbook's history (step 7b), so Ctrl+Z in a form's tab is the text box's own undo.
- **Tests.** In `cliotree-calc`, 1 in `python/tests_modules.rs` (each kind of problem with its line and column). In `cliotree-app`, 3 window tests in `tests/code.rs` (*Compile* and a click on a problem, then fixing it; export and import, with the numbered name and a missing file; a form's text that is not a design and one that is).

**Decisions made for the Immediate window and the Code editor page** (step 10c, 2026-10-28)
- **The Immediate window is a pane at the bottom of the editor,** shown at first, hidden and shown with *View > Immediate window* or Ctrl+G, as in the Visual Basic editor. It shows each expression (`> Tax.half(7)`) and its result below it, an error in red; *Clear* empties it, and the line to type in is under it.
- **It runs as a formula on the node selected in the workbook's window would** (`this` is that node, or the root of the tab shown), and the pane says where: *this is Orders.items[0]*. It goes to the evaluation thread as a job of its own (`Session::run_immediate`, `Immediate`), waits its turn as a button procedure does, so it reads the workbook up to date, and runs under the formula time limit; one that does not stop is abandoned as a formula is. The text is checked as a formula's is before it runs (syntax, double underscores). Nothing it reads becomes a dependency, and nothing is stored. It needs a trusted workbook; untrusted, the line is not shown and the pane says why.
- **Results are shown in Python's own form** (`repr`), after `PLAIN`, so a node shows as the lists, dicts and values it holds; anything else, a function say, shows as Python shows it. An error shows its code and message, with the traceback under it. This is the "canonical Python form" of the Options section.
- **Only expressions,** as the design says, not statements: `x = 1` is a syntax error. A walrus assignment does not outlive the expression, as in formulas.
- **The history** is `immediate-history.json` in the configuration directory: `{"version": 1, "entries": [...]}`, oldest first. An expression run goes to the end, and the same text typed again moves to the end instead of being kept twice. The file is read again before each change, as the other files are, so two windows keep each other's entries. Up and Down in the line go through it, and Down past the newest gives back what was being typed.
- **The output limit** cuts a result longer than *Largest result shown* at a character boundary, with *... 1234 more bytes left out*. The pane keeps the last 200 expressions.
- **The Code editor page** comes after Editing. *Editor*: the font, the size (8 to 32 points), the indent width (2 to 8 spaces), and the check boxes *Show line numbers*, *Syntax highlighting* and *Wrap long lines*. *Immediate window*: *History entries kept* (0 to 10,000) and *Largest result shown* (1 KB to 16 MB), and *Clear history*, which, like *Revoke*, takes effect on OK and can be taken back with *Keep history* before then. Lowering the number of entries drops the oldest on OK. They are stored under `code_editor` in `preferences.json`.
- **The font is Geist Mono, the only monospace font bundled.** Any other monospace font would have to be found and loaded from the operating system, which nothing else does yet; the page shows the font so that the choice has its place when that comes.
- **Line numbers are painted beside the rows of the text,** a number on the first row of each line, so that a wrapped line takes its rows without a number on each. A wrapped pane scrolls only up and down.
- **Tests.** In `cliotree-calc`, 2 in `session_tests.rs` (results in Python's form, `this`, modules, errors, refusals before running, nothing pending afterwards; the time limit, one at a time, and trust). In `cliotree-app`, 1 in `options_tests.rs` (the page's options and history on disk, *Clear history*, fewer entries kept), 2 more checks in `code_text_tests.rs`, and 1 window test in `tests/code.rs` (a result, an error, the history file, Up and Down, untrusted). The `code_editor` snapshot shows the Immediate window and the *Debug* menu now.

**Decisions made for the Display page** (a leftover of step 8g, 2026-10-28)
- **The page comes after General,** as in the table above, with *Tree grid* (indentation per level, 0 to 64 px [16]; row density; *Show the Type column*; *Show the Formula column*) and *Tabular view* (*Default column width*, 40 to 1,000 px [120]). They are stored under `display` in `preferences.json`: `tree_indent_px`, `row_density` (`compact`, `normal` or `comfortable`), `show_type_column`, `show_formula_column`, `table_column_width_px`.
- **Row density applies to the tabular view too,** so that a table opened inside the tree has rows of the same height as the tree around it. A row is its text's height plus 5, 11 or 17 points, and at least 22, 28 or 34 (`Density::padding`, `style::grid_row_height`); Normal is the height rows had before. Forms keep their own rows: their sizes are part of the form's design.
- **A hidden column is left out of the grid,** not drawn at no width; with the Formula column hidden the Value column takes the rest of the width. The grid keeps the widths it was dragged to for each set of columns, so hiding one column does not give its width to another.
- **The default column width is where a column starts.** A column that was dragged keeps its width; a new table, or a column first shown, takes the default.
- **The formula bar's lines** (Editing, *Formula bar*, 1 to 40 [6]) are stored as `editing.formula_bar_lines`. While editing, the bar grows with the text to that many lines and then scrolls.
- **The comment popup options** (hover delay, popup width and height) came with comments in the window; see the decisions for comments.
- **Control channel:** `set_option` takes `display.tree_indent_px`, `display.table_column_width_px`, `editing.formula_bar_lines`, and `display.row_density` with `compact`, `normal` or `comfortable`.
- **Tests.** In `cliotree-app`, 1 in `options_tests.rs` (the page's values and their limits, what is written to `preferences.json` and read by the next session, `set_option`), and 1 window test in `tests/ui.rs` (a deeper indentation, the three row heights in order, and the grid without its Type and Formula columns).

**Decisions made for comments in the window** (a leftover of step 6, 2026-10-28)
- **What can have a comment** (`Calc::comment_refusal`): on an XML tab, the root and every element, including each item of a repeated element. Not an attribute (XML has no place for one), not an element's `#text`, not an array as a whole (its items are the elements), not a node that is absent, and not a node inside the result of a formula, which the formula replaces on every run. The node that holds a formula can have one: a result keeps the node's comment.
- **An edit of its own** (`Calc::set_comment`, `Op::Comment`): inserting, editing and deleting are each one entry in the history (*Insert comment on Order.qty*), which marks the workbook as modified. Formulas cannot see comments, so nothing is recalculated, and undoing a comment on a formula's node leaves its result alone (an `Op::Replace` of the node would have put back the old value). Text that is only white space is no comment; Windows line ends become `\n`; the same text again is no edit. Text with `--` or ending with `-` is refused with the reason (`comment_text_problem`).
- **The triangle** is drawn in the top-right corner of the Value cell, in the tree and in the tabular view alike, in the palette's warning colour (amber): red already marks invalid data and errors.
- **The popup** opens beside the cell when the pointer has rested on it for the hover delay, wraps at the largest width and scrolls past the largest height. It stays while the pointer is on it, so that a long comment can be scrolled, and it is not shown while a menu is open, which it would cover, or while the comment's box is open.
- **The commands** are in the menu of the Value cell (a right click anywhere on it; a click elsewhere on the cell selects it) and in the tree's row menu: *Insert Comment*, or *Edit Comment* and *Delete Comment*. On a node that cannot have one, *Insert Comment* is shown disabled, with the reason on hover. On a JSON tab there are none.
- **The comment box** opens beside the cell with the comment's text. Enter adds a line break; Ctrl+Enter, or a click outside the box, saves; Esc cancels. Text that is refused keeps the box open with the reason under it. While it is open the grid takes no keys.
- **Display options** (Options, Display, *Comments*): *Hover delay* (0 to 5 s [0.5 s]), *Largest popup width* (120 to 1,200 px [360]) and *Largest popup height* (60 to 1,200 px [240]), stored as `display.comment_hover_delay_ms`, `comment_popup_width_px` and `comment_popup_height_px`.
- **Control channel:** `cell` returns `comment`; `set_comment` (`path`, `text`, absent or null to delete) does what the box does.
- **Not done, and why.** A comment at the end of an element and a comment next to text are still dropped with a warning when a file is read (step 6): giving them a place needs a node that is not an element, which nothing shows yet. An errored or null node is absent from the XML written, and so is its comment, as the design says of errored nodes. Forms show no comments.
- **Tests.** In `cliotree-calc`, 3 in `comments_tests.rs` (insert, edit, delete, undo and redo, and the history's words; what is refused and why, and a JSON tab; a comment through a formula's result, no recalculation, and the XML written). In `cliotree-app`, the Display test in `options_tests.rs` covers the three options, and 3 window tests in `tests/comments.rs` (the menu, the box, line breaks, a refused text, Esc, delete and undo; the popup on hover, an attribute's disabled item, a click outside saving; no commands on a JSON tab). One snapshot, `comments`: the triangle on two cells and one popup.

**Decisions made for the XML field commands** (a leftover of step 6, 2026-10-28)
- **The type is found from its lowering source** (`xsd_fields::xsd_type_path`): the XSD lowering records where each type came from (`schema/element[order]/complexType`, `schema/type[Item]`), and that is turned into the path of the `complexType` node in the XSD tab's tree, by the `@name` of each item on the way. The commands of 4d are the same commands: `FieldPlaces` says `xsd`, and only the edit of the type differs (`Calc::xsd_edited_type`); the data is changed exactly as on a JSON tab, since an attribute is a field named `@name` there too.
- **What a new field is written as.** An element goes at the end of the type's `xs:sequence` (made if there is none), with `minOccurs="0"` unless it is required; an attribute goes after the other attributes, with `use="required"` if it is required. Its type is the built-in type of the choice: `string`, `integer`, `decimal`, `boolean`, `date`, `dateTime`, with the prefix the XSD tab binds to the XML Schema namespace (`xs:` usually, none if it is the default namespace). Keys are put in the order the meta-schema declares, so the XSD is written in the order XSD requires.
- **Names are XML names.** A name must start with a letter or `_`, hold only letters, digits, `_`, `-` and `.`, and not start with `xml`; a prefix (`a:b`) is refused, since a new field has no namespace of its own.
- **An attribute is typed without its `@`.** *Add field* on an XML tab has *Element* and *Attribute* choices above the name, and the name is typed bare; *Rename field* on an attribute shows its name without the `@` and keeps it an attribute. In the calculation layer, a field whose name starts with `@` is the attribute, and renaming an element to an attribute or back is refused.
- **Text content.** On an element that holds text (`xs:simpleContent`), the attributes are those of its `xs:extension`; adding an element is refused with a hint to add an attribute, and `#text` cannot be renamed or deleted (its type is changed on the XSD tab).
- **Reordering keeps the kinds in place.** A new order that moves an attribute into the elements' places, or the reverse, is refused, so dragging an attribute among the elements leaves the dialog open with the reason.
- **Not done, and why.** An element written as `ref` to a global element cannot be renamed from the data tab (the name is the global element's, and rewriting every `ref` is an edit of the XSD tab's own structure); the refusal says so. Choice and `xs:all` groups are not in the XSD subset, so a type has one sequence.
- **Tests.** In `cliotree-calc`, 8 in `xsd_fields_tests.rs` (the fields of an XML record; adding an element and an attribute, what the XSD says and that the data written reads back against it, undo; text content; XML names; renaming and its refusals; deleting with undo; reordering and its refusal; a named type used by every item) and the old refusal test now checks that the commands are available. In `cliotree-app`, 1 in `schema_tests.rs` (an imported XML file with an inferred XSD: add an element and an attribute, rename an attribute) and 2 window tests in `tests/xml_fields.rs` (the *Attribute* choice in the dialog; renaming an attribute without its `@`).

**Decisions made for CSV, TSV and pasting** (2026-10-28)
- **Our own reader, no new dependency.** RFC 4180 is small; `delimited::rows` reads it, and the rows become JSON-shaped data that the JSON inference types and checks as it does any other (`delimited::infer_delimited`). A quote left open makes the rest of the text one cell, with a line in the report.
- **Columns are typed before inference, not cell by cell.** Inference would take each cell's own kind and flag the odd ones; a column of postcodes or codes with a leading zero must stay text, and a column of mostly numbers with one note in it is text rather than numbers with an invalid value. The data is then all valid under the inferred schema.
- **What makes the first row data:** a number or a yes or no in it, as the owner put it. An empty or repeated header name does not; the column gets `column_N` or a suffix instead, so the other names are kept.
- **The paste is a plan like a file's** (`ClioApp::plan_paste`, `begin_paste`): the same dialog, limits, matching against the schema tabs and report. Its format is told from the text, since there is no extension. Replacing the tab's data stayed as a choice of that dialog (`SchemaChoice::Replace`) so that nothing the Raw view could do is lost; the control channel's `paste` still replaces directly. While another text box has the keyboard (the dialog's tab name), the Raw view leaves Ctrl+V to it.
- *File > Import...* lists CSV and TSV beside JSON and XML.
- **Tests.** In `cliotree-core`, 5 in `delimited_tests.rs` (the header and the typing of columns, a first row of data, quotes, empty cells and ragged rows with the column order, blank and repeated names). In `cliotree-app`, 3 more in `tab_commands_tests.rs` (the format of pasted text, CSV and TSV imported, a paste as a new tab and as a replace), and the two Raw view tests in `tests/forms.rs` now go through the dialog.

**Risks that only building and measuring can settle**
- **RustPython.** It is young and not production-ready by its own account, it builds only from a pinned git revision, and the single long builtin call cannot be interrupted. Mitigations: the `PythonEngine` trait, the pinned and vendored build, the abandoned-thread backstop, and the test-suite probes.
- **Proxy layer speed.** The budgets are under Python engine. A miss is addressed by the mitigations listed there.
- **Schema inference and conformance.** Inference over real-world files and the selected conformance cases will turn up cases not yet foreseen. The corpus and the must-reject tests are the way to find them.
- **Report rendering and export** (later version). Charts are drawn live in egui, so producing the same output as an image or PDF needs a second rendering path. The layout model should stay renderer-neutral to allow it.
